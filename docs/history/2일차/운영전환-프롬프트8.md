# 운영전환 프롬프트 8 — 출시 품질 및 최종 검증

현재 DotG 웹사이트 프로젝트의 공개 사이트, 관리자 사이트, Supabase 데이터 계층, 인증·권한, Storage, 데이터 무결성, Playwright E2E, CI/CD 및 Vercel Preview 구조를 전체적으로 조사한 뒤, 실제 Production 출시 직전 필요한 접근성, SEO, 성능, 오류 처리, 운영 모니터링, 배포 체크리스트와 최종 smoke test를 수행할 수 있는 상태로 완성하라.

이번 작업은 운영전환 프롬프트 1~7이 완료된 상태를 기준으로 한다.

현재 완료된 사항:

* local, Preview, Production 환경 분리
* Preview·Production에서 Supabase 설정 필수화
* 운영 환경 mock fallback 차단
* 원격 Supabase migration·production seed 적용
* 원격 DB·RLS·Storage 검증
* 최초 admin 생성 및 실제 로그인
* anon/member/editor/admin 권한 체계
* 관리자 route·Server Action·RLS 다중 권한 검사
* 프로젝트·공지사항·모집·사이트 설정·연락처·SNS CRUD
* Storage 이미지 정합성·rollback·orphan 점검
* 관리자 UI 상태 처리 및 데이터 무결성 강화
* Playwright E2E 구축
* Pull Request CI
* local Supabase DB test
* 타입 drift 검사
* Vercel Preview 연결 또는 Preview 검증 기반
* Production 배포 승인·rollback 절차 기반

이미 완료된 환경, 인증, DB, Storage, E2E, CI/CD 구조를 다시 구현하거나 되돌리지 마라.

이번 작업의 핵심 목표는 다음과 같다.

```text
공개 사이트 품질 점검
→ 접근성 검증
→ SEO·메타데이터 검증
→ 성능·이미지·캐시 검토
→ 오류·404·fallback 검증
→ 운영 로그·모니터링 준비
→ Preview 최종 검증
→ Production 배포 체크리스트
→ 배포 후 read-only smoke
→ 출시 준비 상태 판정
```

새로운 대규모 기능을 추가하는 작업이 아니라, 현재 구현된 서비스를 실제 사용자에게 공개해도 되는지 검증하고 필요한 마지막 보완만 수행하는 작업이다.

모든 항목을 완벽히 인증 수준으로 만들겠다고 주장하지 말고, 자동 검사와 수동 검증이 가능한 영역을 구분하라.

주요 검증 범위:

* keyboard

* forms
* modal
* navigation
* contrast

## 3. semantic HTML 및 landmark 검토

공개 사이트의 구조를 조사하고 적절한 HTML landmark를 사용하라.

검토 대상:

```text
<header>
<nav>
<main>
<section>
<article>
<aside>
<footer>
```

요구사항:

* 페이지당 주요 `<main>` 하나
* Header navigation에 accessible name
* Footer navigation이 있다면 별도 accessible name
* 반복 section에 의미 있는 heading
* div로만 구성된 버튼이나 링크 금지
* 클릭 가능한 요소는 button 또는 anchor 사용
* article 성격 콘텐츠는 적절한 semantic element 사용

---

## 4. heading hierarchy 보완

모든 공개 페이지와 관리자 핵심 화면의 heading 구조를 검토하라.

원칙:

```text
페이지 제목
→ h1

주요 section
→ h2

section 내부 subsection
→ h3
```

다음 문제를 찾아 수정하라.

* h1 없음
* h1 여러 개가 의미 없이 존재
* h2 없이 h3 시작
* 디자인 크기를 위해 heading level을 잘못 사용
* Card title을 전부 heading으로 사용해 구조가 혼란스러움
* 숨긴 heading이 접근성 tree를 오염

스타일과 semantic level을 분리하라.

## 6. 모바일 메뉴 접근성

Header와 관리자 모바일 메뉴를 조사하라.

다음 상태를 지원하라.

* 메뉴 버튼에 accessible name
* `aria-expanded`
* `aria-controls`
* 열릴 때 첫 적절한 요소로 focus 이동 여부 검토
* ESC로 닫기
* 바깥 클릭으로 닫기 가능 여부
* 닫을 때 메뉴 버튼으로 focus 복귀
* 메뉴가 닫힌 상태에서 내부 링크 focus 불가
* body scroll lock 필요 여부
* screen reader가 상태 변화를 이해 가능

모바일 메뉴 라이브러리를 새로 도입하기보다 현재 구현을 보완하라.

## 14. metadataBase와 canonical

Production 도메인을 기준으로 canonical URL을 생성할 수 있는 구조를 마련하라.

환경 변수 또는 site config를 재사용할 수 있다면 재사용하라.

예시 개념:

```text
NEXT_PUBLIC_SITE_URL
```

단, 새로운 환경 변수가 필요하다면 운영전환 프롬프트 1의 환경 검증 체계와 통합하라.

정책:

### local

```text
http://localhost:3000
```

### Preview

Preview deployment URL 사용 가능하지만 canonical은 Production URL을 사용하는 전략 검토.

### Production

실제 Production domain.

다음을 방지하라.

* localhost canonical이 Production에 배포
* Vercel random Preview URL이 검색 index canonical
* slash 중복
* 잘못된 protocol
* page metadata가 canonical을 덮어쓰는 오류

## 16. robots.txt 구축

## 41. health/smoke endpoint 검토

```text
/api/health
```

필요한 경우 최소 정보만 반환하라.

```json

}
```

DB 연결 확인이 필요하다면 매우 가벼운 read-only query 사용.

반환 금지:

* Supabase key

* migration 상세

* 내부 version dependency

health endpoint가 공격자가 내부 구조를 알 수 있게 과도한 정보를 제공하지 않도록 하라.

필요하지 않다면 기존 smoke route 검증으로 대체하고 이유를 설명하라.

* focus 흐름
* screen reader UX
* 의미 전달
* 모바일 keyboard

## 68. 구현 제약

다음 제약을 반드시 지켜라.

* 운영전환 프롬프트 1~7의 구조를 유지하라.
* 핵심 기능을 전면 재작성하지 마라.

* 새로운 CMS를 도입하지 마라.
* 새로운 인증 시스템을 도입하지 마라.
* Supabase를 다른 DB로 교체하지 마라.
* Storage provider를 교체하지 마라.
* service role key를 클라이언트에 추가하지 마라.
* Production 데이터를 테스트 목적으로 수정하지 마라.
* Production Storage cleanup을 자동 실행하지 마라.
* SEO 때문에 draft 콘텐츠를 공개하지 마라.
* Preview를 검색 engine index 가능 상태로 두지 마라.
* Lighthouse 점수를 위해 기능을 제거하지 마라.
* 접근성 오류를 rule ignore로 무조건 숨기지 마라.
* 성능을 위해 관리자 권한 검사를 캐시하거나 생략하지 마라.
* 관리자의 사용자별 데이터를 공개 cache에 넣지 마라.
* 모든 페이지를 Client Component로 변경하지 마라.
* 모든 페이지를 강제로 static generation하지 마라.
* Production migration을 자동 실행하지 마라.
* Production deployment를 사용자 승인 없이 수행하지 마라.
* 타입 오류를 `any`, `@ts-ignore`, `eslint-disable`로 우회하지 마라.
* 실패한 검증을 skip 처리해 READY로 판정하지 마라.
* 실행하지 않은 테스트를 실행했다고 표현하지 마라.

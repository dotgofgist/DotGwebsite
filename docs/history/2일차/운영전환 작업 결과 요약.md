# 운영전환 작업 결과 요약

## 1. 작업 범위

운영전환 작업은 DotG 웹사이트를 로컬 개발용 구현에서 Preview/Production 공개를 준비할 수 있는 상태로 끌어올리는 것을 목표로 진행했다. 범위는 Supabase 환경 분리, 원격 배포 기반, 인증/권한, Storage 이미지 정합성, 관리자 UI와 데이터 무결성, Playwright E2E, CI/CD, 출시 품질 게이트까지였다.

실제 원격 Supabase 프로젝트 적용, Vercel Preview/Production 배포, 운영 도메인 기준 최종 smoke/Lighthouse 검증은 필요한 URL과 secret이 없어 수행하지 않았다. 따라서 최종 상태는 로컬과 CI 기준 출시 준비 완료, 실제 원격 배포 검증은 미완료다.

## 2. 환경 분리 및 Supabase 설정 강화

Supabase 환경 판별을 공통화하고 `local`, `preview`, `production`의 동작 정책을 분리했다. `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` 검증을 추가했고, 잘못된 URL이나 누락된 환경 변수가 Supabase SDK까지 전달되지 않도록 차단했다.

로컬 개발에서는 Supabase 설정이 없을 때만 public mock/config fallback을 허용했다. Preview와 Production에서는 환경 변수가 없거나 조회가 실패하면 조용히 fallback하지 않고 오류를 드러내도록 바꿨다. public notices도 Supabase 공개 조회 흐름에 연결했다.

관련 문서와 `.env.example`, README, 환경 설정 문서를 갱신했고, `env:check`, `env:check:production`, `test:env` 등 검증 스크립트를 추가했다.

## 3. 원격 Supabase 배포 기반

원격 Supabase 운영을 재현 가능하게 만들기 위해 production용 최소 seed를 분리했다. 기존 개발 seed는 mock content를 포함하고, production seed는 `site_settings` singleton 같은 최소 운영 데이터만 넣도록 정리했다.

원격 배포 전 점검, SQL 실행, 타입 생성, 읽기 smoke, RLS 점검, 관리자 bootstrap용 SQL snippet을 추가했다. 실제 원격 project ref와 access token이 없어서 remote migration push, production seed 적용, remote smoke/RLS 검증은 수행하지 않았다.

로컬 기준으로는 migration/reset/test/storage/RLS/type/build 검증이 통과했고, 원격 배포 절차와 최초 관리자 생성 절차를 문서화했다.

## 4. 인증 및 권한 체계

관리자 인증/권한 helper를 보강했다. `getCurrentProfile()`, `getCurrentAdmin()`, `requireAdmin()` 등을 추가하고 request 단위 cache를 적용했다. 관리자 layout은 dynamic/no-store 정책을 명시해 사용자별 권한 상태가 섞이지 않게 했다.

관리자 영역은 `editor/admin`만 접근할 수 있게 유지했고, admin 전용 기능을 위한 `requireAdmin()` 경계를 준비했다. Server Action은 권한 확인이 입력 검증과 DB mutation보다 먼저 수행되도록 정리했다.

로그인 후 이동하는 `next` redirect 검증도 강화했다. 외부 URL, `javascript:`, backslash, control character, double-encoding bypass 등을 차단해 open redirect 위험을 줄였다.

DB/RLS 테스트에는 profile trigger, 기본 role, self-promotion 차단, editor/admin helper, missing profile 차단, security definer `search_path` 검증을 추가했다.

## 5. Storage 이미지 정합성

Supabase Storage의 이미지 경로와 DB 참조가 어긋나지 않도록 보강했다. bucket별 허용 path 검증, project/site 전용 path 생성, public URL 생성 차단, 안전 삭제 helper와 경고 로그를 추가했다.

이미지 업로드에는 JPEG/PNG/WebP signature와 dimension metadata 검증을 넣었다. 프로젝트 썸네일, 사이트 로고, hero 섹션 이미지 변경 시 업로드 이후 DB 상태를 확인하고, DB 저장 실패 시 업로드된 object를 rollback하도록 보상 처리를 추가했다.

Storage 정합성 점검 명령도 추가했다. `storage:paths:check`, `storage:dangling:check`, `storage:orphans:check`, `storage:orphans:cleanup` dry-run 기준 검증 결과는 모두 0건이었다. 실제 원격 Storage orphan 삭제 `--apply`는 수행하지 않았다.

## 6. 관리자 UI 및 데이터 무결성

관리자 mutation의 결과 표시와 데이터 무결성을 보강했다. 프로젝트, 공지, 사이트 설정 수정에는 `updated_at` 기반 optimistic concurrency를 적용해 다른 관리자가 먼저 저장한 경우 충돌을 감지하도록 했다.

프로젝트/공지 validation을 정리했다. slug 소문자 규칙, tag/member/link trim 및 중복 제거, URL protocol 검증을 강화했다. form field 오류 메시지는 `role="alert"`와 `aria-live="polite"`를 적용했고, submit 버튼 pending 문구와 `aria-disabled` 상태도 정리했다.

DB migration으로 published content의 `published_at` 필수화, current recruitment의 published 상태 제한, `site_settings` singleton 삭제 차단 trigger, URL protocol check, 프로젝트 멤버 `name + role` 중복 방지 index를 추가했다.

## 7. Playwright E2E 구축

Playwright 기반 E2E 체계를 추가했다. Windows/PowerShell 환경에서 Next dev server를 안정적으로 띄우는 helper를 만들고, local Supabase anon key를 자동 주입하도록 구성했다.

E2E global setup은 로컬 Supabase 안전 여부를 확인하고 테스트 계정과 session storage state를 준비한다. teardown은 `e2e-*` 테스트 콘텐츠와 인증 상태 파일을 정리한다.

테스트 범위는 public smoke, auth/authorization, 관리자 CRUD까지 포함했다. 공개 페이지, 상세 페이지, not-found, anon redirect, unsafe next 방어, logout 후 차단, member/editor/admin 접근 차이, editor의 프로젝트/공지 생성과 수정 및 DB 반영을 검증했다.

검증 결과 Playwright는 desktop Chromium과 mobile Chromium 기준 35개 테스트가 통과했다.

## 8. CI/CD 및 배포 자동화

GitHub Actions workflow를 추가했다. PR/main push 기준 `Static Checks`, `Database Tests`, `Production Build`, `Playwright E2E`를 실행하도록 구성했고, 실패 시 artifact를 업로드하도록 했다.

Preview workflow는 same-repo PR에서만 Vercel Preview 배포를 수행하고 fork PR은 secret 보호를 위해 skip하도록 했다. Production workflow는 `workflow_dispatch` 전용으로 만들고, `production` GitHub Environment 승인, main branch 제한, Supabase remote preflight, `supabase db push`, Vercel production deploy, read-only smoke 절차를 마련했다.

dependency review와 Dependabot 설정도 추가했다. Node/pnpm 버전은 `.nvmrc`, `.node-version`, `packageManager`, `engines`로 고정했다.

로컬 검증에서 `ci:static`, `ci:database`, `ci:build`, `ci:e2e`, secret scan이 통과했다. GitHub Actions 자체 실행과 Vercel 배포는 repository secret과 environment 설정이 없어 실제 확인하지 않았다.

## 9. 출시 품질 게이트

출시 전 품질 점검을 위해 SEO, 접근성, release checklist/runbook을 추가했다. `metadataBase`, canonical, Open Graph/Twitter metadata, favicon, manifest, `robots.txt`, `sitemap.xml`, 프로젝트/공지 상세 동적 metadata를 보강했다.

접근성 E2E와 SEO E2E를 추가했고, primary 색상, 중립 텍스트 대비, primary/disabled 버튼 텍스트 대비를 조정했다. E2E 웹 서버는 `supabase status --output json` 기반으로 local anon key를 조회하도록 안정화했다.

출시 문서로 `production-runbook.md`, `release-checklist.md`, `release-readiness.md`를 추가했다. `@axe-core/playwright`, `test:a11y`, `test:seo`, `release:check` 스크립트도 추가했다.

## 11. 최종 상태

로컬 개발 환경과 CI에서 검증 가능한 범위의 운영전환 작업은 준비된 상태다. 환경 변수 누락 차단, 운영 fallback 금지, Supabase 원격 배포 절차, 권한/RLS 경계, Storage 정합성, 관리자 데이터 무결성, E2E, CI/CD, SEO/접근성 품질 게이트까지 마련됐다.

단, 실제 서비스를 공개하기 전에는 원격 Supabase와 Vercel 환경에서 별도 확인이 필요하다. 현재 판정은 `PARTIALLY READY`에 가깝다. 코드와 자동화는 출시 준비가 되었지만, 실제 Preview/Production 배포와 운영 URL 기준 검증은 아직 완료되지 않았다.

## 12. 남은 작업

- Supabase 원격 프로젝트 생성 및 project link
- 원격 Supabase migration 적용
- production seed 적용
- 원격 Supabase smoke/RLS/storage 검증
- 최초 운영 관리자 계정 생성 및 admin role 부여
- GitHub `preview`, `production` Environment 설정
- GitHub required reviewers와 branch protection 설정
- Vercel project와 GitHub Actions secret 연결
- Vercel Preview URL 기준 `smoke:preview` 실행
- Production URL 기준 `smoke:production` 실행
- 실제 도메인 기준 `NEXT_PUBLIC_SITE_URL` 설정 확인
- 실제 URL 기준 Lighthouse 측정과 수동 스크린리더 평가
- 운영 오류 추적/모니터링 도입 여부 결정

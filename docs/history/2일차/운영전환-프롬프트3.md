# 운영전환 프롬프트 3 — 인증 및 권한 체계 보완

현재 DotG 웹사이트 프로젝트의 인증·세션·관리자 권한 구조를 전체적으로 조사하고, Supabase Auth와 `profiles.role`을 기반으로 한 관리자 접근 제어를 운영 환경 수준으로 보완하라.

이번 작업은 운영전환 프롬프트 1과 2가 완료된 상태를 기준으로 한다.

현재 완료된 사항:

* local, Preview, Production 환경 구분
* Preview와 Production에서 Supabase 환경 변수 필수화
* 운영 환경 mock fallback 금지
* 원격 Supabase 프로젝트 연결
* local·remote migration 동기화
* production seed 적용
* 원격 DB·RPC·Storage·RLS smoke test 통과
* `profiles`가 `auth.users` 생성 trigger로 자동 생성
* 신규 profile의 기본 role은 `member`
* 최초 관리자 계정 생성
* 해당 profile의 role을 `admin`으로 설정
* `/admin/login` 실제 로그인 성공
* `/admin` 실제 접근 성공

이미 완료된 migration, 원격 배포 script, production seed, Storage bucket, 최초 관리자 생성 절차를 다시 구현하거나 되돌리지 마라.

이번 작업의 핵심 목표는 다음과 같다.

```text
인증되지 않은 사용자
→ 관리자 영역 접근 차단

member
→ 관리자 영역과 관리자 mutation 차단

editor
→ 콘텐츠 관리 허용
→ 사용자 역할 및 시스템 관리 권한은 제한

admin
→ 전체 콘텐츠 관리 허용
→ 필요 시 역할 관리 권한 허용

모든 mutation
→ UI 상태와 관계없이 서버에서 권한 재검사
```

8. 삭제되거나 profile이 없는 Auth 사용자가 로그인했을 때 어떻게 처리되는가?
9. 로그인 redirect에 open redirect 가능성이 남아 있는가?
10. 관리자 페이지 또는 응답이 잘못 캐시될 가능성이 있는가?
11. Auth 오류의 내부 정보가 사용자 화면에 그대로 노출되는가?

14. editor와 admin의 권한 차이가 실제로 정의되어 있는가?
15. 관리자 role을 가진 사용자가 0명이 되는 상황에 대한 정책이 있는가?

조사 없이 인증 구조를 전면 교체하거나 새로운 인증 라이브러리를 도입하지 마라.

## 2. 역할별 권한 정책 명문화

현재 역할을 다음 기준으로 명확하게 정의하라.

### anon

허용:

* 공개된 프로젝트 조회
* 공개된 공지사항 조회
* 현재 공개 모집 조회
* 활성화된 연락처와 SNS 조회
* 공개 Storage 이미지 조회
* 관리자 로그인 페이지 접근

금지:

* `/admin` 내부 페이지 접근
* 모든 관리자 mutation
* 비공개 콘텐츠 조회
* Storage 업로드·수정·삭제
* profile role 변경

### authenticated member

허용:

* anon과 동일한 공개 콘텐츠 조회
* 본인의 최소 profile 정보 조회가 필요한 경우 해당 범위

금지:

* 관리자 영역 접근
* 관리자 CRUD
* Storage 쓰기
* 자신의 role 변경
* 다른 사용자의 profile 수정
* editor/admin 전용 RPC 실행

### editor

허용:

* 관리자 영역 접근
* 프로젝트 CRUD
* 공지사항 CRUD
* 모집 CRUD와 current 관리
* 사이트 설정 관리
* 연락처·SNS 관리
* 허용된 Storage 경로의 업로드·수정·삭제

기본적으로 금지:

* 다른 사용자의 role 변경
* admin 승격·강등
* 사용자 계정 관리
* 시스템 보안 설정 변경
* admin 전용 기능

### admin

허용:

* editor가 수행할 수 있는 모든 콘텐츠 관리
* 프로젝트에서 실제로 필요한 admin 전용 기능
* 향후 사용자 역할 관리 기능을 추가할 수 있는 서버 권한

역할 정책을 코드, RLS, 문서에서 일관되게 유지하라.

현재 프로젝트에 사용자 역할 관리 UI가 없다면 이번 작업에서 대규모 사용자 관리 화면을 추가하지 마라. 대신 admin 전용 권한 경계를 준비하고 검증하라.

## 3. 권한 검사 API 통일

현재 흩어져 있는 권한 검사 로직을 조사하고 서버 측 공통 API로 정리하라.

필요하다면 다음과 같은 책임을 분리하라.

* 현재 로그인 사용자 조회
* 현재 사용자의 profile 조회
* 인증 필수 검사
* 콘텐츠 관리자 필수 검사
* admin 필수 검사
* role 판별
* 로그인 페이지 redirect
* unauthorized 페이지 redirect

예시 책임:

```text
getCurrentAuthUser()
getCurrentProfile()
requireAuthenticatedUser()
requireContentManager()
requireAdmin()
```

실제 함수명과 파일 위치는 기존 프로젝트 스타일을 따르라.

다음 조건을 만족해야 한다.

* 인증되지 않으면 로그인 페이지로 이동하거나 명확한 인증 오류 처리
* profile이 없으면 권한을 부여하지 않음
* role이 `member`이면 관리자 권한을 부여하지 않음
* editor와 admin을 명확히 구분 가능
* 서버에서 매 요청마다 현재 DB의 role을 확인
* 클라이언트가 전달한 role 값을 신뢰하지 않음
* 쿠키에 role을 별도 저장해 권한의 최종 근거로 사용하지 않음
* 사용자 ID를 Server Action 인자로 받아 권한 주체로 사용하지 않음
* 권한 검사 오류 메시지에 내부 DB 정보나 token을 노출하지 않음

권한 검사를 지나치게 중복 호출해 한 요청에서 동일한 Auth·profile 조회가 반복되지 않도록 React cache 또는 요청 범위 캐시 사용 가능성을 검토하라.

단, 사용자 간 결과가 공유되는 전역 캐시는 사용하지 마라.

## 4. Server Action 권한 재검사

관리자 mutation Server Action 전체를 조사하라.

최소 대상:

* 프로젝트 생성
* 프로젝트 수정
* 프로젝트 삭제
* 프로젝트 멤버 저장
* 프로젝트 링크 저장
* 프로젝트 이미지 업로드
* 프로젝트 이미지 교체
* 프로젝트 이미지 삭제
* 공지사항 생성
* 공지사항 수정
* 공지사항 삭제
* 모집 생성
* 모집 수정
* current 모집 지정
* current 모집 해제
* 모집 archive
* 사이트 설정 저장
* 연락처 생성
* 연락처 수정
* 연락처 삭제
* SNS 링크 생성
* SNS 링크 수정
* SNS 링크 삭제
* 로고 업로드·교체·삭제
* Hero 이미지 업로드·교체·삭제

각 mutation은 함수 진입 직후 공통 권한 검사를 수행해야 한다.

다음 규칙을 적용하라.

```text
Server Action 호출
→ 입력값 처리 전에 현재 사용자 확인
→ profile 및 role 확인
→ 권한 통과
→ 입력값 검증
→ DB 또는 Storage mutation
```

다음 취약점을 방지하라.

* 숨겨진 버튼을 직접 호출해 mutation 수행
* member가 Server Action endpoint를 직접 호출
* 로그아웃한 세션으로 이전 action 재호출
* 클라이언트가 `created_by`, `updated_by`를 조작
* 클라이언트가 uploader ID를 조작
* 관리자 UUID를 form field로 전달해 신뢰
* editor가 admin 전용 action 호출
* redirect만 수행하고 실제 mutation은 실행되는 구조
* 권한 검사 실패 후 코드가 계속 진행되는 구조

`created_by`, `updated_by` 등 작업자 ID는 반드시 서버에서 확인한 `auth.uid()` 또는 검증된 현재 사용자 ID를 사용하라.

## 5. 관리자 route 보호 보완

`src/proxy.ts`와 관리자 layout/page의 역할을 명확히 분리하라.

권장 책임:

### proxy

* 세션 쿠키 갱신
* 비로그인 사용자의 `/admin` 접근을 빠르게 로그인 페이지로 redirect
* 로그인 페이지의 기본 흐름 보조

### Server Component 또는 관리자 layout

* 실제 사용자 존재 확인
* profile 존재 확인
* role이 editor 또는 admin인지 확인
* 권한 없는 authenticated 사용자를 `/admin/unauthorized`로 이동

### Server Action

* mutation 직전 독립적인 권한 재검사

proxy만을 최종 권한 경계로 사용하지 마라.

다음 경로를 구분하라.

```text
/admin/login
→ 비로그인 접근 허용

/admin/unauthorized
→ 로그인한 비관리자 접근 허용

/admin 및 하위 경로
→ editor/admin만 접근
```

무한 redirect가 발생하지 않도록 다음 시나리오를 검증하라.

* 비로그인 사용자가 `/admin` 접근
* 비로그인 사용자가 `/admin/login` 접근
* member가 `/admin` 접근
* member가 `/admin/unauthorized` 접근
* editor가 `/admin/login` 접근
* admin이 `/admin/login` 접근
* 로그아웃 직후 `/admin` 접근
* 세션 쿠키가 손상된 상태

이미 로그인한 editor/admin이 `/admin/login`에 접근하면 `/admin`으로 보내는 동작을 검토하되, 구현 시 redirect loop가 생기지 않도록 하라.

## 6. 안전한 `next` redirect 강화

로그인 후 사용할 `next` parameter 처리 방식을 조사하고 open redirect 가능성을 차단하라.

허용 조건:

* 같은 사이트의 내부 경로
* `/`로 시작하는 상대 경로
* 필요하면 `/admin` 하위 경로

금지 예시:

```text
https://evil.example
//evil.example
javascript:alert(1)
/\evil.example
인코딩으로 우회한 외부 URL
제어 문자가 포함된 값
```

다음 조건을 만족하라.

* URL decoding 이후에도 안전성 검사
* double encoding 우회 검토
* protocol-relative URL 차단
* backslash 기반 우회 차단
* 빈 값은 기본 `/admin` 사용
* 지나치게 긴 redirect 값 제한
* 잘못된 값은 오류 대신 안전한 기본 경로 사용 가능
* 검사 함수에 단위 테스트 추가

`next`는 redirect 대상일 뿐 권한 증명의 근거로 사용하지 마라.

## 7. profile 이상 상태 처리

Auth 사용자와 `profiles` row의 정합성이 깨진 경우를 처리하라.

다음 상태를 구분하라.

```text
Auth 사용자 없음
→ 비로그인 처리

Auth 사용자 있음 + profile 있음 + role 정상
→ 역할에 따라 처리

Auth 사용자 있음 + profile 없음
→ 권한 부여 금지
→ 관리자 접근 차단
→ 운영자가 확인할 수 있는 로그 또는 안전한 오류

Auth 사용자 있음 + 알 수 없는 role
→ 권한 부여 금지

삭제되거나 비활성화된 Auth 사용자
→ 세션 무효화 또는 로그인 차단
```

일반 사용자가 profile이 없다는 이유로 자동으로 editor/admin profile을 생성하면 안 된다.

`handle_new_user()` trigger의 정상 동작을 유지하되, trigger 실패나 과거 데이터 문제로 profile이 누락된 경우를 안전하게 처리하라.

필요하다면 profile 정합성을 읽기 전용으로 확인하는 SQL snippet 또는 관리 script를 추가할 수 있다.

대규모 사용자 동기화 기능은 이번 범위에 포함하지 마라.

## 8. role 변경 반영 정책

사용자의 role이 변경됐을 때 기존 로그인 세션에서 권한이 어떻게 반영되는지 확인하고 정책을 정리하라.

권한의 최종 근거는 JWT custom claim이 아니라 현재 `profiles.role`이라고 가정한다.

다음 시나리오를 검증하라.

* member가 editor로 승격
* editor가 member로 강등
* editor가 admin으로 승격
* admin이 editor로 강등
* 로그인 중 profile 삭제
* 로그인 중 Auth 사용자 비활성화 또는 삭제

최소 요구사항:

* role 강등 후 기존 세션으로 관리자 mutation을 계속 수행할 수 없어야 함
* role 강등 후 관리자 페이지 새 요청에서 접근이 차단되어야 함
* role 승격 후 재로그인 없이 새 요청에서 반영 가능한지 확인
* Server Action은 매번 현재 DB role을 조회
* 클라이언트에 캐시된 role이 권한의 최종 근거가 아님
* 관리자 Header에 표시되는 role도 과도하게 오래 캐시하지 않음

필요하다면 관리자 route를 dynamic 또는 no-store 성격으로 처리하라.

단, 프로젝트 전체의 캐시를 무조건 비활성화하지 말고 관리자 인증 관련 영역에만 적용하라.

## 9. 관리자 응답 캐시 및 뒤로가기 검토

관리자 페이지와 사용자별 데이터가 공유 캐시에 저장되지 않도록 검토하라.

다음 항목을 확인하라.

* 관리자 layout의 static rendering 여부
* 관리자 page의 fetch cache
* Supabase server query의 cache 정책
* 사용자 profile 표시
* 로그아웃 후 브라우저 뒤로가기
* 다른 사용자가 같은 배포 인스턴스에서 이전 관리자 데이터를 볼 가능성
* `revalidatePath()` 이후 인증 정보 캐시 영향

필요하다면 관리자 인증·사용자 정보 조회에 다음 정책을 적용하라.

* dynamic rendering
* no-store
* 사용자별 request-scoped 조회
* 적절한 cache invalidation

다음은 피하라.

* 전역 변수에 현재 사용자 저장
* 모듈 수준 singleton에 profile 저장
* role 결과를 사용자 구분 없이 캐시
* 관리자 페이지 HTML을 공개 CDN cache에 저장

로그아웃 후 브라우저 뒤로가기로 이전 화면이 잠깐 보이는 브라우저 캐시는 완전히 차단하기 어려울 수 있다. 이 경우 새 요청과 mutation이 반드시 차단되는지 우선 검증하고 문서화하라.

## 10. 로그인·로그아웃 UX 및 오류 처리

현재 로그인 UI를 유지하면서 인증 오류 처리를 보완하라.

### 로그인

* 이메일 공백 제거
* 이메일 형식 검증
* 빈 비밀번호 차단
* 중복 제출 방지
* 로그인 처리 중 버튼 비활성화
* 잘못된 계정 정보에 일반적인 오류 메시지 표시
* 사용자의 존재 여부를 과도하게 노출하지 않기
* Supabase 내부 오류 전체를 사용자에게 표시하지 않기
* 서버 로그에는 필요한 진단 정보만 기록
* token, password, cookie를 로그에 기록하지 않기

### 로그아웃

* 서버에서 Supabase sign out 수행
* 쿠키 제거 또는 무효화 확인
* 로그아웃 후 로그인 페이지 또는 공개 홈으로 이동
* 로그아웃 action 실패 시 사용자에게 명확한 상태 제공
* 로그아웃 후 관리자 mutation 차단
* 여러 탭에서의 세션 상태 차이는 문서화

이번 프롬프트에서 비밀번호 재설정, 회원가입, OAuth 로그인 UI를 새로 구현하지 마라. 현재 요구사항에 없다면 범위를 확대하지 마라.

## 11. 로그인 시도 제한 검토

Supabase Auth 자체의 rate limit과 애플리케이션 수준 방어를 조사하라.

다음 사항을 확인하라.

* email/password 로그인 요청 제한
* 반복 실패 시 Supabase가 반환하는 오류
* 애플리케이션에서 추가 제한이 필요한지
* IP 기반 제한을 신뢰할 수 있는 환경인지
* Vercel 환경에서의 요청 IP 처리
* 사용자 존재 여부 노출 위험

이번 작업에서 외부 Redis나 별도 rate-limit 서비스를 무조건 도입하지 마라.

현재 규모에 맞춰 다음 중 합리적인 방식을 선택하라.

* Supabase Auth 기본 rate limit을 문서화하고 사용
* 단순한 중복 제출 방지
* 필요 시 향후 rate limit 도입 지점 명시

메모리 기반 서버 전역 rate limiter는 serverless 환경에서 신뢰할 수 없으므로 운영 보안 기능으로 간주하지 마라.

## 12. admin 전용 권한 경계 준비

현재 admin 전용 mutation이 없다면 억지로 새 관리 기능을 만들지 마라.

다음 항목을 준비하라.

* admin만 통과하는 공통 검사
* editor가 해당 검사에서 차단되는 테스트
* member와 anon 차단 테스트

* 오류 또는 redirect 정책
* RLS/RPC에서 admin 전용 기능을 추가할 때 사용할 기준 문서화

`bootstrap-admin.sql`은 최초 관리자 설정을 위한 운영 절차이므로 일반 웹 요청에서 호출할 수 없게 유지하라.

admin 승격 함수를 public RPC로 노출하지 마라.

## 13. 마지막 admin 보호 정책 결정

현재 사용자 역할 관리 UI가 없더라도, 운영 정책으로 마지막 admin 보호 여부를 조사하고 문서화하라.

다음 위험을 설명하라.

```text
유일한 admin을 editor/member로 강등
→ 관리자 권한 복구를 위해 Dashboard 또는 SQL 개입 필요

이번 작업에서는 역할 관리 기능이 없다면 복잡한 DB trigger를 추가하지 않아도 된다.

대신 다음 중 하나를 선택하고 이유를 명시하라.

* 역할 관리는 Dashboard/운영 SQL로만 수행하며 마지막 admin 확인 절차를 문서화
* 향후 admin 역할 변경 RPC에 마지막 admin 보호 조건을 적용할 수 있도록 테스트·설계만 준비

현재 migration history를 불필요하게 변경하지 마라.

## 15. RLS와 애플리케이션 권한의 일치 검증

애플리케이션 권한 검사와 DB RLS가 서로 같은 정책을 적용하는지 확인하라.

다음 조합을 검증하라.

| 역할     | 관리자 페이지 | Server Action | DB write | Storage write |
| ------ | ------- | ------------- | -------- | ------------- |
| anon   | 차단      | 차단            | 차단       | 차단            |
| member | 차단      | 차단            | 차단       | 차단            |
| editor | 허용      | 허용            | 허용       | 허용            |
| admin  | 허용      | 허용            | 허용       | 허용            |

admin 전용 기능이 있다면 editor는 차단되어야 한다.

애플리케이션 권한 검사만 통과하고 RLS에서 실패하거나, RLS는 허용하지만 애플리케이션에서 불필요하게 차단하는 불일치를 찾아 수정하라.

RLS를 우회하기 위해 service role client를 추가하지 마라.

일반 관리자 CRUD는 로그인한 사용자의 세션과 RLS를 통해 처리하라.

## 16. 테스트 계층 추가

현재 테스트 환경을 조사하고 인증·권한 테스트를 추가하라.

실제 원격 Supabase에 의존하지 않는 테스트를 기본으로 구성하라.

### 단위 테스트

최소 항목:

* 안전한 `next` 경로 허용
* 외부 URL 차단
* protocol-relative URL 차단
* backslash 우회 차단
* 인코딩 우회 차단
* 빈 next의 기본 경로
* 지나치게 긴 next 처리
* role 판별
* editor/admin 콘텐츠 관리자 판별
* admin 전용 판별
* profile 없음 처리
* 알 수 없는 role 처리

### DB 및 RLS 테스트

최소 항목:

* anon의 관리자 table insert/update/delete 차단
* member의 관리자 mutation 차단
* member의 자기 role 변경 차단
* editor의 콘텐츠 CRUD 허용
* admin의 콘텐츠 CRUD 허용
* editor의 admin 전용 기능 차단
* `can_manage_content()` 결과
* `is_admin()` 결과
* profile 생성 trigger
* 신규 profile 기본 role이 member
* `security definer` 함수의 고정된 `search_path`
* 불필요한 PUBLIC execute 권한이 없는지

### Server Action 또는 통합 테스트

가능한 범위:

* 비로그인 action 호출 차단
* member action 호출 차단
* editor action 호출 허용
* admin action 호출 허용
* created_by/updated_by 조작 차단
* 권한 검사 실패 후 mutation 미발생
* role 강등 후 기존 세션 action 차단

현재 테스트 구조상 Server Action 직접 테스트가 지나치게 복잡하다면 권한 helper와 DB RLS를 우선 검증하고, 브라우저 기반 검증은 운영전환 프롬프트 6의 Playwright 범위로 명확히 남겨라.

## 20. 검증

pnpm.cmd lint
pnpm.cmd exec tsc --noEmit
pnpm.cmd build
pnpm.cmd supabase db reset
pnpm.cmd supabase test db
pnpm.cmd run test:env
pnpm.cmd run test:supabase
```

이번 작업에서 인증 관련 별도 test script를 추가했다면 함께 실행하라.

```text
pnpm.cmd run test:auth
pnpm.cmd run test:authorization
```

실제 script 이름은 구현 결과에 맞게 사용하라.

다음 상태를 자동 또는 수동으로 검증하라.

```text
anon → /admin 차단
member → /admin 차단
editor → /admin 허용
admin → /admin 허용

anon → 관리자 mutation 차단
member → 관리자 mutation 차단

editor → admin 전용 검사 차단
admin → admin 전용 검사 허용
```

* local Supabase로 검증한 항목
* 실제 원격 환경에서 수동 확인한 항목
* Playwright 단계로 남긴 항목

테스트를 위해 운영 admin 계정의 role을 변경하지 마라.

## 21. 최종 보고 형식

작업이 끝나면 다음 순서로 결과를 보고하라.

### 1. 기존 인증·권한 구조 분석

* 로그인·로그아웃 흐름
* 세션 갱신 방식
* 관리자 route 보호 방식
* Server Action 권한 검사
* RLS 역할 정책
* 발견한 위험 요소

### 2. 역할별 최종 권한

다음 표 형식으로 작성하라.

```text
기능 | anon | member | editor | admin
```

최소 기능:

* 공개 조회
* 관리자 페이지
* 프로젝트 CRUD
* 공지 CRUD
* 모집 관리
* 사이트 설정
* Storage write
* admin 전용 검사
* role 변경

### 3. 구현 내용

* 공통 Auth helper
* 공통 role helper
* `requireContentManager()`
* `requireAdmin()`
* proxy·layout·Server Action 책임 분리
* 안전한 redirect
* profile 이상 상태 처리
* role 변경 반영
* 캐시 정책
* 로그인·로그아웃 오류 처리
* 테스트 및 문서

### 4. 변경 파일 목록

각 파일에 대해 다음 형식으로 작성하라.

```text
파일 경로
- 변경 목적
- 핵심 변경 내용
```

### 5. Server Action 권한 적용 현황

다음 형식으로 작성하라.

```text
Action 또는 기능 | 요구 역할 | 서버 재검사 | RLS 보호 | 결과
```

### 6. route 보호 현황

다음 형식으로 작성하라.

```text
경로 | anon | member | editor | admin
```

### 7. 테스트 결과

실제로 실행한 명령과 성공·실패 결과를 정확히 작성하라.

DB 테스트 개수와 결과가 출력된다면 함께 작성하라.

### 8. 수동 검증 결과

* 비로그인 접근
* member 접근
* editor 접근
* admin 접근
* 로그아웃
* role 강등·승격 반영

실제로 확인하지 못한 것은 확인했다고 표현하지 마라.

### 9. 남은 위험 요소

* 아직 자동화되지 않은 인증 흐름
* 브라우저 기반 E2E가 필요한 항목
* 사용자 역할 관리 UI 미구현
* 마지막 admin 보호의 운영 의존성
* 외부 rate limit 미도입
* audit log 미구현

### 10. 다음 작업

이번 프롬프트 범위를 넘어 다음 프롬프트에서 처리할 항목만 작성하라.

* Storage 이미지 정합성 강화
* 관리자 UI와 데이터 무결성 보완
* Playwright E2E
* CI/CD
* Vercel Preview·Production 배포 검증
* 운영 오류 추적 및 모니터링

오류나 미검증 항목이 남아 있다면 성공한 것처럼 표현하지 말고 원인과 재현 방법을 명확하게 작성하라.

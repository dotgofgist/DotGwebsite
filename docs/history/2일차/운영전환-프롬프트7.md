# 운영전환 프롬프트 7 — CI/CD 및 배포 자동화 구축

현재 DotG 웹사이트 프로젝트의 환경 설정, Supabase migration·RLS·Storage, 관리자 인증·권한, 콘텐츠 CRUD, 이미지 정합성, 데이터 무결성, Playwright E2E 테스트 구조를 전체적으로 조사한 뒤, Pull Request 검증부터 Vercel Preview 배포와 배포 후 smoke test까지 이어지는 안전한 CI/CD 체계를 구축하라.

이번 작업은 운영전환 프롬프트 1~6이 완료된 상태를 기준으로 한다.

현재 완료된 사항:

* local, Preview, Production 환경 분리
* Preview·Production 환경에서 Supabase 설정 필수화
* 운영 환경 mock fallback 차단
* 원격 Supabase migration 및 production seed 적용
* 원격 DB·RLS·Storage smoke test
* 최초 admin 생성 및 실제 로그인
* anon/member/editor/admin 역할별 권한 경계
* 관리자 route·Server Action·RLS 다중 권한 검사
* Storage 이미지 업로드·교체·삭제 보상 처리
* orphan·dangling Storage 점검 기반
* 관리자 UI 상태 처리와 데이터 무결성 보완
* Playwright E2E 환경과 fixture
* 역할별 인증·CRUD·Storage 브라우저 테스트
* E2E의 운영 Supabase 접근 차단
* headless E2E 실행과 실패 artifact 생성

이미 완료된 환경, DB, 인증, Storage, 관리자 기능, E2E 구조를 다시 구현하거나 되돌리지 마라.

이번 작업의 핵심 목표는 다음과 같다.

```text
Pull Request 생성
→ 의존성 고정 설치
→ lint
→ TypeScript 검사
→ 환경 설정 검사
→ migration 정합성 검사
→ local Supabase 초기화
→ DB·RLS 테스트
→ 생성 DB 타입 drift 검사
→ 애플리케이션 build
→ Playwright E2E
→ 실패 artifact 저장
→ Vercel Preview 배포
→ Preview smoke/E2E
→ merge 가능 상태 보고
```

Production 배포는 별도의 보호된 승인과 검증을 거치도록 구성하고, Pull Request만으로 운영 DB나 운영 사이트가 자동 변경되지 않게 하라.

## 2. CI/CD 전체 구조 설계

workflow를 역할별로 분리하라.

권장 구조:

```text
Pull Request CI
├─ static-checks
├─ database-tests
├─ build
└─ e2e-local

Preview Deployment
├─ PR 검증 통과
├─ Vercel Preview 배포
├─ Preview URL 확인
└─ Preview smoke test

Production Readiness
├─ main branch 검증
├─ migration 상태 확인
├─ production build
└─ 배포 승인 대기

Production Deployment
├─ 수동 승인
├─ migration 사전 점검
├─ migration 적용
├─ Vercel Production 배포
├─ 배포 후 smoke test
└─ 결과 기록
```

이번 프롬프트에서는 최소한 다음을 완성하라.

* Pull Request CI
* local Supabase 기반 DB 테스트
* local Playwright E2E
* Vercel Preview 자동 또는 통합 배포
* Preview 배포 후 read-only smoke test
* Production 배포용 보호된 workflow 골격
* 배포·rollback 문서

Production에 destructive mutation을 실행하는 자동화를 활성화하지 마라.

## 3. workflow 파일 분리

`.github/workflows` 아래 workflow를 책임별로 구성하라.

예시:

```text
.github/workflows/
├─ ci.yml
├─ preview.yml
├─ production.yml
└─ dependency-review.yml
```

실제 파일 수는 repository 규모에 맞게 결정하라.

권장 책임:

### `ci.yml`

* PR 및 main push 검증
* lint
* typecheck
* 환경 검증
* migration 검사
* DB test
* build
* local E2E

### `preview.yml`

* PR Preview URL 확인
* Preview smoke test
* 필요 시 Preview E2E
* 결과를 GitHub check로 표시

### `production.yml`

* `workflow_dispatch`
* production environment 승인
* migration 사전 점검
* 운영 배포
* 배포 후 smoke test
* 실패 시 중단

### dependency workflow

* 의존성 변경 검토
* 취약점 검사
* lockfile 검증

workflow가 너무 세분화돼 동일 install과 build가 과도하게 반복된다면 job 간 artifact 또는 reusable workflow 사용을 검토하라.

복잡한 reusable workflow를 억지로 만들지 마라.

## 4. Node와 pnpm 버전 고정

로컬과 CI의 버전 차이로 실패하지 않도록 런타임을 명확히 고정하라.

확인 및 보완 대상:

* `.nvmrc`
* `.node-version`
* `package.json`의 `engines`
* `packageManager`
* Corepack
* pnpm lockfile 버전

다음 조건을 만족하라.

* Next.js 16과 현재 dependency가 지원하는 Node 버전 사용
* CI에서 정확한 Node major version 사용
* pnpm 버전 고정
* `pnpm install --frozen-lockfile`
* lockfile 불일치 시 CI 실패
* CI에서 자동 lockfile 수정 금지
* 로컬 문서와 CI 버전 일치

예시 개념:

```yaml
- uses: actions/setup-node@...
  with:
    node-version-file: ".nvmrc"
    cache: "pnpm"
```

GitHub Action 버전은 가능한 한 안정된 major 또는 commit SHA pinning 정책을 검토하라.

## 5. 최소 권한 workflow 설정

GitHub Actions workflow의 기본 권한을 최소화하라.

기본 권장:

```yaml
permissions:
  contents: read
```

추가 권한은 필요한 job에만 부여하라.

예:

* Pull Request comment가 필요하면 `pull-requests: write`
* deployment status가 필요하면 `deployments: write`
* OIDC가 필요하면 `id-token: write`

다음 원칙을 지켜라.

* 모든 workflow에 `write-all` 금지
* `pull_request_target` 사용 금지 또는 강한 근거 필요
* fork PR에서 repository secret 사용 금지
* PR 코드가 secret을 읽을 수 있는 workflow 구조 금지
* third-party action은 신뢰 가능한 publisher 사용
* 불필요한 checkout credential 유지 금지 검토
* shell에 secret 직접 echo 금지
* `set -x`와 유사한 secret 노출 방지

## 6. PR static checks job

다음 검증을 독립 job 또는 명확한 step으로 추가하라.


중복되거나 없는 script는 임의로 호출하지 말고 필요한 script를 정리해서 추가하라.

다음 조건을 만족해야 한다.

* secret이 없는 PR에서도 static check 가능

## 7. 의존성 캐시

pnpm store cache를 구성하라.

요구사항:

* lockfile 기반 cache key
* Node 버전 반영
* pnpm cache 공식 지원 방식 사용
* `node_modules` 직접 cache는 신중히 검토
* cache miss에서도 정상 실행
* cache corruption 시 복구 가능
* Playwright browser cache 별도 검토
* Supabase Docker image cache는 유지보수성과 비용을 고려

cache가 검증 결과를 바꾸거나 생성 파일 drift를 숨기면 안 된다.

## 8. local Supabase CI job

GitHub-hosted Linux runner에서 local Supabase를 실행하고 schema와 DB 테스트를 검증하라.

권장 흐름:

```text
1. repository checkout
2. Node·pnpm setup
3. dependency install
4. Docker 사용 가능 상태 확인
5. Supabase local start
6. supabase db reset
7. supabase test db
8. Storage·RLS 점검
9. 종료 또는 runner 정리
```

실제 script에 맞춰 다음 명령을 검토하라.

```text
pnpm supabase start
pnpm supabase db reset
pnpm supabase test db
pnpm run supabase:storage:check
pnpm run supabase:rls:check
```

요구사항:

* development seed만 적용
* production seed 실행 금지
* remote link 사용 금지
* `--linked` 명령 금지
* 원격 project ref 불필요
* local Supabase 시작 실패 시 로그 출력
* Docker service 상태 진단
* DB test 결과가 check에 표시
* 테스트 종료 시 운영 데이터와 무관함이 명확해야 함

Supabase CLI version은 project dependency와 일치하도록 고정하라.

## 9. migration 정합성 검사

CI에서 다음 문제를 감지하라.

* migration 파일 순서 오류
* 중복 timestamp
* 적용된 migration 수정
* local DB reset 실패
* schema change가 migration 없이 발생
* production seed가 development seed에 섞임
* destructive SQL 추가
* RLS 누락
* Storage policy 누락

기존 `supabase:migrations:check`를 재사용하고 부족한 부분만 보완하라.

파괴적 migration 검사는 단순 문자열 검색만으로 완전한 보안을 보장한다고 주장하지 마라.

검토 대상으로 표시할 문장:

* `drop table`
* `drop column`
* `truncate`
* `delete from` without clear scope
* enum 값 제거
* policy 제거
* RLS disable

파괴적 변경이 필요할 수 있으므로 무조건 실패보다 명시적인 override 또는 리뷰 요구 정책을 검토하라.

## 10. 생성 DB 타입 drift 검사

migration 또는 remote schema가 변경됐는데 `database.types.ts`가 갱신되지 않은 상태를 CI에서 차단하라.

권장 흐름:

```text
local Supabase reset
→ 임시 파일로 타입 생성
→ 현재 database.types.ts와 비교
→ 차이가 있으면 실패
```

요구사항:

* 생성 실패 시 기존 파일 훼손 금지
* CI에서 파일을 자동 commit하지 않음
* diff 요약 출력
* 개발자가 실행할 수정 명령 안내
* 줄바꿈 차이만으로 불필요하게 실패하지 않도록 환경 일치
* local 생성 타입을 기준으로 검사
* 원격 credential 없이 동작
* Windows와 Linux 생성 결과 차이 검토

실패 메시지 예시:

```text
Supabase database types are out of date.
Run: pnpm run supabase:types
Commit the updated database.types.ts.
```

## 11. unit·integration test job

현재 존재하는 Node 기반 테스트를 CI에 포함하라.

검토 대상:

* 환경 정책 테스트

## 12. production build job

CI에서 Next.js production build를 수행하라.

요구사항:

* `NODE_ENV=production`
* 안전한 test용 Supabase URL과 anon key
* 실제 원격 Supabase 요청 금지
* production mock fallback 금지 정책 유지
* 환경 변수 검증 통과
* build output 성공
* dynamic route와 metadata build 오류 감지
* `next.config.ts` 검증
* remote image pattern 검증
* bundle secret 포함 여부 점검 가능성 검토

placeholder URL을 사용할 때 실제 네트워크 query가 발생하면 build 구조를 수정해 정적 생성과 runtime query 책임을 분리하라.

오류를 무시하거나 fallback을 다시 활성화하지 마라.

## 13. Playwright local E2E job

운영전환 프롬프트 6에서 구축한 Playwright를 CI에 연결하라.

권장 흐름:

```text
1. local Supabase start/reset
2. E2E fixture 준비
3. Next.js production build
4. Next.js server 실행
5. Playwright browser 설치
6. headless E2E 실행
7. cleanup
8. report와 artifact 저장
```

다음 조건을 만족해야 한다.

* 운영 Supabase 차단
* local E2E environment marker 확인
* test Auth 계정 준비
* storage state 생성
* role별 테스트
* DB·Storage fixture 정리
* 임의 sleep 사용 금지
* CI retry 정책 적용
* 테스트 재실행 가능

## 19. Preview Supabase 전략

* 단순함

## 24. Production migration과 앱 배포 순서

```text

4. backward-compatible migration 적용

6. Production 앱 배포
```

다음 상황을 고려하라.

예:

```text
배포 A
→ 새 column 추가
→ 기존 column 유지
→ 양쪽 호환

배포 B
→ 앱을 새 column으로 전환

배포 C
→ 이전 column 제거
```

## 29. rollback 절차

앱과 DB rollback을 구분하라.

### 앱 rollback

* 이전 Vercel deployment 확인
* 이전 deployment를 Production으로 promote
* 환경 변수 변경 여부 확인
* rollback 후 smoke test

### DB rollback

DB는 단순히 이전 migration 파일로 되돌리기 어렵다는 점을 명시하라.

원칙:

* 파괴적 migration 최소화
* forward-fix 우선
* migration 전에 backup 또는 PITR 정책 확인
* 데이터 삭제 migration은 별도 승인
* rollback SQL은 필요할 때 명시적으로 작성
* 기존 migration 파일 수정 금지

다음 시나리오를 문서화하라.

```text
앱 배포 실패 + migration은 backward compatible
→ 이전 앱 rollback 가능

migration이 이전 앱과 비호환
→ 즉시 rollback 어려움
→ forward-fix 또는 별도 DB 복구 필요
```

## 38. CI 실행 시간 최적화

전체 검증이 지나치게 느려지지 않도록 job 구성을 검토하라.

가능한 분리:

```text
static-checks
→ 빠르게 실패

database-tests
→ Supabase Docker

build
→ Next.js build

e2e
→ Supabase + build + Playwright
```

고려사항:

* job마다 dependency install 반복
* artifact로 build output 전달
* Supabase local 중복 실행
* cache
* 병렬 job
* runner disk 사용량
* Playwright browser 설치 시간

속도를 위해 검증을 생략하지 마라.

PR에서 필수 smoke와 main에서 full E2E를 구분할 수 있으나 핵심 권한·CRUD는 PR check에 유지하라.

## 39. flaky test 관리 정책

CI 재시도에서만 통과하는 Playwright 테스트를 기록하고 해결하도록 정책을 마련하라.

요구사항:

* CI retries 제한
* flaky 결과를 성공으로 숨기지 않음
* Playwright의 flaky 상태 보고
* trace 확인 절차
* 재현 명령
* 임의 sleep 추가 금지
* selector·fixture·비동기 원인 우선 수정

flake가 발견되면 workflow summary 또는 test report에서 식별 가능해야 한다.

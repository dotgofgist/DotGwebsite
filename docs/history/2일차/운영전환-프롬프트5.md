# 운영전환 프롬프트 5 — 관리자 UI 및 데이터 무결성 보완

현재 DotG 웹사이트 프로젝트의 관리자 CRUD 화면, Server Action, query 계층, Supabase schema와 RLS를 전체적으로 조사한 뒤, 실제 운영자가 안정적으로 콘텐츠를 관리할 수 있도록 관리자 UI 상태 처리와 데이터 무결성을 보완하라.

이번 작업은 운영전환 프롬프트 1~4가 완료된 상태를 기준으로 한다.

현재 완료된 사항:

* local, Preview, Production 환경 분리
* 운영 환경 mock fallback 차단
* 원격 Supabase migration·production seed 적용
* 원격 DB·RLS·Storage 검증
* 최초 admin 생성 및 실제 로그인
* anon/member/editor/admin 권한 경계
* 관리자 route, Server Action, RLS의 다중 권한 검사
* 프로젝트·공지사항·모집·사이트 설정·연락처·SNS CRUD
* 프로젝트 대표 이미지, 로고, Hero 이미지 관리
* Storage 업로드·교체·삭제 보상 처리
* Storage orphan·dangling path 점검 기반

이미 완료된 환경 설정, 원격 배포 script, 인증·권한 구조, Storage 정합성 로직을 다시 구현하거나 되돌리지 마라.

이번 작업의 핵심 목표는 다음과 같다.

```text
관리자 입력
→ 클라이언트 UX 검증
→ Server Action 권한 재검사
→ 서버 입력 검증
→ DB 제약 및 RPC
→ 성공·실패 상태 반환
→ 사용자에게 명확한 결과 표시
→ 관련 페이지 재검증
```

관리자 UI에서 버튼이 동작하는 것만으로 완료하지 말고, 잘못된 입력·중복 요청·동시 수정·부분 실패가 발생해도 데이터가 일관된 상태를 유지하도록 하라.

## 2. 관리자 mutation 결과 형식 통일

현재 Server Action의 성공·실패 반환 방식을 조사하고 공통 결과 형식으로 정리하라.

필요하다면 다음과 같은 구조를 사용하라.

```text
status
message
fieldErrors
formError
data
```

예시 개념:

```ts
type ActionResult<T = undefined> =
  | {
      success: true;
      message: string;
      data?: T;
      fieldErrors?: never;
    }
  | {
      success: false;
      message: string;
      fieldErrors?: Record<string, string[]>;
      code?: string;
    };
```

실제 타입은 현재 프로젝트 스타일에 맞게 결정하라.

다음 조건을 만족해야 한다.

* 성공과 실패가 명확하게 구분됨
* 필드별 검증 오류 지원
* 폼 전체 오류 지원
* Supabase 내부 오류를 그대로 노출하지 않음
* 호출부가 redirect 여부를 명확히 결정 가능
* 삭제, 생성, 수정, current 변경 등에서 동일한 패턴 사용
* 이미지 action의 기존 구조화 오류와 충돌하지 않음
* 타입 안전성 유지
* `any` 사용 금지
* 사용자가 재시도 가능한 오류와 재시도 불가능한 오류 구분 가능

모든 Server Action을 무리하게 한 파일로 합치지 마라.

## 3. 관리자 폼 제출 UX 통일

프로젝트·공지·모집·사이트 설정·연락처·SNS 폼에 공통 제출 UX를 적용하라.

최소 요구사항:

* 제출 중 버튼 비활성화
* 제출 중 상태 문구
* 중복 클릭 방지
* 성공 메시지
* 실패 메시지
* 필드별 오류 표시
* 오류 발생 필드와 메시지 연결
* 성공 후 적절한 이동 또는 현재 페이지 유지
* 성공 후 불필요한 오류 상태 초기화
* Server Action 응답 전 낙관적 성공 표시 금지
* 버튼만 비활성화하고 서버 중복 요청 방지를 생략하지 않음

예시 상태:

```text
기본
→ 저장

제출 중
→ 저장 중…

성공
→ 저장되었습니다.

실패
→ 입력 내용을 확인해 주세요.
```

접근성 요구사항:

* 오류 메시지에 `role="alert"` 또는 적절한 live region
* `aria-describedby`
* 첫 오류 필드 focus 이동 검토
* disabled와 `aria-disabled` 구분
* 키보드 제출 가능
* 시각적 색상만으로 오류를 전달하지 않음

공통 버튼이나 상태 컴포넌트가 필요하다면 기존 UI 스타일을 유지하며 추가하라.

## 4. 입력값 보존과 재시도

Server Action 검증 실패 시 사용자가 입력한 값을 최대한 유지하라.

다음 폼을 확인하라.

* 프로젝트 생성·수정
* 공지사항 생성·수정
* 모집 생성·수정
* 사이트 설정
* 연락처 생성·수정
* SNS 생성·수정

다음 원칙을 적용하라.

* 검증 실패만으로 전체 폼 초기화 금지
* 입력값과 field error 함께 반환
* 비밀번호나 파일 binary 등 유지하면 안 되는 값은 제외
* 파일 업로드 실패 후 파일 재선택이 필요한 경우 명확히 안내
* redirect 이전에는 성공 여부 확정
* React의 action state를 사용할 경우 stale state 방지
* 수정 화면에서 기존 DB 값과 사용자의 실패 입력을 구분

브라우저가 기본적으로 input 값을 유지하는 구조라면 불필요한 상태 복제를 하지 마라.

## 5. 저장하지 않은 변경사항 경고

관리자 수정 폼에서 사용자가 내용을 변경한 뒤 이동하려는 경우 경고를 제공하라.

대상:

* 프로젝트 수정
* 공지사항 수정
* 모집 수정
* 사이트 설정
* 필요하다면 생성 폼

다음 시나리오를 고려하라.

* 관리자 내부 링크 클릭
* 브라우저 새로고침
* 브라우저 뒤로가기
* 탭 닫기
* 저장 성공 후 이동
* 저장 실패 후 이동
* 이미지 업로드만 별도로 완료된 경우
* current 설정 등 즉시 action과 일반 폼 변경이 섞인 경우

요구사항:

* 실제 변경이 있을 때만 경고
* 저장 성공 후 dirty 상태 초기화
* 단순 focus나 동일 값 재입력은 변경으로 보지 않도록 검토
* `beforeunload`는 필요한 범위에서만 사용
* 커스텀 route navigation 차단이 과도하게 복잡하다면 최소 안전 범위를 구현하고 한계를 문서화
* 접근성 있는 확인 UI 사용
* 브라우저 기본 경고와 커스텀 모달 중 역할을 구분

Next.js App Router에서 신뢰하기 어려운 비공식 navigation interception 구현을 무리하게 추가하지 마라.

## 6. 삭제 UX와 idempotency 보완

모든 삭제 또는 archive 흐름을 조사하고 안전하게 통일하라.

대상:

* 프로젝트 삭제
* 공지사항 삭제
* 프로젝트 이미지 삭제
* 로고 삭제
* Hero 이미지 삭제
* 연락처 삭제
* SNS 삭제
* 모집 archive
* current 해제

요구사항:

* 삭제 전 대상 이름 표시
* 파괴적 작업임을 명확히 표시
* 삭제 중 버튼 비활성화
* 중복 삭제 요청 안전성
* 이미 삭제된 row에 대한 idempotent 처리
* 실패 시 modal을 닫지 않거나 적절한 오류 표시
* 성공 후 목록 또는 상위 페이지 갱신
* Storage 부분 실패는 기존 프롬프트 4 정책 유지
* archive와 영구 삭제를 명확히 구분
* 삭제 action에 권한 재검사 유지
* 삭제 대상 ID를 hidden input으로 받더라도 서버에서 존재 여부 재검증

사용자가 삭제 취소 버튼과 삭제 확인 버튼을 혼동하지 않도록 UI 우선순위를 정리하라.

## 7. slug 검증과 중복 처리 통일

프로젝트와 공지사항 slug 정책을 조사하고 클라이언트·서버·DB에서 일관되게 적용하라.

정의할 항목:

* 허용 문자
* 영문 소문자
* 숫자
* 하이픈
* 시작·끝 하이픈 금지 여부
* 연속 하이픈 처리
* 최대 길이
* 공백 변환
* 한글 slug 허용 여부
* 대소문자 정규화
* Unicode normalization
* 예약 경로

다음 예시를 처리하라.

```text
My Project
→ my-project

my--project
→ 정책에 따라 정규화 또는 오류

-admin
→ 오류

admin
→ 예약어라면 오류

프로젝트
→ 한글 허용 여부에 따른 처리
```

요구사항:

* create와 update에 동일한 규칙
* 자기 자신의 기존 slug는 수정 시 중복으로 판단하지 않음
* DB unique constraint 유지
* race condition으로 unique 위반이 발생하면 사용자 친화적인 오류 반환
* Supabase error code를 구조화된 slug 오류로 변환
* slug 생성 기능이 있다면 사용자가 직접 수정 가능 여부를 명확히 함
* 공개 URL 변경에 따른 영향 문서화

DB unique constraint를 UI 중복 검사로 대체하지 마라.

## 8. 공백·null·빈 배열 정규화

입력값이 DB에 일관되게 저장되도록 공통 정규화 규칙을 마련하라.

예:

```text
"   "
→ null 또는 빈 문자열 중 schema 정책에 맞는 값

빈 URL
→ null

빈 날짜
→ null

빈 태그
→ 제거

중복 태그
→ 제거

빈 프로젝트 멤버
→ 저장하지 않음

빈 외부 링크
→ 저장하지 않음
```

대상:

* 제목
* 요약
* 본문
* slug
* 태그
* 프로젝트 멤버 이름·역할
* 외부 링크 URL
* 모집 지원 URL
* 연락처 URL
* SNS URL
* 이미지 path
* 날짜
* 선택적 설명

다음 조건을 만족하라.

* trim 규칙 통일
* 빈 문자열과 null의 역할 문서화
* mapper에서 임의 변환이 반복되지 않음
* DB query 조건과 일치
* unique constraint에서 빈 문자열끼리 충돌하지 않도록 함
* 사용자가 입력한 의미 있는 줄바꿈은 보존
* 본문 전체를 무조건 trim해 서식을 파괴하지 않음

## 11. 모집 데이터 무결성 강화

동시에 current인 모집은 최대 1개

## 12. `site_settings` singleton 보장

현재 `site_settings.id = 1` 방식과 production seed를 유지하면서 singleton invariant를 DB 수준에서 검증하라.

목표:

```text
site_settings에는 운영 singleton row만 존재
```

확인할 사항:

* `id = 1` check constraint 존재 여부
* 다른 ID insert 가능 여부
* upsert conflict target
* row 삭제 가능 여부
* row가 없을 때 자동 복구 방식
* concurrent upsert
* production seed 반복 실행
* 관리자 action이 항상 ID 1을 대상으로 하는지
* client가 ID를 전달해 다른 row를 수정할 수 있는지

필요하다면 새로운 보정 migration을 추가하라.

권장 가능한 방식:

* `id`에 check constraint
* singleton update RPC
* ID를 Server Action 내부에서 고정

관리자 폼에서 singleton ID를 사용자 입력으로 받지 마라.

## 15. 날짜와 timezone 정책 정리

프로젝트, 공지사항, 모집에서 날짜와 timestamp 처리를 조사하라.

명확히 구분하라.

* 달력 날짜
* 게시 timestamp
* 생성·수정 timestamp
* 모집 시작·종료 시각
* 사용자에게 표시되는 timezone

기준 timezone은 서비스 운영 기준에 맞춰 명확히 문서화하라.

* UTC 변환 후 날짜 변경

* `new Date("YYYY-MM-DD")`의 UTC 해석 문제
* 공개일 표시가 하루 전·후로 보이는 문제
* 시작일이 종료일보다 늦은 상태

공통 date utility가 있다면 재사용하고 테스트를 추가하라.

## 16. 공개 상태와 `published_at` 정합성

프로젝트·공지·모집의 공개 상태와 `published_at` 정책을 통일하라.

정의할 사항:

```text
draft → published
→ published_at이 없으면 현재 시각 설정

published → published
→ 기존 published_at 유지

published → draft
→ published_at 유지 또는 null 처리 중 기존 정책 선택

archived
→ 공개 query에서 항상 제외
```

현재 구현 정책과 문서를 조사해 일관되게 적용하라.

다음 상태를 점검하는 SQL 또는 테스트를 추가하라.

* published인데 `published_at` 없음
* draft인데 공개 query에 노출
* archived인데 current
* current인데 unpublished
* pinned인데 unpublished인 공지가 공개 노출
* `updated_at`이 mutation 후 갱신되지 않음

자동 수정 migration은 데이터 손상 가능성을 검토한 뒤 결정하라.

운영 데이터가 이미 있다면 보정 migration의 영향과 rollback 가능성을 설명하라.

## 17. 동시 수정 충돌 검토

두 관리자가 같은 콘텐츠를 동시에 수정하는 경우를 고려하라.

예:

```text
관리자 A가 기존 데이터를 열음
관리자 B가 먼저 수정
관리자 A가 오래된 값으로 저장
→ B의 변경이 덮어써짐
```

현재 규모에 맞춰 optimistic concurrency를 검토하라.

가능한 방식:

* `updated_at`을 form에 포함
* update 조건에 기존 `updated_at` 포함
* update row가 0개면 충돌 오류
* 사용자에게 새로고침 후 다시 시도 안내

적용 대상 우선순위:

* 프로젝트
* 공지사항
* 모집
* 사이트 설정

연락처·SNS처럼 작은 row에도 적용할지 유지보수성을 고려하라.

요구사항:

* 클라이언트가 전달한 `updated_at`을 권한 정보로 신뢰하지 않음
* 충돌 시 강제 덮어쓰기 금지
* 충돌 오류를 일반 DB 오류와 구분
* 성공 후 최신 `updated_at` 반영
* timestamp 정밀도 문제 고려
* Storage 이미지 action과 충돌할 경우 기존 프롬프트 4 정책 유지

복잡도가 지나치게 크다면 핵심 콘텐츠부터 적용하고 나머지는 명확한 후속 항목으로 남겨라.

## 18. DB constraint 보정 migration

조사 결과 DB 수준의 invariant가 부족하다면 새로운 migration을 추가하라.

검토 대상:

* slug unique

* 시작일·종료일 순서

* 원격 적용은 이번 작업에서 자동 실행하지 않음
* 원격 적용 전 별도 preflight 필요

기존 데이터에 위반 row가 있어 constraint 추가가 실패할 수 있다면 진단 SQL을 제공하라.

## 27. 검증

작업 완료 후 프로젝트의 실제 script를 확인한 뒤 최소한 다음 검증을 수행하라.

```powershell
pnpm.cmd lint
pnpm.cmd exec tsc --noEmit
pnpm.cmd build
pnpm.cmd supabase db reset
pnpm.cmd supabase test db
pnpm.cmd run test:env
pnpm.cmd run test:supabase
```

이번 작업에서 관리자 또는 무결성 관련 test script를 추가했다면 함께 실행하라.

예:

```powershell
pnpm.cmd run test:admin
pnpm.cmd run test:validation
pnpm.cmd run test:data-integrity
pnpm.cmd run supabase:migrations:check
```

실제 script 이름은 구현 결과에 맞게 사용하라.

새 migration을 추가한 경우 다음을 확인하라.

```text
빈 local DB
→ migration 전체 적용 성공
→ development seed 성공
→ DB test 성공
→ 타입 생성 성공
→ build 성공
```

다음 실패 시나리오를 검증하라.

```text
중복 slug
→ 사용자 친화적 field error
→ 기존 데이터 유지

잘못된 날짜
→ DB mutation 없음

동시 수정 충돌
→ 오래된 요청 차단
→ 최신 데이터 유지

current 모집 동시 지정
→ 최종 current 최대 1개

site_settings 다른 ID insert
→ DB 차단

중복 제출
→ 중복 콘텐츠 생성 방지
```

원격 Supabase에는 새 migration을 자동 push하지 마라.

최종 보고에 원격 적용 전 실행해야 할 명령을 정확히 작성하라.

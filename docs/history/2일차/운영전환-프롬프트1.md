# 운영전환 프롬프트 1 — 환경 분리 및 운영 설정 강화

현재 DotG 웹사이트 프로젝트의 전체 코드를 먼저 조사한 뒤, 로컬 개발 환경과 Vercel Preview·Production 환경을 명확하게 분리하고 운영 환경의 설정 누락을 조기에 감지할 수 있도록 환경 설정 구조를 강화하라.

이번 작업에서는 원격 Supabase 프로젝트 생성, 실제 migration 적용, Playwright 테스트, CI/CD 구축까지 진행하지 않는다. 해당 작업들은 이후 프롬프트에서 별도로 수행한다.

## 1. 작업 전 조사

먼저 다음 항목을 조사하고 현재 구조를 요약하라.

* 프로젝트 루트와 `dotg-web` 디렉터리 구조
* `package.json`의 script 구성
* Next.js 버전과 App Router 사용 구조
* Supabase 환경 변수 참조 위치
* `src/lib/supabase/env.ts`
* `src/lib/supabase/client.ts`
* `src/lib/supabase/server.ts`
* `src/lib/supabase/proxy.ts`
* `src/proxy.ts`
* 공개 페이지 query 계층
* mock data 또는 config fallback이 사용되는 위치
* `next.config.ts`
* `.env`, `.env.local`, `.env.example` 관련 파일
* Vercel 또는 배포 관련 문서
* README의 환경 설정 안내

조사 결과를 바탕으로 현재 다음 상황이 실제 코드에서 어떻게 처리되는지 확인하라.

1. Supabase 환경 변수가 전혀 없는 경우
2. URL만 있고 anon key가 없는 경우
3. anon key만 있고 URL이 없는 경우
4. 잘못된 Supabase URL이 설정된 경우
5. 로컬 개발 환경에서 Supabase가 연결되지 않는 경우
6. Preview 환경에서 Supabase 설정이 누락된 경우
7. Production 환경에서 Supabase 설정이 누락된 경우
8. Supabase 조회 중 네트워크 또는 DB 오류가 발생한 경우
9. 환경 변수 미설정 상태에서 mock fallback이 실행되는 경로
10. 운영 환경에서 fallback 데이터가 노출될 가능성

조사 없이 파일을 추측해서 수정하지 말고, 실제 코드와 현재 구현 의도를 확인한 뒤 작업하라.

## 2. 환경 구분 정책

다음 세 환경을 명확하게 구분하라.

* local development
* Vercel Preview
* Vercel Production

환경 판별은 가능한 한 Next.js와 Vercel에서 제공하는 표준 환경 변수를 활용하라.

예시로 검토할 수 있는 값:

* `NODE_ENV`
* `VERCEL`
* `VERCEL_ENV`
* `NEXT_PUBLIC_VERCEL_ENV`

단, 클라이언트에 불필요한 서버 환경 변수를 노출하지 말고, 서버 전용 판별과 클라이언트용 판별을 구분하라.

환경 판별 로직이 여러 파일에 흩어지지 않도록 공통 모듈로 정리하라.

필요하다면 다음과 같은 구분을 제공하라.

* 현재 환경이 local인지
* Preview인지
* Production인지
* Vercel에서 실행 중인지
* mock fallback이 허용되는 환경인지
* Supabase 설정이 필수인 환경인지

파일명과 API 구조는 기존 프로젝트 스타일에 맞게 설계하라.

## 3. Supabase 환경 변수 검증 강화

현재 Supabase 환경 변수 처리 방식을 개선하라.

필수 환경 변수:

* `NEXT_PUBLIC_SUPABASE_URL`
* `NEXT_PUBLIC_SUPABASE_ANON_KEY`

다음 요구사항을 만족해야 한다.

### 로컬 개발 환경

* 환경 변수가 없어도 단순 import 과정에서 즉시 build가 깨지지 않아야 한다.
* 로컬에서 fallback을 허용하는 기존 개발 경험은 가능하면 유지한다.
* 단, URL 또는 key 중 하나만 설정된 불완전한 상태는 명확하게 감지해야 한다.
* fallback이 작동할 경우 개발자가 이를 알 수 있도록 경고를 출력하라.
* 경고에는 secret 값이나 전체 key를 포함하지 마라.
* 같은 요청에서 경고가 과도하게 반복되지 않도록 처리하라.

### Preview 환경

* Supabase 환경 변수가 반드시 필요하다.
* 환경 변수가 없거나 불완전하면 mock fallback을 사용하지 마라.
* 설정 오류를 조용히 숨기지 말고 명확한 에러로 처리하라.
* 빌드 시점에 검증할 수 있는 항목과 런타임에서만 검증할 수 있는 항목을 구분하라.

### Production 환경

* Supabase 환경 변수가 반드시 필요하다.
* 환경 변수 누락, 불완전한 설정, 유효하지 않은 URL 형식이 있으면 즉시 실패해야 한다.
* 어떠한 경우에도 mock data 또는 정적 config fallback으로 조용히 전환하지 마라.
* 운영 사이트가 설정 누락 상태에서 정상 콘텐츠처럼 mock 데이터를 표시하면 안 된다.

### 공통 검증

* URL은 유효한 URL 형식인지 확인하라.
* 가능하면 HTTPS를 요구하되, 로컬 Supabase 주소는 예외 처리하라.
* 빈 문자열과 공백 문자열을 미설정으로 취급하라.
* 오류 메시지는 어떤 변수가 문제인지 알려주되 key 값 자체를 노출하지 마라.
* service role key는 사용하거나 요구하지 마라.
* 서버와 브라우저 양쪽에서 동일한 정책이 유지되도록 하라.
* 클라이언트 번들에 서버 전용 환경 값이 포함되지 않도록 하라.

## 4. mock fallback 정책 정리

현재 공개 페이지 query에서 사용하는 mock/config fallback 구조를 조사하고 다음 정책으로 정리하라.

### fallback 허용

다음 조건에서만 허용한다.

* 로컬 개발 환경
* Supabase 환경 변수가 완전히 설정되지 않은 상태
* 프로젝트가 기존에 의도적으로 fallback을 지원하는 공개 데이터 조회 경로

### fallback 금지

다음 환경에서는 금지한다.

* Vercel Preview
* Vercel Production
* 기타 production build로 판단되는 환경

다음 사항도 반영하라.

* Supabase 환경 변수가 완전히 설정된 상태에서 실제 조회가 실패하면 fallback하지 마라.
* DB 오류, 네트워크 오류, 권한 오류를 mock 데이터로 숨기지 마라.
* 실제 조회 실패는 기존 error boundary에서 처리될 수 있도록 오류를 전달하라.
* fallback 허용 여부를 각 query 파일에서 개별적으로 판단하지 말고 공통 정책으로 관리하라.
* 프로젝트, 공지사항, 모집, 사이트 설정, 연락처, SNS 등 공개 query 전반에 동일한 정책을 적용하라.
* 관리자 영역에서는 mock fallback을 허용하지 마라.

가능하면 다음 상태를 구분하라.

```text
Supabase 미설정 + 로컬
→ fallback 허용

Supabase 미설정 + Preview
→ 설정 오류

Supabase 미설정 + Production
→ 설정 오류

Supabase 설정 완료 + 조회 성공
→ 실제 데이터 반환

Supabase 설정 완료 + 조회 실패
→ 오류 전달, fallback 금지
```

## 5. Supabase client 생성 로직 보완

브라우저 client, 서버 client, proxy client 생성 로직을 검토하고 환경 검증 정책과 일치하도록 수정하라.

확인할 사항:

* 환경 변수가 없을 때 client 생성 함수의 동작
* 서버 컴포넌트에서의 동작
* Client Component에서의 동작
* Server Action에서의 동작
* proxy 또는 middleware 성격의 코드에서의 동작
* Auth session 갱신 과정
* 환경 변수 누락 시 알기 어려운 저수준 오류가 발생하지 않는지
* 잘못된 URL로 인해 생성 단계 또는 요청 단계에서 모호한 오류가 발생하지 않는지

환경 변수가 없을 때 `undefined`나 잘못된 문자열을 Supabase SDK에 전달하지 마라.

필요하다면 다음과 같이 API를 구분하라.

* Supabase 설정 존재 여부를 확인하는 함수
* 설정이 반드시 필요할 때 값을 반환하거나 오류를 던지는 함수
* 로컬 fallback 경로에서 선택적으로 설정을 가져오는 함수

함수명과 파일 구조는 현재 프로젝트 스타일을 따르되, 호출부에서 의도가 명확하게 드러나도록 하라.

## 6. 빌드 시 환경 검증

Preview와 Production에서 필수 환경 변수 누락을 가능한 한 조기에 확인할 수 있도록 검증 절차를 추가하라.

검토 가능한 방식:

* 별도의 환경 검증 스크립트
* `prebuild` 또는 별도 package script
* Next.js config 로딩 시 서버 전용 검증
* 배포 전 실행 가능한 `pnpm` 명령

다음 조건을 만족해야 한다.

* 로컬 개발자가 환경 변수 없이 단순히 의존성을 설치하거나 lint를 실행하는 흐름은 가능하면 유지한다.
* Preview·Production 배포에서는 환경 변수 누락이 build 또는 배포 초기에 발견되어야 한다.
* 환경 검증 스크립트는 Vercel 환경을 인식해야 한다.
* key 값 전체를 로그에 출력하지 마라.
* 검증 로직을 중복 구현하지 마라.
* Windows에서도 실행 가능하도록 shell 전용 문법에 의존하지 마라.

필요하다면 다음과 같은 script를 추가할 수 있다.

```text
env:check
env:check:production
```

실제 script 이름은 기존 명명 규칙에 맞게 결정하라.

## 10. 테스트 추가

현재 테스트 구조를 조사한 뒤 환경 정책에 대한 자동화 테스트를 추가하라.

최소 테스트 항목:

* 모든 Supabase 변수가 없는 로컬 환경
* URL만 있는 로컬 환경
* anon key만 있는 로컬 환경
* 유효하지 않은 URL
* 공백 문자열
* 로컬에서 fallback 허용
* Preview에서 fallback 금지
* Production에서 fallback 금지
* Supabase 설정 완료 후 실제 조회 오류가 fallback으로 전환되지 않는지
* 오류 메시지에 key 값이 포함되지 않는지
* 환경 판별 함수 테스트
* 환경 검증 script 성공·실패 조건

테스트 과정에서 실제 원격 Supabase에 접근하지 않도록 하라.

`process.env`를 변경하는 테스트는 각 테스트 종료 후 원래 값을 복구해 다른 테스트를 오염시키지 않도록 하라.

## 11. 구현 제약

다음 제약을 반드시 지켜라.

* service role key를 추가하지 마라.
* secret이나 실제 Supabase 값을 코드에 하드코딩하지 마라.
* 공개 페이지의 기존 로컬 fallback 기능을 이유 없이 제거하지 마라.
* Preview와 Production에서는 fallback을 허용하지 마라.
* 실제 Supabase query 실패를 fallback 데이터로 숨기지 마라.
* 관리자 영역에 mock fallback을 추가하지 마라.
* 기존 RLS 정책과 DB schema를 불필요하게 변경하지 마라.
* 이번 작업에서 원격 migration을 실행하지 마라.
* 이번 작업에서 Vercel에 실제 배포하지 마라.
* 이번 작업에서 Playwright나 GitHub Actions를 구축하지 마라.
* 기존 UI 디자인을 변경하지 마라.
* 환경 검증을 위해 Client Component를 불필요하게 늘리지 마라.
* 서버 전용 코드가 클라이언트 번들에 포함되지 않도록 주의하라.
* 테스트를 통과시키기 위해 타입 검사를 우회하지 마라.
* `any`, `@ts-ignore`, `eslint-disable` 사용을 최소화하고, 새로 추가할 경우 이유를 설명하라.

## 12. 검증

작업 완료 후 프로젝트에서 사용 가능한 명령을 확인한 뒤 최소한 다음 검증을 수행하라.

```text
pnpm.cmd lint
pnpm.cmd exec tsc --noEmit
pnpm.cmd build
```

환경 정책 테스트를 위한 별도 명령을 추가했다면 함께 실행하라.

가능한 경우 다음 조건도 각각 검증하라.

```text
로컬 + Supabase 미설정
로컬 + Supabase 완전 설정
Preview 환경 모의 + Supabase 미설정
Production 환경 모의 + Supabase 미설정
Production 환경 모의 + Supabase 완전 설정
```

Preview·Production 모의 검증은 실제 배포 없이 환경 변수를 임시로 주입해 수행하라.

Windows PowerShell 환경에서도 실행 가능한 검증 방법을 사용하라.

빌드 과정에서 실제 Supabase 네트워크 요청이 발생해 실패한다면, 원인을 분석하고 환경 검증과 빌드 시 데이터 조회의 책임을 분리하라. 단순히 오류를 무시하지 마라.

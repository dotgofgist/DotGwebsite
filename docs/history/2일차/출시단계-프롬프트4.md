# 출시단계 프롬프트 4 — GitHub / Vercel Preview 환경 구축

DotG 웹사이트는 현재 다음 출시단계를 진행 중이다.

```text
기본구조
→ 구현단계
→ 운영전환
→ 출시단계 프롬프트 1
→ 출시단계 프롬프트 2
→ 출시단계 프롬프트 3
→ 출시단계 프롬프트 4
```

프롬프트 2에서 실제 Production Supabase 구축은 완료되었다.

확인된 상태:

```text
Production Supabase: ACTIVE_HEALTHY
Remote migrations: 6/6 synced
Production seed: PASS
Remote schema: PASS
Remote RLS: PASS
Remote Storage: PASS
Remote smoke: PASS
```

프롬프트 3에서는 Production Auth/Admin/Storage 구조와 권한 정책까지 자동 검증되었으며, 실제 관리자 credential을 사용하는 브라우저 CRUD/Storage 검증은 사용자 수동 작업 대상으로 분리되었다.

프롬프트 3 수동 검증이 아직 최종 완료되지 않았더라도 이번 프롬프트에서는 **Preview 인프라 구축 자체는 진행할 수 있다.**

단:

> 프롬프트 3에서 BLOCKER/HIGH 문제가 발견되었거나 Production 데이터 정합성 문제가 발생한 경우 Preview 검증보다 해당 문제 해결을 우선한다.

이번 작업의 목적은:

> **GitHub와 Vercel을 실제로 연결하고, Pull Request 기반 Vercel Preview 배포 환경을 구축하여 DotG 웹사이트를 로컬이 아닌 외부 HTTPS URL에서 검증할 수 있는 상태로 만드는 것**

이다.

이번 프롬프트에서는 **Production Vercel 배포나 공식 도메인 연결은 수행하지 않는다.**

---

# 0. 작업 원칙

이번 작업에서는 실제 GitHub/Vercel 외부 환경을 다루므로 다음 규칙을 반드시 지켜라.

## 절대 금지

* Vercel Production 배포를 수행하지 않는다.
* Production domain을 임의로 연결하지 않는다.
* main branch에 직접 push하지 않는다.
* 사용자 승인 없이 branch protection을 약화시키지 않는다.
* GitHub secret 값을 출력하지 않는다.
* Vercel token을 source code에 저장하지 않는다.
* Supabase DB password를 source/문서에 저장하지 않는다.
* Supabase service role key를 Preview에 넣지 않는다.
* `.env` secret을 Git에 commit하지 않는다.
* Preview를 위해 Production RLS/Auth 정책을 약화시키지 않는다.
* CI test를 skip하도록 변경하지 않는다.
* fork PR에서 secret이 노출되도록 workflow를 변경하지 않는다.
* 현재 정상 동작 중인 workflow를 이유 없이 재작성하지 않는다.
* 기존 사용자 변경사항을 reset/stash/checkout하지 않는다.
* Git commit/push를 임의로 수행하지 않는다.

# 1. 작업을 세 종류로 구분

이번 단계에서는 다음 구분을 반드시 사용한다.

```text
[A] Codex가 직접 조사/수행
[B] 사용자가 GitHub/Vercel Dashboard에서 수행
[C] 사용자 설정 후 Codex가 검증
```

Dashboard 설정이 필요한 시점에는 다음 형식으로 안내한다.

```text
[사용자 작업 필요]

서비스:
GitHub / Vercel / Supabase

해야 할 일:
1. ...
2. ...

설정해야 할 변수 이름:
- ...

Codex에게 전달해도 되는 정보:
- secret이 아닌 식별 정보

Codex에게 전달하지 말아야 할 정보:
- token
- password
- secret value
```

secret 값을 채팅으로 요구하지 않는다.

# 5. Preview workflow 보안 점검

다음을 반드시 확인한다.

## Fork PR

fork repository에서 온 PR에서는 secret 기반 Vercel deploy가 실행되지 않아야 한다.

예상 구조:

```text

→ Preview deploy

→ CI만 실행
→ secret deploy skip
```

workflow expression과 event context를 실제로 검토한다.

## Pull Request 권한

필요 이상의 GitHub token permission이 설정되어 있지 않은지 확인한다.

가능하면 최소 권한을 사용한다.

## Secret 출력

다음 값이 workflow log에 출력되지 않는지 확인한다.

```text
VERCEL_TOKEN
SUPABASE_ACCESS_TOKEN
database password
private credential
```

# 6. Preview와 Production Supabase 전략 확인

현재 DotG에는 실제 Production Supabase project가 구축되어 있다.

Preview 환경에서 어떤 Supabase를 사용할지 기존 문서/workflow/code를 조사하여 판단한다.

가능한 전략:

```text
A. Preview 전용 Supabase project
B. Production Supabase를 Preview에서 read/write
C. Production Supabase를 Preview에서 제한적으로 사용
```

임의로 결정하지 말고 현재 프로젝트 설계와 기존 문서를 먼저 확인한다.

현재 별도의 Preview Supabase가 준비되어 있지 않고 Production Supabase를 사용하도록 기존 배포 구조가 설계되어 있다면, Preview 관리자 CRUD가 실제 Production DB에 영향을 줄 수 있음을 명확히 기록한다.

그 경우 Preview QA에서 테스트 데이터 naming/cleanup 규칙을 강제한다.

새 Preview Supabase project가 반드시 필요하다고 판단되더라도 사용자 승인 없이 생성하지 않는다.

# 13. `NEXT_PUBLIC_SITE_URL` Preview 정책 확인

SEO/canonical 코드가 Preview에서 어떤 URL을 사용하는지 조사한다.

확인할 것:

* `NEXT_PUBLIC_SITE_URL`
* `VERCEL_URL`
* `VERCEL_PROJECT_PRODUCTION_URL`
* fallback logic
* metadataBase

Preview deployment가 Production 공식 canonical URL을 잘못 생성하지 않는지 확인한다.

현재 설계가 Preview에서도 Production canonical을 사용하도록 의도되었다면 그대로 유지한다.

Preview URL 자체를 canonical로 쓰도록 설계되어 있다면 해당 로직을 확인한다.

임의로 SEO 정책을 바꾸지 않는다.

문제가 있으면 보고하고 필요한 최소 수정만 수행한다.

# 15. Supabase Auth Preview Redirect 준비

Preview deployment URL에서 관리자 로그인을 검증하려면 Supabase Auth redirect 설정이 필요할 수 있다.

현재 앱 login 구현을 확인하여 실제 redirect URL 요구사항을 파악한다.

Vercel Preview URL은 deployment마다 달라질 수 있으므로 Supabase가 지원하는 redirect wildcard 사용 여부와 현재 보안 정책을 확인한다.

사용자에게 Dashboard에서 변경이 필요하다면 정확한 형태를 안내한다.

무분별한 wildcard를 추가하지 않는다.

가능하면 DotG Vercel Preview hostname 범위로 제한한다.

예시를 실제 project hostname 확인 없이 그대로 적용하지 않는다.

# 18. Vercel token 권한 확인

Preview workflow에서 `VERCEL_TOKEN`을 사용한다면 token scope가 필요한 범위인지 확인한다.

사용자가 새 token을 만들어야 한다면:

* 적절한 Vercel account/team
* 필요한 project 접근
* 최소 권한 원칙
* 안전한 GitHub Secret 저장

을 안내한다.

기존 token이 정상 동작한다면 새 token을 만들지 않는다.

Token 값은 채팅에 공유하지 않는다.

# 19. GitHub ↔ Vercel 자동 배포 중복 확인

Vercel Git Integration 자체가 PR마다 자동 Preview를 생성하고 동시에 GitHub Actions의 `preview.yml`도 Vercel deploy를 수행한다면 **중복 Preview deployment가 발생할 수 있다.**

반드시 이를 조사한다.

다음 중 하나의 구조인지 확인한다.

```text
A.
Vercel Git Integration deploy
+ GitHub Actions는 test/smoke만

B.
Vercel Git Integration 자동 deploy 비활성/제어
+ GitHub Actions가 deploy

C.
둘 다 deploy
→ 중복 가능성
```

현재 기존 설계의 의도를 문서/workflow에서 확인한다.

중복 deployment가 실제로 발생하는 구조라면 무시하지 말고 보고한다.

사용자 승인 없이 한쪽 integration을 임의로 제거하지 않는다.

필요한 최소 설정 변경안을 제시한다.

# 21. Preview 배포를 발생시킬 방법 결정

현재 `preview.yml` trigger가 PR 이벤트라면 실제 Preview 검증을 위해 **PR이 필요할 수 있다.**

Codex는 임의로 commit/push/PR을 만들지 않는다.

현재 Git 상태와 사용자의 branch workflow를 확인한다.

Preview 배포를 위해 commit/push/PR이 필요한 경우:

```text
[사용자 작업 필요 — Git]

Preview workflow를 실제 실행하려면 현재 변경사항이 GitHub의 same-repository PR에 있어야 합니다.

필요 작업:
1. 변경사항 검토
2. commit
3. remote branch push
4. main 대상 PR 생성

Codex는 사용자 승인 없이 commit/push하지 않습니다.
```

라고 안내한다.

현재 이미 적절한 PR이 있다면 그것을 재사용한다.

# 22. Preview용 commit 범위 점검

PR 생성이 필요하다면 현재 Git diff를 확인하고 **출시 단계와 무관한 파일이 섞이지 않았는지** 점검한다.

특히:

```text
src/lib/supabase/database.types.ts
docs/history/...
```

등의 의도적 변경과 기타 변경을 구분한다.

Codex는 commit을 직접 수행하지 않지만 사용자에게 어떤 변경을 포함해야 하는지 안내할 수 있다.

secret/local credential/report 파일은 절대 commit 대상에 포함하지 않는다.

# 23. Preview workflow 실제 실행 확인

same-repo PR이 생성되고 필요한 secret/environment가 설정된 후 GitHub Actions 결과를 확인한다.

* code failure
* GitHub setting
* missing secret
* Vercel setting
* Supabase configuration
* deployment
* smoke

중 하나로 분류한다.

workflow를 우회하지 않는다.

# 24. Preview Deployment URL 확인

Preview deployment가 성공하면 생성된 HTTPS URL을 확인한다.

최종 보고서에는 secret이 아닌 Preview URL을 기록할 수 있다.

확인:

* HTTPS 정상
* root page 응답
* Next.js asset loading
* no deployment protection issue
* no infinite redirect

Vercel Deployment Protection 때문에 CI smoke가 접근하지 못한다면 실제 정책을 확인한다.

보안을 무조건 해제하지 않는다.

필요하다면 안전한 bypass 또는 Preview 정책을 사용자에게 안내한다.

# 25. Preview 환경 판별 확인

Preview URL에서 앱이 실제로:

```text
environment = preview
```

로 인식되는지 확인한다.

특히 운영전환에서 구축한 정책:

```text
local
→ Supabase 미설정 시 일부 fallback 허용

preview
→ Supabase 설정 필수
→ query failure를 mock으로 숨기지 않음

production
→ Supabase 설정 필수
→ fallback 금지
```

이 Preview에서 실제로 적용되는지 검증한다.

# 26. Preview Supabase 연결 검증

Preview 페이지에서 실제 Supabase query가 정상 수행되는지 확인한다.

현재 Production DB에 콘텐츠가 거의 없어도 0건 자체는 오류가 아니다.

확인:

```text
Preview Next.js
       ↓
Supabase remote
       ↓
public query
       ↓
Preview UI
```

다음 오류가 없어야 한다.

* missing Supabase env
* invalid URL/key
* schema mismatch
* RLS error
* mock fallback
* server runtime error

# 28. Preview Auth 로그인 준비

프롬프트 4에서는 **Preview 인프라 검증만 수행하고 광범위한 관리자 CRUD는 프롬프트 5에서 수행한다.**

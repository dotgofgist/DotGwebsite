# 출시단계 프롬프트 1 — 출시 전 코드·문구 품질 정리

현재 DotG 웹사이트는 기본구조 → 구현단계 → 운영전환을 완료했고, 출시단계 진입 전 현황 점검 결과 다음 판정을 받았다.

```text
READY FOR RELEASE STAGE
```

현재 build, TypeScript, lint, Supabase DB/RLS/Storage, E2E, SEO, 접근성, release gate에는 BLOCKER가 없다.

다만 출시 전 해결해야 할 HIGH 이슈로 다음 문제가 확인되었다.

> 일부 사용자 노출 한국어 문자열이 mojibake 형태로 깨진 상태로 저장되어 있다.

또한 Git workspace에는 문서 rename/untracked 상태가 남아 있다.

이번 작업의 목적은 **외부 Production 환경을 구축하기 전에 현재 코드베이스의 사용자 노출 문자열과 워크스페이스 상태를 정리하여 안전한 출시 기준점을 만드는 것**이다.

이번 프롬프트에서는 Supabase Production 프로젝트 생성, remote migration, Vercel 배포, GitHub Environment 설정 등 외부 인프라 작업은 하지 않는다.

---

# 0. 작업 원칙

다음 규칙을 반드시 지켜라.

* 실제 현재 워크스페이스를 먼저 조사한 후 수정한다.
* 깨진 문자열을 추측만으로 일괄 치환하지 않는다.
* 파일 전체를 임의의 인코딩으로 재인코딩하지 않는다.
* 정상적인 한국어 문자열까지 변경하지 않는다.
* UI 디자인이나 기능 구조를 불필요하게 변경하지 않는다.
* DB schema를 변경하지 않는다.
* 새로운 migration을 만들지 않는다.
* Supabase remote DB에 연결하거나 변경하지 않는다.
* Vercel/GitHub 배포 작업을 수행하지 않는다.
* dependency를 추가하거나 업데이트하지 않는다.
* 테스트를 통과시키기 위해 테스트를 약화시키지 않는다.
* 기존 RLS/Auth/Storage 정책을 변경하지 않는다.
* 기존 사용자 변경사항을 임의로 reset, checkout, stash, 삭제하지 않는다.
* Git commit/push를 수행하지 않는다.
* secret 값을 출력하지 않는다.

이번 작업은 **문구 복구 + 필요한 최소 코드 정합성 수정 + 검증**에 한정한다.

# 1. 작업 시작 전 Git 상태 기록

먼저 다음을 실행한다.

```powershell

git branch --show-current
git log -5 --oneline
```

현재 현황 점검 당시 다음 상태가 보고되었다.

docs/history/2일차/운영전환 현황점검 프롬프트.md

실제 현재 상태와 비교한다.

기존 사용자 변경사항은 절대 되돌리지 않는다.

# 2. Mojibake 전수 조사

워크스페이스에서 깨진 한국어 문자열을 전수 조사한다.

최소한 다음 영역을 조사한다.

```text
src/
supabase/
tests/
e2e/
scripts/
docs/
README*
```

단, 다음과 같은 생성물이나 외부 dependency는 조사 대상에서 제외한다.

```text
node_modules/
.next/
playwright-report/
test-results/
coverage/
.pnpm-store/
.git/
```

다음 유형을 모두 찾는다.

## 2-1. 명백한 replacement character

예:

```text
�
��
```

Unicode replacement character `U+FFFD`가 포함된 파일을 찾는다.

## 2-2. 잘못 디코딩된 UTF-8 문자열

한국어 UTF-8 bytes가 잘못된 문자셋으로 읽혀 다음과 같은 형태가 된 경우를 조사한다.

예:

```text
ì...
ë...
ê...
```

단순히 해당 문자 자체가 존재한다고 무조건 오류로 판단하지 말고 파일 내용과 문맥을 확인한다.

## 2-3. 사용자 노출 영역

특히 다음을 우선 조사한다.

* Header
* Footer
* Hero
* navigation
* 공개 페이지 제목/설명
* 버튼
* form label
* validation message
* error message
* empty state
* loading state
* 관리자 화면 문구
* 로그인 화면
* 프로젝트 관리
* 공지 관리
* 모집 관리
* 사이트 설정
* 연락처
* SNS
* 이미지 관리

## 2-4. 테스트 문자열

다음을 확인한다.

* Playwright locator
* `getByText`
* `getByRole(... name:)`
* assertion 문자열
* test fixture
* test helper

UI 문자열을 복구하면 E2E selector도 동일하게 정합성을 맞춰야 한다.

## 2-5. SQL

다음을 확인한다.

* migration에 저장된 사용자 노출 기본 문자열
* `supabase/seed.sql`
* `supabase/seeds/production.sql`
* SQL test fixture

특히 이미 실행된 migration의 과거 의미를 변경할 수 있으므로 migration 수정은 매우 신중하게 판단한다.

현재 migration history를 변경해야 할 필요가 없다면 기존 migration을 함부로 수정하지 않는다.

# 3. Mojibake 인벤토리 작성

수정하기 전에 발견 항목을 내부적으로 다음과 같이 정리한다.

| 파일   | 위치   | 깨진 문자열 | 용도                | 복구 근거                 |
| ---- | ---- | ------ | ----------------- | --------------------- |
| path | line | ...    | UI / test / SQL 등 | git history / 주변 문맥 등 |

복구 근거는 가능한 한 다음 순서로 사용한다.

1. Git history에 존재하는 정상 문자열
2. 동일 기능의 다른 정상 문자열
3. E2E/test fixture
4. 문서 또는 mock data
5. 주변 코드의 명확한 의미

Git history에서 정상 문자열을 확인할 필요가 있다면 read-only 명령을 사용한다.

예:

```powershell
git log -- <file>
git show <commit>:<file>
git diff
```

기존 정상 문자열을 찾을 수 있다면 이를 우선한다.

확실하게 원문을 판단할 수 없는 문자열은 임의로 창작하지 않는다.

그 경우 최종 보고서의 `사용자 확인 필요` 항목에 기록한다.

---

# 4. 실제 한국어 문자열 복구

확실하게 복구 가능한 mojibake를 수정한다.

수정 원칙:

* 의미를 바꾸지 않는다.
* 기존 UX copy를 새로 작성하지 않는다.
* 문체를 임의로 개선하지 않는다.
* 맞춤법 개선 작업으로 범위를 확장하지 않는다.
* 정상 한국어까지 일괄 치환하지 않는다.
* 기능 로직을 변경하지 않는다.

예를 들어 원래 문자열이 Git history에서 확인되는 경우 정확히 기존 문자열을 복원한다.

---

# 5. Source ↔ Test 문자열 정합성 복구

UI 문자열 수정으로 테스트 selector가 영향을 받는 경우 테스트도 함께 수정한다.

단 다음 규칙을 지킨다.

* 테스트를 단순히 통과시키기 위해 assertion을 삭제하지 않는다.
* selector의 구체성을 의도적으로 약화시키지 않는다.
* 실제 UI와 테스트가 같은 정상 문자열을 사용하도록 한다.
* 접근성 role/name 기반 selector를 가능하면 유지한다.

예:

```text
UI 깨진 문자열
        ↓ 복구
정상 한국어 UI
        ↓
Playwright accessible name도 동일한 정상 문자열
```

# 6. SQL / Seed 문자열 정합성 확인

SQL에 mojibake가 발견되면 해당 SQL의 성격을 먼저 구분한다.

## Migration

이미 migration history에 포함된 SQL이라면 단순 문자열 문제 때문에 과거 migration을 무조건 수정하지 않는다.

다음을 판단한다.

* 실제 DB row에 사용자 노출 문자열을 삽입하는 migration인가?
* 단순 comment/test description인가?
* migration checksum/history에 영향을 줄 수 있는가?
* 현재 schema와 운영 배포 과정에 영향을 줄 수 있는가?

기존 migration 파일 변경이 안전하지 않다면 변경하지 말고 보고한다.

## Development seed

개발용 mock/seed 문자열이 깨져 있다면 정상 문자열로 복구할 수 있다.

## Production seed

현재 production seed는 최소 baseline만 포함하는 것으로 보고되어 있다.

production seed에 사용자 노출 문자열이 깨져 있다면 실제 의미를 확인한 뒤 수정한다.

production seed의 다음 원칙은 유지한다.

* fake projects 없음
* fake notices 없음
* fake recruitment 없음
* fake Auth user 없음
* fake admin 없음
* 최소 production baseline
* 재실행 안전성 유지

# 7. UTF-8 저장 상태 확인

수정한 text source가 정상적인 UTF-8로 저장되어 있는지 확인한다.

최소 대상:

```text
.ts
.tsx
.js
.mjs
.mts
.sql
.md
.json
.yml
.yaml
```

주의:

파일 전체를 일괄적으로 재인코딩하지 않는다.

기존 파일에 BOM이 없었다면 특별한 이유 없이 BOM을 추가하지 않는다.

line ending도 불필요하게 전체 파일에 변경하지 않는다.

즉 다음과 같은 대규모 noise diff를 만들지 않는다.

```text
파일 전체가 수정된 것으로 표시됨
실제 변경은 문자열 1개뿐
```

수정 후 `git diff --stat`과 `git diff`를 확인하여 불필요한 전체 파일 변환이 없는지 확인한다.

# 8. 사용자 노출 한국어 추가 검사

1차 수정 후 다시 전체 검색한다.

최소 다음을 확인한다.

* `U+FFFD` 잔존 여부
* 의심되는 mojibake 패턴
* 비정상적인 연속 특수문자
* 깨진 한국어를 참조하던 E2E selector

결과를 다음으로 구분한다.

```text
확실한 mojibake: 0건
의심 항목: N건
사용자 확인 필요: N건
```

확실하게 잘못된 문자열은 가능한 범위에서 모두 제거한다.

# 10. Git 문서 변경 상태 조사

현재 다음 문서 변경 상태가 보고되어 있다.

```text
deleted:
docs/history/1일차/기본구조-작업-결과-요약.md

untracked:
docs/history/1일차/기본구조 작업 결과 요약.md
docs/history/2일차/운영전환 작업 결과 요약.md
docs/history/2일차/운영전환 현황점검 프롬프트.md
```

이 변경들이 단순 rename인지 내용 변경인지 조사한다.

다음을 확인한다.

* 기존 deleted 파일과 새 untracked 파일의 내용 동일 여부
* 파일명만 변경된 것인지
* 새 문서가 기존 문서의 업데이트 버전인지
* 실제 작업 이력을 보존하기 위해 필요한 문서인지

단:

**사용자가 만든 문서를 임의로 삭제하지 않는다.**

rename이 명백한 경우에도 Git commit은 하지 않는다.

내용이나 의도가 애매하면 그대로 유지하고 최종 보고서에서 정리 방법을 제안한다.

# 11. `.gitignore` 상태 확인

현황 점검에서 root `.gitignore`와 `dotg-web/.gitignore`의 역할 분리가 언급되었다.

현재 workspace 구조를 확인하고 다음과 같은 실제 위험이 있는지만 조사한다.

* `.env*` accidentally tracked 가능성
* Playwright auth state
* Playwright report
* test result
* local Supabase 임시 파일
* `.next`
* node_modules
* local credential
* Vercel local metadata
* 기타 generated artifact

이미 적절하게 ignore되고 있다면 수정하지 않는다.

실제로 누락된 generated/credential path가 있고 출시 작업 중 추적될 가능성이 명백한 경우에만 최소한으로 수정한다.

사용자 작성 문서나 release 결과 문서를 ignore하지 않는다.

# 12. Secret 재점검

tracked source를 대상으로 secret 하드코딩 여부를 다시 확인한다.

최소 확인 대상:

* Supabase service role key
* Supabase access token
* DB password
* GitHub token
* Vercel token
* private key
* production credential

실제 값은 출력하지 않는다.

결과는 다음처럼만 보고한다.

```text
하드코딩 secret 발견 없음
```

또는

```text
주의가 필요한 파일: <path>
```

secret이 발견되더라도 최종 답변에 실제 값을 그대로 출력하지 않는다.

# 15. E2E 검증

이번 작업은 UI 문자열과 selector를 변경할 가능성이 있으므로 Playwright E2E 검증이 중요하다.

현재 프로젝트의 실제 script를 확인하고 전체 E2E를 실행한다.

예상 계열:

```powershell
pnpm run ci:e2e
```

실제 package.json script 이름을 우선한다.

다음을 확인한다.

* public smoke
* auth
* authorization
* admin CRUD
* desktop
* mobile
* SEO
* accessibility

테스트를 통과시키기 위해 테스트 coverage를 제거하거나 skip 처리하지 않는다.

# 16. Release Gate 재검증

현재 존재하는 다음 release 검증을 실행한다.

```powershell

```

실제 script가 존재하는지 먼저 확인한다.

release gate에서 실패가 발생하면 원인을 조사한다.

이번 작업으로 인해 발생한 regression은 해결한다.

# 17. Diff 최종 검토

검증 완료 후 반드시 다음을 확인한다.

```powershell
git status --short
git diff --stat
git diff
```

검토 기준:

* mojibake 복구와 직접 관련 없는 코드 변경 없음
* 대규모 encoding noise 없음
* line ending 전체 변경 없음
* dependency 변경 없음
* migration 불필요한 변경 없음
* secret 추가 없음
* 테스트 약화 없음

# 18. 완료 기준

다음을 모두 만족해야 프롬프트 1 완료로 판정한다.

# 출시단계 프롬프트 2 — Supabase Production 환경 구축

DotG 웹사이트는 현재 다음 개발 단계를 완료한 상태다.

```text
기본구조
→ 구현단계
→ 운영전환
→ 출시단계 프롬프트 1
```

출시단계 프롬프트 1 결과:

```text
Application code: 정상
TypeScript: PASS
Lint: PASS
Build: PASS
E2E: 75 PASS
SEO / Accessibility: PASS
Release Check: PASS
Secret Scan: PASS
Git Workspace: clean
BLOCKER: 없음
HIGH: 없음
```

작업 이력용 Markdown 문서 1개에 인코딩 손상이 남아 있지만 Production 배포와 관계없는 MEDIUM 문서 이슈이므로 이번 작업 범위에서는 건드리지 않는다.

이번 작업의 목적은:

> **실제 DotG Production Supabase 프로젝트를 구축하고 현재 로컬 migration/schema/RLS/Storage 구조를 안전하게 원격 환경에 적용한 뒤, 원격 DB가 출시 가능한 상태인지 검증하는 것**

이다.

이번 프롬프트에서는 **Vercel Production 배포, GitHub Environment 구성, 공식 도메인 연결은 수행하지 않는다.**

---

# 0. 가장 중요한 작업 원칙

이번 단계부터 실제 Production Supabase를 다루므로 다음 규칙을 반드시 지켜라.

## 절대 금지

* 사용자 확인 없이 remote DB를 reset하지 않는다.
* `supabase db reset`을 remote 대상으로 실행하지 않는다.
* Production 데이터를 truncate/drop하지 않는다.
* destructive SQL을 임의로 실행하지 않는다.
* 개발용 `supabase/seed.sql`을 Production에 적용하지 않는다.
* fake project/notice/recruitment/user/admin 데이터를 Production에 넣지 않는다.
* migration history를 임의로 삭제하거나 조작하지 않는다.
* 기존 migration을 이유 없이 수정하지 않는다.
* service role key를 source code에 저장하지 않는다.
* access token, DB password 등의 secret을 출력하거나 문서에 기록하지 않는다.
* `.env` secret을 Git에 추가하지 않는다.
* 사용자의 기존 Supabase project를 잘못 선택한 상태에서 migration을 실행하지 않는다.
* Git commit/push를 수행하지 않는다.
* Vercel Production deploy를 수행하지 않는다.

# 1. Codex 작업과 사용자 작업을 명확하게 구분

이번 작업에는 Codex가 직접 수행할 수 없는 Supabase Dashboard 작업이 포함될 수 있다.

따라서 작업을 다음 세 종류로 구분해서 진행한다.

```text
[A] Codex가 직접 수행
[B] 사용자가 Supabase Dashboard/CLI 인증에서 수행
[C] 사용자 작업 후 Codex가 검증
```

사용자의 조작이 필요한 시점에는 작업을 추측해서 진행하지 말고 다음 형식으로 명확히 안내한다.

```text
[사용자 작업 필요]

해야 할 일:
1. ...
2. ...

완료 후 Codex에 알려줄 정보:
- secret이 아닌 식별 정보만

절대 공유하지 말아야 할 정보:
- DB password
- access token
- service role key
```

secret 자체가 필요할 경우 사용자가 채팅에 붙여넣도록 요구하지 말고, 로컬 CLI 로그인 또는 환경 변수/secret store를 사용하도록 안내한다.

# 4. Production seed 안전성 재검증

실제 remote 연결 전에 반드시 다음 두 seed를 구분한다.

```text
supabase/seed.sql
supabase/seeds/production.sql
```

확인할 것:

## Development seed

`supabase/seed.sql`에 다음과 같은 개발 데이터가 포함되어 있는지 확인한다.

* mock project
* mock notice
* mock recruitment
* fake content
* development fixture

해당 파일은 Production에서 절대 실행하지 않는다.

## Production seed

`supabase/seeds/production.sql`을 확인한다.

현재 보고된 구조는 다음과 같다.

```text
site_settings singleton baseline만 생성
on conflict do nothing
fake project 없음
fake notice 없음
fake recruitment 없음
fake auth user 없음
fake admin 없음
```

실제 파일이 이 상태인지 재검증한다.

Production seed가 idempotent한지도 확인한다.

문제가 발견되면 remote write 이전에 중단하고 보고한다.

---

# 5. Migration 안전성 사전 검사

`supabase/migrations` 전체를 순서대로 조사한다.

확인할 것:

* migration 개수
* timestamp/order
* 중복 migration
* schema dependency
* RLS
* Storage bucket/policy
* RPC/function
* trigger
* index/constraint

특히 Production에 위험할 수 있는 SQL을 검색한다.

예:

```text
DROP TABLE
DROP SCHEMA
TRUNCATE
DELETE FROM ... without condition
ALTER ... destructive
CASCADE
```

위 표현이 존재한다고 무조건 문제로 판단하지 말고 실제 migration 문맥을 분석한다.

현재 현황 점검에서는 destructive drop/truncate가 없다고 보고됐으므로 실제 상태와 일치하는지 확인한다.

# 6. 로컬 기준 최종 preflight

Production을 건드리기 전에 로컬 검증을 수행한다.

기존 프로젝트 script를 우선 사용한다.

최소한 다음 계열을 확인한다.

```text
environment validation
Supabase migration validation
database tests
RLS tests
Storage tests
production build
```

가능하면 현재 repository에 존재하는 preflight/release script를 사용한다.

이미 프롬프트 1에서 전체 release gate를 통과했으므로 불필요한 중복 테스트를 과도하게 실행할 필요는 없지만, **remote migration 직전에 필요한 DB/Supabase 안전성 검증은 반드시 실행한다.**

실패가 있다면 Production 작업으로 넘어가지 않는다.

---

# 7. Supabase Production Project 존재 여부 확인

현재 repository만으로는 실제 Production Supabase project 존재 여부를 알 수 없었다.

먼저 현재 Supabase CLI 연결 상태를 안전한 read-only 방식으로 확인한다.

다음과 같은 항목을 확인한다.

* 현재 project link 존재 여부
* linked project ref
* 현재 CLI 인증 상태
* 해당 project가 local이 아닌 remote인지

secret은 출력하지 않는다.

## Production project가 아직 없다면

Codex가 임의의 Production project를 생성했다고 가정하지 않는다.

사용자에게 Supabase Dashboard에서 Production project를 생성하도록 안내한다.

사용자에게 필요한 설정 항목은 최소한 다음과 같다.

```text
Organization
Project name
Region
Database password
```

Project name은 현재 프로젝트 문맥에 맞는 이름을 제안할 수 있지만 최종 선택은 사용자에게 맡긴다.

Region은 실제 서비스 이용자와 운영 환경을 고려하여 사용자가 선택하도록 한다.

DB password는 사용자 본인이 안전하게 보관해야 하며 Codex에게 전달하지 않도록 안내한다.

---

# 8. 사용자가 Production Project를 만든 뒤 필요한 정보

Codex가 실제 project를 연결하기 위해 필요한 정보와 필요하지 않은 정보를 명확하게 구분한다.

## 사용자에게 받아도 되는 정보

예:

```text
Supabase Project Ref
```

이는 secret이 아닌 project 식별 정보다.

필요하다면 project URL처럼 공개 클라이언트 설정에 사용되는 값도 별도로 구분한다.

## 사용자에게 채팅으로 요구하지 말아야 할 정보

```text
Database Password
Supabase Access Token
Service Role Key
JWT Secret
Private credentials
```

이들은 로컬 CLI login/environment 또는 안전한 secret 설정을 사용한다.

---

# 9. Supabase CLI 인증

현재 CLI가 인증되어 있지 않다면 안전한 인증 절차를 안내한다.

기존 프로젝트 문서에서 권장하는 방식이 있다면 해당 절차를 우선한다.

가능하면 사용자가 secret을 채팅에 전달하지 않아도 되는 인증 방식을 사용한다.

인증 후 project 목록 또는 필요한 read-only 명령을 통해 Production project에 접근 가능한지 확인한다.

출력에서 token/password 등 민감정보는 숨긴다.

---

# 10. Production Project Link

Production project ref를 확인한 뒤 현재 `dotg-web` workspace와 정확한 project를 연결한다.

기존 script가 있으면 script를 사용하고, 그렇지 않다면 Supabase CLI의 project link 기능을 사용한다.

연결 직후에는 migration을 push하지 않는다.

먼저 다음을 다시 확인한다.

```text
현재 local repository
        ↓
linked project ref
        ↓
의도한 DotG Production Supabase project
```

잘못된 project에 연결되어 있지 않은지 확인한다.

최종 보고서에는 전체 secret이나 password를 기록하지 않는다.

Project ref는 필요한 경우 일부 마스킹하거나 식별 목적의 정보만 사용한다.

---

# 11. Remote Preflight 실행

현재 구현되어 있는 remote preflight를 실행한다.

최소 다음을 검증한다.

* CLI authentication
* project link
* local migration 존재
* remote 접근 가능
* 필요한 environment 상태
* production seed 존재
* remote deployment script 준비

preflight가 실패하면 `db push`로 넘어가지 않는다.

원인을 해결한 뒤 다시 검증한다.

---

# 12. Local ↔ Remote Migration 상태 비교

remote DB에 변경을 적용하기 전에 migration 상태를 비교한다.

기존 script 또는 Supabase CLI를 이용해 다음을 확인한다.

```text
Local migrations
Remote migrations
```

그리고 다음 중 어떤 상태인지 판단한다.

### Case A — 새 Production project

```text
Remote migration 없음
Local migration 전체 적용 필요
```

정상적인 경우 다음 단계로 넘어갈 수 있다.

### Case B — 일부 migration 이미 존재

local/remote history를 정확하게 비교한다.

일치하는 migration과 미적용 migration을 구분한다.

### Case C — migration history 불일치

예:

```text
remote에 local에 없는 migration 존재
같은 migration id인데 내용이 다름
예상하지 않은 schema가 존재
```

이 경우 자동으로 repair하지 않는다.

`migration repair`, history 변경, destructive reset 등을 임의로 수행하지 말고 작업을 중단하여 보고한다.

---

# 13. Remote DB가 비어 있는 신규 Production인지 확인

가능한 범위에서 read-only 방식으로 Production DB 상태를 확인한다.

특히 예상하지 않은 기존 데이터나 schema가 있는지 확인한다.

새 Production project여야 하는 상황인데 이미 application table/data가 존재한다면 원인을 먼저 확인한다.

절대로:

```text
일단 reset하고 다시 시작
```

하지 않는다.

---

# 14. Migration 적용

다음 조건을 모두 만족할 때만 remote migration을 적용한다.

```text
[ ] 의도한 Production project 확인
[ ] CLI 인증 정상
[ ] project link 정상
[ ] preflight PASS
[ ] migration history 정상
[ ] destructive conflict 없음
[ ] production seed 안전성 확인
```

기존 repository에 remote db push script가 있다면 해당 script를 우선 사용한다.

적용 과정에서 실제로 어떤 migration이 실행되는지 확인한다.

실패하면 반복 실행하기 전에 원인을 조사한다.

migration 실패를 숨기거나 migration history를 임의로 고치지 않는다.

적용 후 remote migration 상태를 다시 조회한다.

다음 application table이 존재하는지 확인한다.

```text
profiles
projects
project_members
project_links
notices
recruitments
recruitment_steps
site_settings
contact_items
social_links
```

또한 다음을 확인한다.

* RPC

* Storage bucket
* Storage policies

schema 전체 내용을 출력할 필요는 없으며 존재/정상 여부를 검증한다.

# 16. Production Seed 적용

migration이 성공한 뒤에만:

```text
supabase/seeds/production.sql
```

을 적용한다.

절대로:

```text
supabase/seed.sql
```

을 Production에 사용하지 않는다.

적용 후 확인한다.

* `site_settings` baseline 존재
* fake contents 없음
* fake account 없음
* fake admin 없음

가능하면 Production seed를 다시 적용해도 문제가 없는 idempotent 구조인지 확인한다.

단, 실제 Production에 불필요한 반복 write를 수행할 필요가 없다면 SQL 구조 검토로 검증해도 된다.

---

# 17. Remote RLS 검증

현재 repository에 있는 remote RLS check를 사용한다.

최소한 다음 권한 경계를 확인한다.

## anon

허용:

```text
published/active public content read
```

차단:

```text
admin mutation
private/unpublished content
```

## authenticated member

차단:

```text
content admin write
self role escalation
```

## editor/admin

현재 설계에 따라 content 관리 권한이 정상인지 확인한다.

실제 admin account 생성은 다음 프롬프트에서 다룰 것이므로 이번 단계에서 가짜 admin 사용자를 Production DB에 만들지 않는다.

DB/RLS 구조 자체를 검증 가능한 범위에서 확인한다.

---

# 18. Remote Storage 구조 확인

migration으로 다음 bucket이 정상 생성되었는지 확인한다.

```text
project-images
site-assets
```

확인할 것:

* public/private 설정
* object policy
* public read
* content manager write policy
* project path 제한
* site asset path 제한

이번 프롬프트에서는 실제 관리자 계정으로 이미지 upload/replace/delete 통합 테스트까지 수행하지 않는다.

그 작업은 출시단계 프롬프트 3에서 진행한다.

이번 단계에서는 **Storage infrastructure가 remote에 정상 생성되었는지** 확인한다.

---

# 19. Remote Read Smoke Test

기존 repository의 remote smoke script를 실행한다.

현재 Production DB에 실제 콘텐츠가 거의 없을 수 있으므로:

```text
데이터가 0건
```

이라는 이유만으로 실패로 판단하지 않는다.

확인 목적은:

* remote connection 정상
* application table 접근 정상
* public query 실행 가능
* schema mismatch 없음
* permission error 없음

이다.

실제 fake content를 smoke용으로 Production에 삽입하지 않는다.

---

# 20. Remote Type Generation

현재 Production schema를 기준으로 Supabase TypeScript type을 생성하는 기존 script가 있으면 실행한다.

현재 repository의 `database.types.ts`와 비교한다.

확인할 것:

```text
remote schema
    ↓
generated types
    ↓
repository types
```

차이가 없다면 정상.

차이가 있다면 원인을 분석한다.

migration을 정확히 적용했는데 generated type에 의미 있는 차이가 발생하면 현재 `database.types.ts`가 outdated일 수 있다.

그 경우 필요한 type 갱신은 수행할 수 있지만:

* schema를 임의로 바꾸지 않는다.
* unrelated formatting diff를 만들지 않는다.
* generated file 외 불필요한 코드를 변경하지 않는다.

변경이 생겼다면 이후 TypeScript/build 검증을 수행한다.

# 21. Production 환경 변수 목록 산출

현재 codebase에서 Production 실행에 필요한 Supabase 관련 환경 변수 이름을 조사한다.

실제 값을 출력하지 않는다.

다음처럼 구분한다.

```text
Vercel Public Variables
Server-side Variables
Supabase CLI / CI Secrets
GitHub Actions Secrets
```

예상 이름을 추측하지 말고 실제 코드와 workflow를 기준으로 작성한다.

현재 프롬프트에서는 Vercel/GitHub Dashboard에 값을 등록하지 않는다.

프롬프트 4/6에서 사용할 수 있도록 **필요한 변수 이름만 최종 보고서에 정리한다.**

# 22. Auth Production 설정 사전 확인

이번 프롬프트에서는 실제 admin 생성까지 진행하지 않지만 Supabase Auth 기본 설정을 조사한다.

저장소 및 가능한 read-only 설정 기준으로 다음을 확인한다.

* email/password 인증 사용 가능 구조
* profile trigger 존재
* 신규 user 기본 role = member
* admin bootstrap procedure 존재
* admin status check 존재

Dashboard에서 추가로 설정해야 할 Auth URL/redirect 관련 항목이 있다면 다음 프롬프트/Preview 설정에서 처리할 항목으로 별도 기록한다.

임의의 production user를 생성하지 않는다.

# 24. Secret 검증

remote 설정 후 반드시 확인한다.

다음 정보가 Git tracked 파일에 들어가지 않았는지 확인한다.

```text

Production secret
```

`.env*` 또는 local credential 파일도 Git status에 나타나지 않는지 확인한다.

# 출시단계 프롬프트 3 — Production Auth/Admin/Storage 통합 검증

DotG 웹사이트는 현재 다음 상태다.

```text
기본구조
→ 구현단계
→ 운영전환
→ 출시단계 프롬프트 1
→ 출시단계 프롬프트 2
```

출시단계 프롬프트 2에서 실제 Production Supabase 구축을 완료했다.

현재 확인된 상태:

```text
Production Supabase: ACTIVE_HEALTHY
Region: ap-northeast-2

Local migrations: 6
Remote migrations: 6
Migration sync: PASS

Production seed: PASS
Remote schema: PASS
Remote RLS: PASS
Remote Storage infrastructure: PASS
Remote read smoke: PASS
Storage integrity checks: PASS
Remote type generation: PASS
```

또한 운영전환 단계에서 이미 다음 작업이 완료되어 있다.

* Production Auth 관리자 계정 생성
* 해당 Auth user의 `profiles` 생성
* admin role 부여
* 관리자 bootstrap 절차 수행

따라서 이번 작업에서는 **새로운 관리자 계정을 생성하거나 기존 계정의 credential/role을 변경하지 않는다.**

이번 작업의 목적은:

> **기존 Production 관리자 계정을 기준으로 Auth → 권한 → 관리자 Server Action → DB CRUD → Storage까지 실제 Production Supabase 환경에서 통합적으로 정상 작동하는지 검증하는 것**

이다.

아직 Vercel Preview/Production 배포 단계는 아니므로 Vercel 배포나 공식 Production URL 검증은 수행하지 않는다.

---

# 0. 작업 원칙

이번 작업은 실제 Production Supabase에 연결되므로 다음 규칙을 반드시 지켜라.

## 절대 금지

* 새로운 Production Auth user를 임의로 생성하지 않는다.
* 새로운 admin 계정을 bootstrap하지 않는다.
* 기존 관리자 비밀번호를 변경하지 않는다.
* 기존 관리자의 role을 임의로 변경하지 않는다.
* 실제 운영 콘텐츠를 테스트 목적으로 수정하거나 삭제하지 않는다.
* Production DB를 reset하지 않는다.
* table truncate/drop을 하지 않는다.
* migration을 새로 만들지 않는다.
* 기존 migration을 수정하지 않는다.
* development seed를 Production에 적용하지 않는다.
* service role key를 source code에 저장하지 않는다.
* 관리자 이메일/password를 source 또는 문서에 하드코딩하지 않는다.
* access token, DB password, service role key를 출력하지 않는다.
* 실제 credential을 Git tracked 파일에 저장하지 않는다.
* 테스트 데이터를 남긴 채 작업을 종료하지 않는다.
* 테스트를 통과시키기 위해 RLS/Auth 정책을 약화시키지 않는다.
* Vercel deploy를 수행하지 않는다.
* Git commit/push를 수행하지 않는다.

# 1. 프롬프트 2에서 발생한 의도적 변경 보존

현재 다음 generated file은 프롬프트 2에서 Production schema 기준 type generation을 수행한 결과 변경되었다.

```text
src/lib/supabase/database.types.ts
```

변경 내용에는 Production PostgREST metadata 등이 포함되어 있다.

이 변경은 **의도적인 Production schema 동기화 결과**이므로:

* 임의로 revert하지 않는다.
* 이전 버전으로 checkout하지 않는다.
* unrelated change로 판단하지 않는다.

현재 Git 상태를 먼저 확인하고 해당 변경을 기존 사용자 변경으로 보존한다.

# 6. 관리자 credential 처리 방식 조사

실제 브라우저 로그인 검증 전에 현재 repository의 E2E/Auth credential loading 구조를 조사한다.

확인할 것:

* Playwright storage state 생성 방식
* 기존 local E2E test user와 Production admin이 어떻게 구분되는지
* `.env` / `.env.local` / CI secret 사용 방식
* credential이 Git ignore 대상인지

## 매우 중요

기존 Production 관리자 credential을 다음에 넣지 않는다.

```text
source code
test fixture
SQL file
Markdown document
Git tracked .env
command history에 그대로 남는 방식
```

실제 로그인에 credential이 필요하고 안전한 설정이 아직 없다면 Codex는 값을 요구하지 말고:

```text
[사용자 작업 필요]

Production 관리자 credential을 Git에서 제외된 로컬 환경 변수에 설정하십시오.

필요한 환경 변수:
- <실제 코드 기준 email 변수 이름>
- <실제 코드 기준 password 변수 이름>

값 자체를 Codex 채팅에 붙여넣지 마십시오.
```

형식으로 안내한다.

새로운 환경 변수 이름을 임의로 만들기 전에 기존 E2E/Auth 구조에서 이미 사용하는 이름이 있는지 먼저 확인한다.

# 8. Credential 없이 가능한 Production 권한 검증 먼저 수행

설계대로:

# 9. Production 연결 브라우저 검증 환경 준비

아직 Vercel Preview/Production 배포 전이므로 필요하다면 **로컬 Next.js 앱을 Production Supabase에 연결하여** 통합 검증한다.

단 다음 원칙을 지킨다.

* Production Supabase URL/key를 Git tracked 파일에 저장하지 않는다.
* development Supabase와 Production Supabase를 혼동하지 않는다.
* 실행 전에 현재 환경이 Production Supabase를 가리키는지 명확히 확인한다.
* 테스트 종료 후 local environment가 실수로 Production에 고정되지 않도록 확인한다.
* production fallback 금지 정책을 유지한다.

현재 프로젝트에 Production/remote smoke 또는 E2E용 안전 장치가 있다면 반드시 재사용한다.

새로운 bypass flag를 임의로 추가하지 않는다.

# 14. Production CRUD 테스트 전략

이 단계에서는 실제 Production DB에 write가 발생할 수 있다.

따라서 실제 동아리 콘텐츠를 건드리지 않고 **명확하게 식별 가능한 임시 테스트 데이터**만 사용한다.

모든 테스트 데이터는 다음 원칙을 따른다.

예:

```text
title:
e2e-production-verification-...

slug:
e2e-production-verification-<unique>
```

또는 현재 프로젝트에서 이미 사용하는 `e2e-*` naming convention을 그대로 사용한다.

규칙:

* 실제 운영 slug와 충돌하지 않는다.
* 테스트 목적이 명확하다.
* 테스트 종료 후 cleanup한다.
* cleanup 실패 시 반드시 보고한다.
* 실제 기존 콘텐츠를 수정 테스트 대상으로 사용하지 않는다.

# 17. Recruitment Production 검증

Recruitment는 current 상태가 실제 사이트에 영향을 줄 수 있으므로 특히 조심한다.

기존 실제 current recruitment가 있는지 먼저 확인한다.

## 실제 current recruitment가 있다면

기존 current 모집을 임의로 해제하거나 테스트 recruitment로 교체하지 않는다.

대신 가능한 범위에서:

* draft/upcoming temporary recruitment 생성
* save
* validation
* archive

정도만 검증한다.

## current recruitment가 없다면

current 지정 테스트가 안전한지 판단할 수 있지만, 이번 검증만을 위해 불필요하게 공개 상태를 만들 필요는 없다.

가능하면 기존 SQL/RPC tests로 current switching 로직을 확인하고 Production에서는 destructive/public-visible 변경을 최소화한다.

반드시 확인할 것:

* create RPC
* save RPC
* steps
* archive
* published/current invariant
* RLS

# 18. Site Settings 검증

`site_settings`는 singleton이며 실제 공개 사이트 전체에 영향을 줄 수 있으므로 테스트 값을 임의로 저장하지 않는다.

먼저 current row를 read-only로 확인한다.

Production에서 write path를 반드시 검증해야 한다면:

* 기존 값을 먼저 읽는다.
* 변경 전 snapshot을 확보한다.
* 의미에 영향이 없는 안전한 field인지 판단한다.
* test update
* 즉시 원래 값으로 복구
* DB 값이 완전히 복원되었는지 확인

하지만 기존 automated test/RPC/database test로 충분히 검증되어 있고 Production 실데이터 변형 위험이 크다면 직접 mutation하지 않아도 된다.

그 경우:

```text
Production destructive-risk 때문에 read-only 검증 + 기존 automated coverage로 대체
```

라고 보고한다.

# 21. Site Asset Storage 검증

실제 Production logo/Hero를 교체하지 않는다.

사이트 asset write path의 Production 검증이 반드시 필요하다면 별도의 temporary path를 사용할 수 있는지 현재 path policy를 먼저 확인한다.

현재 policy가:

```text
logo/...
hero/...
```

만 허용한다면 기존 실제 asset을 덮어쓰지 않는 unique temporary object name을 사용한다.

예:

```text
logo/e2e-production-...
hero/e2e-production-...
```

단 DB `site_settings.logo_path`, `hero_image_path`를 실제 temporary asset으로 바꾸는 것은 사용자 노출에 영향을 줄 수 있으므로 최대한 피한다.

가능하면:

* Storage object RLS/write/read/delete 검증
* application upload logic은 automated test

조합으로 검증한다.

Production 공개 사이트에 임시 테스트 이미지가 노출되는 테스트는 하지 않는다.

# 22. Storage 비권한 write 차단

가능한 existing RLS test/script를 이용하여:

```text
anon write → DENY
member write → DENY
editor/admin write → ALLOW
```

를 Production policy 기준으로 확인한다.

실제 비권한 계정 credential을 새로 만들지 않는다.

기존 test harness에서 role/JWT simulation이 가능하다면 그것을 사용한다.

# 23. Storage 정합성 재검사

CRUD/Storage 테스트 후 기존 integrity script를 Production 기준으로 실행한다.

최소:

```text
storage:paths:check
storage:dangling:check
storage:orphans:check
```

결과 목표:

```text
invalid paths: 0
dangling references: 0
unexpected orphan test objects: 0
```

cleanup이 필요한 테스트 object가 있다면 안전하게 테스트 object만 제거한다.

기존 실제 orphan object는 이번 작업에서 자동 삭제하지 않는다.

실제 Production orphan cleanup `--apply`는 테스트 잔여물임이 명백한 경우가 아니면 수행하지 않는다.

# 27. 자동 테스트 재검증

Production 통합 검증 후 로컬 코드 regression이 없는지 확인한다.

현재 package scripts 기준으로 필요한 검증을 실행한다.

최소:

```powershell
pnpm exec tsc --noEmit
pnpm lint
pnpm build
```

그리고 관련:

```text
test:auth
test:admin
test:storage
test:supabase
```

가 존재하면 실행한다.

전체 E2E를 다시 실행하는 것이 현재 환경에서 안전하고 Production DB를 테스트 fixture로 오염시키지 않는 구조인지 먼저 확인한다.

기존 `ci:e2e`가 local Supabase 전용이라면 Production 연결 상태에서 그대로 실행하지 않는다.

local E2E는 local Supabase 환경으로 분리한 뒤 실행한다.

# 28. Production 검증과 Local E2E 환경 분리 확인

이번 작업에서 특히 중요하다.

Production Supabase를 연결한 상태로 기존 destructive E2E/global teardown을 실수로 실행하면 안 된다.

현재 E2E global setup이 local Supabase safety check를 수행하는 것으로 보고되어 있으므로 이 안전 장치가 실제 작동하는지 확인한다.

확인:

```text
Local E2E
→ local Supabase만 허용

Production integration check
→ production-safe 테스트만 허용
```

Production 환경에서 기존 local fixture cleanup이 실행되지 않도록 한다.

# 운영전환 프롬프트 2 — 원격 Supabase 배포 기반 구축

현재 DotG 웹사이트 프로젝트의 전체 코드와 Supabase 구성을 조사한 뒤, 로컬 Supabase에서 검증된 DB·Auth·Storage 구조를 새로운 원격 Supabase 프로젝트에 안전하고 반복 가능하게 적용할 수 있는 배포 기반을 구축하라.

운영전환 프롬프트 1에서 구현한 환경 구분과 Supabase 환경 변수 검증 정책을 유지하라. 해당 구조를 임의로 되돌리거나 중복 구현하지 마라.

이번 작업의 목표는 다음 과정을 재현 가능하게 만드는 것이다.

```text
빈 원격 Supabase 프로젝트
→ 프로젝트 연결
→ migration 적용
→ Storage bucket 및 policy 적용 확인
→ 초기 데이터 적용
→ 최초 관리자 생성
→ DB 타입 재생성
→ 원격 smoke test
→ 배포 준비 상태 확인
```

원격 Supabase 접근 정보가 현재 환경에 제공되어 있다면 비파괴적 범위에서 실제 연결과 검증을 수행하라.

접근 정보가 없거나 인증이 필요한 경우에는 추측한 project ref, access token, 비밀번호를 사용하지 말고 다음을 구현하라.

* 실행 가능한 script
* 검증 명령
* 초기화 절차
* 운영 체크리스트
* 실패 시 진단 방법

실제 원격 작업을 수행하지 못한 부분은 최종 보고에서 명확히 구분하라.

## 1. 작업 전 조사

먼저 프로젝트의 다음 항목을 실제 파일을 기준으로 조사하라.

* 프로젝트 루트와 `dotg-web` 디렉터리 구조
* `supabase/` 디렉터리 전체
* `supabase/config.toml`
* migration 파일 전체와 적용 순서
* seed 파일과 seed 실행 방식
* DB 테스트 파일
* RLS 테스트 파일
* Supabase RPC 및 함수
* trigger
* enum
* Storage bucket 생성 migration
* Storage RLS policy migration
* `database.types.ts` 생성 방식
* `package.json`의 Supabase 관련 script
* README의 Supabase 로컬 개발 절차
* `docs/database-schema.md`
* `docs/authentication.md`
* `docs/storage-management.md`
* 환경 변수 예제 파일
* 운영전환 프롬프트 1에서 추가된 환경 설정 문서 및 script

다음 사항을 조사 결과에 포함하라.

1. migration이 하나의 빈 프로젝트에 처음부터 순차 적용 가능한지
2. migration 사이에 숨겨진 선행 조건이 있는지
3. 이전 migration이 이후 migration에 의해 무효화되거나 충돌하는지
4. 개발용 seed가 운영 환경에서도 실행될 위험이 있는지
5. seed에 고정 UUID 또는 테스트 계정 의존성이 있는지
6. Storage bucket이 migration으로 생성되는지
7. Storage bucket 생성과 policy 적용 순서가 안전한지
8. `profiles` row가 어떤 방식으로 생성되는지
9. Auth 사용자 생성 시 profile 자동 생성 trigger가 있는지
10. 최초 admin을 만드는 공식 절차가 존재하는지
11. DB 타입 생성 명령이 local과 remote 중 어디를 기준으로 하는지
12. 원격 프로젝트를 초기화할 때 파괴적 명령이 실행될 가능성이 있는지
13. 테스트 데이터와 운영 초기 데이터가 구분되어 있는지
14. RLS가 누락된 public schema 테이블이 있는지
15. 함수 또는 RPC의 `security definer` 사용이 안전한지

조사 없이 migration을 새로 만들거나 기존 migration을 수정하지 마라.

## 2. migration 배포 가능성 점검

현재 migration 전체가 빈 원격 Supabase 프로젝트에 정상 적용될 수 있는지 점검하라.

다음 항목을 검증하라.

* 파일명 기준 migration 순서
* extension 생성 순서
* enum 생성 순서
* table 생성 순서
* foreign key 참조 순서
* index 생성 순서
* function과 trigger 생성 순서
* RLS 활성화 순서
* RLS policy 생성 순서
* RPC가 참조하는 table과 function의 생성 순서
* Storage bucket 생성 순서
* Storage policy 생성 순서
* seed가 참조하는 schema와 column의 존재 여부

문제가 발견되면 다음 원칙으로 수정하라.

* 이미 공유되거나 적용됐을 가능성이 있는 기존 migration을 무작정 수정하지 마라.
* 필요한 경우 새로운 보정 migration을 추가하라.
* migration은 가능한 한 idempotent하게 작성하라.
* `drop table`, `drop column`, `truncate` 등 파괴적 변경을 피하라.
* 개발 DB에만 맞춰진 가정을 제거하라.
* 로컬 DB reset이 계속 성공해야 한다.
* 원격 프로젝트에서도 Supabase 표준 role과 schema를 사용해야 한다.

migration 파일을 정리하거나 squash하지 마라. 별도 요청 없이 기존 migration history를 재작성하지 마라.

## 3. 개발 seed와 운영 초기 데이터 분리

현재 seed 구조를 조사하고 개발·테스트 데이터와 운영 초기 데이터를 분리하라.

다음 기준을 적용하라.

### 개발용 seed

개발 환경에서 다음 목적을 위해 사용할 수 있다.

* 공개 페이지 확인용 프로젝트
* 공지사항
* 모집 정보
* 연락처
* SNS 링크
* 사이트 설정
* 테스트용 profile 또는 fixture

개발 seed에는 실제 운영 콘텐츠나 실제 사용자 정보를 넣지 마라.

### 운영 초기 데이터

운영 환경에는 서비스가 시작되기 위해 반드시 필요한 최소 데이터만 적용하라.

예시:

* `site_settings` singleton 기본 row
* 필수 설정값의 안전한 기본값
* 시스템 동작에 필요한 기준 row

다음 데이터는 운영 seed에 자동 삽입하지 않는 것을 기본 원칙으로 하라.

* 가짜 프로젝트
* 가짜 공지
* 가짜 모집 정보
* 가짜 사용자
* 가짜 관리자
* 테스트 이메일
* 실제처럼 보이는 연락처 또는 SNS 주소

필요하다면 다음과 같이 파일 또는 실행 경로를 분리하라.

```text
supabase/seed.sql
supabase/seeds/development.sql
supabase/seeds/production.sql
```

실제 구조는 Supabase CLI와 현재 프로젝트 구성에 맞게 결정하라.

다음 요구사항을 만족해야 한다.

* `supabase db reset`은 개발 seed를 정상 적용할 수 있어야 한다.
* 원격 운영 프로젝트에 개발 seed가 실수로 적용되지 않도록 해야 한다.
* 운영 초기 데이터 적용 명령은 명시적으로 실행해야 한다.
* production seed는 반복 실행해도 중복 row가 생기지 않도록 작성하라.
* 운영 seed에 Auth 사용자 생성 로직을 넣지 마라.
* seed 파일에 secret, 비밀번호, token을 넣지 마라.

## 4. 원격 Supabase 연결 script 정리

Supabase CLI를 이용해 원격 프로젝트를 연결하고 migration을 적용하는 절차를 정리하라.

검토해야 할 표준 흐름:

```text
supabase login
supabase link
supabase db push
```

프로젝트에서 pnpm을 통해 Supabase CLI를 실행하고 있다면 해당 방식을 유지하라.

예:

```text
pnpm.cmd supabase ...
```

필요하다면 다음과 같은 package script를 추가하라.

```text
supabase:link
supabase:db:push
supabase:db:diff
supabase:types:remote
supabase:smoke:remote
```

단, 다음 원칙을 지켜라.

* project ref를 코드에 하드코딩하지 마라.
* access token을 script에 포함하지 마라.
* DB password를 파일에 저장하지 마라.
* 운영 프로젝트에 `db reset`을 실행하는 script를 만들지 마라.
* 원격 DB에 destructive reset을 유도하는 명령을 만들지 마라.
* Windows PowerShell에서도 실행 가능하게 하라.
* shell-specific inline 환경 변수 문법에 의존하지 마라.
* 기존 script와 중복된다면 새로 만들지 말고 정리하라.

script 이름은 기존 프로젝트 명명 방식에 맞게 조정할 수 있다.

## 5. 원격 migration 적용 전 안전 점검

원격 DB에 migration을 적용하기 전에 실행할 수 있는 사전 점검 절차를 구현하라.

가능하면 다음 항목을 확인하라.

* Supabase CLI 설치 여부
* 로그인 또는 access token 여부
* 프로젝트 link 여부
* 대상 project ref 확인
* local migration 상태
* 원격 migration history
* 미적용 migration 목록
* migration 파일 checksum 또는 변경 여부
* 현재 Git working tree 상태
* 필수 환경 변수 존재 여부
* Production 대상 작업인지 명시적 확인
* 개발 seed가 함께 적용되지 않는지

자동 script에서 사용자 입력을 요구하는 방식이 테스트나 CI를 방해할 수 있다면 다음과 같이 분리하라.

* 읽기 전용 검사 명령
* 실제 적용 명령
* 운영자 확인 체크리스트

자동으로 원격 migration을 실행하기보다는, 적용 전 상태를 출력하고 운영자가 명시적으로 배포 명령을 실행하도록 구성하는 편을 우선하라.

## 6. Storage bucket 초기화 검증

현재 migration에 정의된 다음 public bucket을 확인하라.

* `project-images`
* `site-assets`

다음 항목을 검증하라.

* bucket이 migration으로 생성되는지
* public bucket 설정이 의도대로 적용되는지
* 허용 파일 크기 제한 여부
* 허용 MIME type 제한 여부
* bucket 이름이 앱 코드와 일치하는지
* `project-images` 경로 정책
* `site-assets` 경로 정책
* anon 읽기 권한
* authenticated 읽기 권한
* editor 업로드·수정·삭제 권한
* admin 업로드·수정·삭제 권한
* member 쓰기 차단
* project path의 `{projectId}/thumbnail/...` 제한
* site asset의 `logo/...`, `hero/...` 제한
* object 삭제 policy
* object update policy
* `storage.objects` policy가 다른 bucket에 영향을 주지 않는지

Storage bucket과 policy가 migration만으로 재현되지 않는다면 이를 migration 기반으로 정리하라.

Dashboard에서 수동으로 만든 설정에 의존하지 않도록 하라.

단, 이번 프롬프트에서는 이미지 업로드 보상 처리나 orphan object 정리 기능까지 구현하지 마라. 해당 작업은 운영전환 프롬프트 4의 범위다.

## 7. 원격 Storage 검증 script

원격 Supabase에 연결된 상태에서 Storage 설정을 읽기 전용으로 확인할 수 있는 smoke test 또는 점검 script를 추가하라.

가능하면 다음을 확인하라.

* 두 bucket의 존재
* public 설정
* bucket별 파일 크기 설정
* bucket별 MIME 설정
* 관련 RLS policy 존재 여부

Supabase 관리 API나 service role key가 필요한 방식은 사용하지 마라.

anon key로 확인할 수 없는 관리 정보는 SQL 점검 script 또는 Supabase CLI 기반 절차로 제공하라.

점검 결과는 최소한 다음처럼 명확해야 한다.

```text
PASS project-images bucket exists
PASS site-assets bucket exists
PASS public read policy exists
PASS member write is denied
PASS editor write policy exists
```

실제 원격 연결이 없는 환경에서도 script 자체의 정적 검증 또는 local 검증이 가능하도록 구성하라.

## 8. 최초 관리자 생성 절차 구축

빈 원격 프로젝트에서 첫 번째 `admin` 사용자를 안전하게 생성하는 절차를 마련하라.

현재 Auth와 `profiles` 구조를 조사한 뒤 다음 흐름을 지원하라.

```text
Supabase Auth 사용자 생성
→ auth.users UUID 확인
→ profiles row 존재 확인
→ role을 admin으로 설정
→ 관리자 로그인
→ /admin 접근 확인
```

다음 사항을 확인하라.

* Auth 사용자 생성 시 `profiles` row가 자동 생성되는지
* 자동 생성 trigger가 없다면 profile 생성 절차
* role의 기본값
* profile이 중복 생성될 가능성
* Auth 사용자는 있지만 profile이 없는 경우
* profile은 있지만 Auth 사용자가 없는 경우
* admin role 변경 권한
* RLS 때문에 최초 admin 설정이 막히는지
* 관리자 UI에서 자기 자신을 admin으로 승격할 수 있는 취약점이 없는지

최초 관리자 생성은 다음 중 안전한 방식을 선택하라.

* Supabase Dashboard에서 Auth 사용자 생성 후 SQL Editor에서 UUID를 지정해 role 변경
* 제한된 초기화 SQL 함수
* 로컬에서 운영자가 명시적으로 실행하는 관리 script

다음 방식은 사용하지 마라.

* 이메일이나 비밀번호 하드코딩
* 모든 신규 사용자를 admin으로 만드는 trigger
* public 또는 anon이 호출 가능한 admin 승격 RPC
* 특정 이메일 문자열을 코드에서 admin으로 간주
* service role key를 클라이언트나 일반 앱 script에 저장
* seed로 가짜 Auth 사용자를 삽입

초기 관리자 생성용 SQL을 제공한다면 반드시 명시적인 사용자 UUID를 인자로 사용하고, 반복 실행 시 안전해야 한다.

예시 형식:

```sql
select public.bootstrap_admin('<AUTH_USER_UUID>');
```

단, 실제 함수명과 구현 방식은 현재 schema와 보안 구조를 검토한 뒤 결정하라.

초기화 함수가 영구적으로 남는 것이 위험하다면 함수 대신 1회성 운영 SQL 절차를 문서화하라.

가장 안전하고 단순한 방식을 선택하고 선택 이유를 설명하라.

## 9. 관리자 계정 상태 점검

최초 관리자 설정 후 다음 상태를 확인할 수 있는 SQL 또는 점검 절차를 추가하라.

* Auth 사용자 존재
* profile 존재
* profile role이 admin인지
* profile ID와 Auth UUID가 일치하는지
* 로그인 가능한 이메일 상태인지
* 삭제되거나 비활성화된 사용자가 아닌지
* admin 사용자가 최소 1명 존재하는지

민감 정보는 출력하지 마라.

다음 정보만 출력하는 것을 권장한다.

* 사용자 UUID 일부 또는 전체 UUID
* 이메일 마스킹 값
* role
* profile 존재 여부
* Auth 사용자 존재 여부

비밀번호, token, session, key는 출력하지 마라.

## 10. 원격 DB 타입 생성 구조 정리

현재 `database.types.ts` 생성 방식을 조사하고 local DB와 원격 DB 중 어떤 schema를 기준으로 생성하는지 명확히 하라.

다음 명령 흐름을 지원하라.

### 로컬 기준 타입 생성

```text
pnpm.cmd run supabase:types
```

### 원격 기준 타입 생성

project ref 또는 link 상태를 이용해 원격 schema에서 타입을 생성하는 별도 명령을 제공하라.

예시:

```text
pnpm.cmd run supabase:types:remote
```

다음 조건을 만족해야 한다.

* project ref를 코드에 하드코딩하지 마라.
* 생성 결과 경로는 기존 `src/lib/supabase/database.types.ts`를 유지하라.
* 타입 생성 후 파일이 변경됐는지 확인할 수 있어야 한다.
* 생성된 타입이 현재 코드와 호환되는지 TypeScript 검사로 검증하라.
* 타입 생성 명령 실패 시 기존 파일을 빈 파일로 덮어쓰지 않도록 하라.
* Windows에서도 동작하도록 하라.
* 자동 생성 파일임을 파일 또는 문서에 명시하라.

가능하다면 임시 파일로 생성한 뒤 성공 시 최종 파일을 교체하는 안전한 방식을 사용하라.

## 11. 원격 DB smoke test 구축

원격 Supabase 프로젝트에 연결한 뒤 주요 schema가 정상 적용됐는지 확인하는 읽기 중심 smoke test를 구축하라.

* `projects`
* `project_members`

* `recruitment_status`
* `user_role`

### 주요 기능

* `site_settings` singleton row

* 프로젝트·공지·모집 공개 조회 가능 여부
* 비공개 콘텐츠 anon 노출 차단
* anon의 관리자 테이블 mutation 차단

* Storage bucket 존재

원격 smoke test는 운영 데이터를 생성·수정·삭제하지 않는 것을 우선하라.

mutation 검증이 반드시 필요한 경우에는 다음 조건을 적용하라.

* 전용 테스트 row 사용
* 테스트임이 명확한 식별자 사용
* 테스트 종료 후 정리
* 운영 프로젝트에서는 기본적으로 비활성화
* 명시적인 실행 옵션 없이는 mutation하지 않기

가능하면 smoke test를 다음 두 단계로 구분하라.

```text
remote smoke read-only
remote smoke mutation
```

운영 프로젝트에서는 read-only 검사를 기본으로 하라.

## 12. RLS 원격 적용 확인

로컬 DB 테스트가 통과하는 것과 별개로, 원격 프로젝트에 RLS가 실제 적용됐는지 확인하는 절차를 마련하라.

다음을 검사하라.

* public schema의 대상 테이블 모두 RLS 활성화
* anon 공개 조회 policy
* authenticated member 읽기 범위
* editor 쓰기 범위
* admin 쓰기 범위
* manager 권한 재검사 방식
* owner 또는 creator 기반 조건
* Storage object policy
* public 함수 실행 권한
* `security definer` 함수의 `search_path`
* 필요하지 않은 `PUBLIC` execute 권한

RLS 검증은 DB 테스트 또는 SQL 점검 파일 형태로 추가할 수 있다.

운영 DB에서 사용 가능한 읽기 전용 RLS 점검 쿼리도 문서화하라.

## 16. 자동화 테스트 추가

현재 테스트 구조를 활용해 이번 작업에서 추가한 기능을 검증하라.

최소 테스트 항목:

* migration 전체를 빈 local DB에 적용
* 개발 seed 적용
* production seed가 있다면 반복 실행
* production seed에 가짜 콘텐츠가 없는지
* Storage bucket 생성
* Storage bucket 이름 일치
* Storage policy 존재
* 모든 대상 테이블 RLS 활성화
* 주요 RPC 존재
* `site_settings` singleton 초기 상태
* profile 생성 방식
* 최초 관리자 설정 SQL 또는 절차의 안전성

## 17. 구현 제약

다음 제약을 반드시 지켜라.

* 원격 프로젝트에 개발 seed를 자동 적용하지 마라.
* 기존 적용 가능성이 있는 migration history를 재작성하지 마라.
* destructive migration을 추가하지 마라.
* Dashboard 수동 설정에만 의존하지 마라.
* 이번 작업에서 Vercel 실제 배포를 수행하지 마라.
* 이번 작업에서 Playwright E2E를 구축하지 마라.
* 이번 작업에서 GitHub Actions를 구축하지 마라.
* 이번 작업에서 Storage 업로드 보상 로직을 구현하지 마라.
* UI 디자인과 공개 페이지 구조를 변경하지 마라.
* 타입 오류를 `any`, `@ts-ignore`, `eslint-disable`로 우회하지 마라.
* 실제 원격 작업을 수행하지 못했다면 완료했다고 주장하지 마라.

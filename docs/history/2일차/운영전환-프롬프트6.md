# 운영전환 프롬프트 6 — Playwright E2E 테스트 구축

현재 DotG 웹사이트 프로젝트의 공개 페이지, 관리자 인증, 역할별 접근 제어, 콘텐츠 CRUD, Storage 이미지 관리, 관리자 UI 상태 처리와 데이터 무결성 구조를 조사한 뒤, 실제 브라우저에서 핵심 사용자 흐름을 검증할 수 있는 Playwright E2E 테스트 체계를 구축하라.

이번 작업은 운영전환 프롬프트 1~5가 완료된 상태를 기준으로 한다.

현재 완료된 사항:

* local, Preview, Production 환경 분리
* Preview·Production 환경에서 Supabase 필수 설정
* 운영 환경 mock fallback 차단
* 원격 Supabase migration 및 production seed 적용
* 원격 DB·RLS·Storage 검증
* 최초 admin 생성 및 실제 로그인 확인
* anon/member/editor/admin 권한 체계
* proxy·관리자 layout·Server Action·RLS 다중 권한 검사
* 프로젝트·공지사항·모집·사이트 설정·연락처·SNS CRUD
* 프로젝트 대표 이미지, 로고, Hero 이미지 관리
* Storage 업로드·교체·삭제 보상 처리
* orphan·dangling Storage 점검 기반
* 관리자 폼 제출 상태, 성공·실패 메시지, 검증 오류 처리
* 데이터 무결성 constraint와 mutation 검증
* current 모집 singleton 정책
* `site_settings` singleton 정책
* slug·URL·날짜·정렬 순서 검증
* 동시 수정 충돌 처리 기반

이미 완료된 환경, 인증, Storage, 관리자 CRUD, DB constraint 구조를 다시 구현하거나 되돌리지 마라.

이번 작업의 핵심 목표는 다음과 같다.

```text
실제 브라우저 실행
→ 테스트 전용 데이터 준비
→ 역할별 로그인
→ 공개·관리자 주요 흐름 실행
→ UI와 DB 결과 확인
→ 테스트 데이터 정리
→ 재실행 가능한 E2E 체계 구축
```

Playwright 테스트는 단순히 페이지가 열리는지만 확인하지 말고, 실제 운영자가 수행하는 핵심 흐름과 권한 차단이 브라우저에서 일관되게 동작하는지 검증해야 한다.

## 2. Playwright 설치 및 기본 설정

프로젝트에 Playwright가 없다면 공식 패키지를 추가하고 기본 설정을 구축하라.

검토할 패키지:

```text
@playwright/test
```

필요한 브라우저 설치 절차도 package script 또는 문서에 포함하라.

예:

```powershell
pnpm exec playwright install
```

CI에서는 필요한 브라우저와 system dependency 설치 방식을 별도로 고려하라.

`playwright.config.ts`를 프로젝트 구조에 맞게 작성하라.

최소 설정 항목:

* `testDir`
* `baseURL`
* timeout
* expect timeout
* retries
* workers
* reporter
* screenshot
* video
* trace
* webServer
* browser project
* viewport
* locale
* timezone
* output directory

권장 정책:

```text
로컬
- 실패 시 screenshot
- 첫 retry 시 trace
- 필요 시 video retain-on-failure
- workers 병렬 실행 가능 여부는 DB 격리 수준에 따라 결정

CI
- retries 활성화
- HTML 또는 blob reporter
- 실패 artifact 저장
- production build 또는 안정적인 preview server 사용
```

테스트 언어와 UI가 한국어라면 locale을 `ko-KR`로 설정하는 것을 검토하라.

날짜 검증이 있다면 timezone을 `Asia/Seoul`로 명시하라.

## 3. E2E 전용 환경 보호

E2E 테스트가 운영 Supabase를 사용하지 않도록 강한 안전장치를 추가하라.

다음 정책을 구현하라.

```text
E2E
→ local Supabase 또는 명시적인 Preview 테스트 프로젝트만 허용

Production Supabase
→ 기본적으로 E2E mutation 금지
```

필요한 환경 변수 예시:

```text
E2E_BASE_URL
E2E_SUPABASE_URL
E2E_SUPABASE_ANON_KEY
E2E_ALLOW_REMOTE
E2E_TARGET_ENV
```

실제 이름은 기존 환경 정책과 충돌하지 않도록 결정하라.

다음 검증을 추가하라.

* 테스트 대상 URL 존재
* Supabase URL 존재
* local Supabase URL 판별
* remote 환경이면 명시적 허용 필요
* Production project ref 또는 Production URL 차단
* 테스트 전용 marker 존재 여부
* 운영전환 프롬프트 1의 환경 검증 구조 재사용
* secret 값 로그 출력 금지

예:

```text
Supabase URL이 localhost 또는 127.0.0.1
→ 기본 허용

remote Preview 프로젝트
→ E2E_ALLOW_REMOTE=true일 때만 허용

Production 프로젝트
→ 강제 차단
```

실제 project ref를 코드에 하드코딩하지 말고 환경 또는 안전한 설정 파일로 주입하라.

## 4. 테스트 계정 전략 수립

다음 역할의 E2E 테스트 계정을 준비하라.

* member
* editor
* admin

anon은 로그인하지 않은 context를 사용한다.

테스트 계정은 다음 조건을 만족해야 한다.

* 운영 계정과 분리
* 고정된 테스트 이메일 형식 사용 가능
* 실제 개인 이메일 사용 금지
* 비밀번호를 repository에 평문 저장 금지
* local Supabase reset 후 재생성 가능
* 각 role의 profile이 정확히 준비됨
* 테스트 종료 후 필요하면 정리 가능
* admin bootstrap 절차와 일반 E2E fixture 분리

가능한 전략을 비교하라.

### 전략 A: local seed에서 Auth fixture 준비

장점:

* 테스트 반복성 높음
* local reset 후 일정한 상태

주의:

* `auth.users` 직접 seed 방식이 Supabase 권장 흐름과 호환되는지 확인
* 비밀번호 hash 처리
* Auth schema 직접 조작 위험

### 전략 B: 테스트 setup에서 Supabase Auth API로 사용자 생성

장점:

* 실제 Auth 흐름과 유사

주의:

* admin API 또는 service role 필요 여부
* secret 관리
* local에서만 사용할 수 있는 관리 endpoint 여부

### 전략 C: Supabase CLI·SQL fixture

장점:

* local DB에 명시적으로 적용 가능

주의:

* Auth 사용자 생성 정합성
* profile trigger 실행 여부

현재 프로젝트와 local Supabase 환경에서 가장 안전하고 재현 가능한 방식을 선택하라.

service role key가 필요하다면 다음 조건을 지켜라.

* E2E local 전용
* 브라우저 context에 노출 금지
* `NEXT_PUBLIC_` 접두사 금지
* repository에 실제 값 저장 금지
* CI secret 또는 local CLI가 제공하는 값 사용
* 앱 코드에서는 사용 금지
* 일반 관리자 CRUD에서 사용 금지

가능하면 local Supabase의 test fixture를 CLI 또는 DB script로 준비하여 앱 runtime에 service role을 추가하지 않는 방식을 우선하라.

## 5. E2E fixture 및 데이터 격리

테스트가 development seed의 임의 데이터에 과도하게 의존하지 않도록 E2E fixture 전략을 구축하라.

필요하다면 다음을 분리하라.

```text
supabase/seed.sql
→ 일반 로컬 개발용 mock content

supabase/seeds/e2e.sql
→ E2E 전용 fixture
```

또는 E2E setup script에서 고유 데이터를 생성하라.

테스트 데이터 식별 규칙을 정하라.

예:

```text
e2e-project-<run-id>
e2e-notice-<run-id>
E2E 연락처 <run-id>
```

요구사항:

* slug 충돌 방지
* 테스트별 고유 ID
* 병렬 테스트 충돌 방지
* 테스트 종료 후 정리 가능
* 실패한 테스트의 잔여 데이터 재실행 시 충돌하지 않음
* 운영 콘텐츠와 구분 가능
* 테스트 목록이 공개 페이지에 잠깐 노출될 수 있는 경우 명확한 prefix 사용
* local reset 기반이면 cleanup 단순화 가능

테스트 격리 전략을 다음 중 선택하라.

* 전체 suite 전 local DB reset
* test file별 fixture 생성·삭제
* worker별 고유 namespace
* serial suite

DB와 Storage 격리가 충분하지 않다면 무리한 병렬화를 피하라.

## 6. global setup과 teardown

필요하다면 Playwright global setup·teardown을 구축하라.

global setup에서 수행 가능한 작업:

1. E2E 환경 안전성 검사
2. local Supabase 실행 상태 확인
3. migration 적용 여부 확인
4. 테스트 fixture 적용
5. member/editor/admin 계정 준비
6. 필요한 Storage bucket 확인
7. 테스트용 이미지 fixture 확인
8. 로그인 storage state 생성

global teardown에서 수행 가능한 작업:

* 테스트 생성 콘텐츠 정리
* 테스트 Storage object 정리
* 임시 파일 삭제
* 민감한 storage state 삭제
* 결과 요약

다음 원칙을 지켜라.

* setup 실패 시 테스트를 진행하지 않음
* cleanup 실패를 숨기지 않음
* Production 대상이면 setup 단계에서 즉시 중단
* 테스트 사용자 비밀번호 로그 출력 금지
* 테스트 계정 전체 session 정보 로그 출력 금지
* teardown이 실패해도 원인과 잔여 데이터 식별 가능

local DB reset을 suite 전에 실행하는 구조라면, 사용자가 개발 중인 local 데이터를 잃을 수 있다는 점을 고려하라.

다음 중 안전한 방식을 선택하라.

* E2E 전용 Supabase local instance
* 명시적 `e2e:reset` 명령
* 실행 전 경고
* 일반 `test:e2e`에서는 파괴적 reset을 자동 수행하지 않고 별도 명령으로 분리

## 7. 인증 storage state 구축

member, editor, admin의 로그인 상태를 재사용할 수 있도록 Playwright storage state 사용을 검토하라.

예시 구조:

```text
playwright/.auth/member.json
playwright/.auth/editor.json
playwright/.auth/admin.json
```

요구사항:

* `.gitignore`에 포함
* 실제 token 커밋 금지
* setup project에서 실제 로그인 UI 또는 Auth API를 이용해 생성
* role별 project 설정
* 세션 만료 시 재생성
* 로그인 실패 시 명확한 setup 오류
* 운영 관리자 계정을 사용하지 않음

가능하면 admin 인증도 실제 `/admin/login` UI를 통해 한 번 검증하고, 이후 테스트에서 storage state를 재사용하라.

로그인 UI 자체 테스트는 별도의 unauthenticated context에서 수행하라.

## 8. selector 전략

Playwright selector는 가능한 한 사용자 관점의 접근 가능한 selector를 사용하라.

우선순위:

1. `getByRole`
2. `getByLabel`
3. `getByPlaceholder`
4. `getByText`
5. 안정적인 URL
6. 필요한 경우에만 `data-testid`

예:

```ts
page.getByRole("button", { name: "저장" });
page.getByLabel("프로젝트 제목");
page.getByRole("link", { name: "프로젝트 관리" });
```

다음 selector는 피하라.

* CSS class 이름
* Tailwind class
* DOM 깊이에 의존한 selector
* `nth()`에 과도하게 의존
* 스타일 변경에 깨지는 selector
* generated ID

`data-testid`를 추가해야 한다면 다음 기준을 적용하라.

* 동일한 텍스트 버튼이 여러 개라 구분이 불가능
* 목록 row를 특정 entity ID로 찾을 필요
* toast 또는 상태 영역 식별
* 이미지 미리보기
* 삭제 modal 대상 확인

`data-testid`를 UI 전체에 무분별하게 추가하지 마라.

## 9. 공개 사이트 smoke 테스트

비로그인 context에서 공개 route를 검증하라.

최소 테스트:

### 메인 페이지

* 페이지 정상 응답

## 30. DB 결과 검증

UI 메시지만 보고 성공으로 판단하지 말고 핵심 mutation은 DB 결과도 확인하라.

확인 대상:

* 프로젝트 생성·수정·삭제
* 공지 생성·수정·삭제
* current 모집
* `site_settings`
* 연락처
* SNS
* image path

방법:

* local SQL query helper
* Supabase client
* CLI query script
* 기존 `run-supabase-sql.mts` 재사용

원칙:

* DB 검증 helper는 Node 측에서만 실행
* 브라우저에 관리 credential 노출 금지
* 운영 DB 사용 금지
* SQL injection 방지를 위해 테스트 입력 parameterization
* 테스트 결과 로그에 secret 출력 금지

## 31. Storage 결과 검증

## 32. 테스트 안정성

flaky test를 줄이기 위해 다음 원칙을 적용하라.

* 임의 `waitForTimeout()` 사용 금지
* UI 상태 또는 network response를 기다림
* `expect().toBeVisible()` 등 자동 대기 활용
* animation에 의존하지 않음
* selector 안정성
* 테스트 순서 의존 제거
* 고유 fixture
* 병렬 실행 범위 제한
* redirect 완료 확인
* revalidation 반영 대기
* 이미지 로딩 완료 확인
* toast 자동 소멸 타이밍에 과도하게 의존하지 않음

정말 필요한 경우에만 짧은 timeout을 사용하고 이유를 주석으로 설명하라.

## 33. 재시도 정책

* retry에서 trace 수집
* 첫 실패 원인 보존

테스트가 retry에서만 통과한다면 원인을 조사하고 최종 보고에 기록하라.

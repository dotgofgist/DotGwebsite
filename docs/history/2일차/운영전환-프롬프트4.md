# 운영전환 프롬프트 4 — Supabase Storage 이미지 정합성 강화

현재 DotG 웹사이트 프로젝트의 프로젝트 대표 이미지, 사이트 로고, Hero 이미지 업로드·교체·삭제 흐름을 전체적으로 조사하고, Supabase Storage와 데이터베이스 사이의 불일치가 발생하지 않도록 이미지 관리 기능을 운영 환경 수준으로 보완하라.

이번 작업은 운영전환 프롬프트 1~3이 완료된 상태를 기준으로 한다.

현재 완료된 사항:

* local, Preview, Production 환경 분리
* Preview·Production 환경에서 Supabase 필수 설정
* 원격 Supabase migration 적용 완료
* production seed 적용 완료
* `project-images`, `site-assets` bucket 생성 완료
* Storage public read 정책 적용 완료
* editor/admin Storage write 정책 적용 완료
* 관리자 인증 및 role 기반 권한 검사 적용
* 관리자 프로젝트 이미지 관리 UI 존재
* 사이트 로고·Hero 이미지 관리 UI 존재
* DB에는 public URL이 아닌 Storage object path 저장
* 공개 렌더링 시 object path로부터 public URL 생성
* JPEG, PNG, WebP 형식 허용
* MIME type과 파일 signature 검증 적용
* SVG 등 허용하지 않은 형식 차단

이미 완료된 migration, bucket, RLS policy, 인증 구조, 원격 배포 script를 다시 구현하거나 되돌리지 마라.

이번 작업의 핵심 목표는 다음과 같다.

```text
파일 업로드
→ 파일 검증
→ 안전한 Storage 경로 생성
→ Storage 업로드
→ DB path 저장
→ 실패 시 보상 처리
→ 이전 object 정리
→ 최종 상태 검증
```

DB와 Storage는 동일한 트랜잭션에 포함되지 않으므로, 중간 단계 실패를 명시적으로 처리해야 한다.

2. DB 저장 실패 시 새로 업로드된 object가 정리되는가?
3. 이미지 교체 시 기존 object를 언제 삭제하는가?
4. 기존 object 삭제가 실패해도 새 이미지 저장은 성공 처리되는가?
5. 이미지 삭제 시 DB와 Storage 중 어느 쪽을 먼저 변경하는가?
6. 동일 요청이 두 번 실행되면 중복 object가 생성되는가?
7. 동일 파일명이 충돌할 가능성이 있는가?
8. 프로젝트 ID가 없는 상태에서 이미지 경로를 어떻게 만드는가?
9. 클라이언트가 object path를 조작할 수 있는가?
10. 다른 프로젝트의 이미지를 삭제할 가능성이 있는가?
11. 삭제 실패가 사용자에게 표시되는가?
12. 프로젝트 삭제 후 orphan object가 남을 수 있는가?
13. `site_settings` 이미지 path가 실제 Storage object와 일치하는가?
14. 최대 파일 크기와 해상도 제한이 실제로 적용되는가?
15. 공개 URL 생성 시 존재하지 않는 object path를 어떻게 처리하는가?

조사 없이 Storage 구조를 전면 교체하거나 별도 이미지 서비스를 도입하지 마라.

## 2. 이미지 작업의 상태 모델 정의

이미지 업로드·교체·삭제의 성공 조건과 실패 상태를 명확히 정의하라.

최소한 다음 상태를 구분하라.

```text
검증 실패
→ Storage와 DB 모두 변경 없음

Storage 업로드 실패
→ DB 변경 없음

Storage 업로드 성공 + DB 저장 성공
→ 정상 완료

Storage 업로드 성공 + DB 저장 실패
→ 새 object 삭제 보상 처리

새 object와 DB 저장 성공 + 기존 object 삭제 실패
→ 새 이미지 사용 유지
→ 기존 object를 orphan 후보로 기록 또는 보고

DB path 제거 성공 + object 삭제 성공
→ 정상 삭제

DB path 제거 성공 + object 삭제 실패
→ 공개 화면에서는 이미지 제거
→ object는 orphan 후보

object 삭제 성공 + DB path 제거 실패
→ DB가 존재하지 않는 object를 가리키는 위험 상태
→ 이 순서를 기본 흐름으로 사용하지 않음
```

이미지 교체와 삭제는 **사용자에게 보이는 DB 상태의 일관성**을 우선하면서, Storage 정리는 보상 처리와 별도 점검으로 보완하라.

## 3. 공통 Storage 이미지 서비스 계층 구축

프로젝트 이미지와 사이트 이미지 Server Action에 중복된 Storage 로직이 있다면 공통 서비스 계층으로 정리하라.

필요하다면 다음 책임을 분리하라.

* 파일 검증
* 이미지 metadata 추출
* 안전한 object path 생성
* Storage upload
* Storage remove
* object 존재 확인
* DB 저장 실패 시 upload rollback
* public URL 생성
* 기존 object 정리
* Storage 오류 정규화

예시 책임:

```text
validateImageFile()
createProjectThumbnailPath()
createSiteAssetPath()
uploadStorageObject()
removeStorageObject()
uploadWithRollback()
getPublicStorageUrl()
```

실제 함수명과 파일 위치는 기존 프로젝트 구조에 맞게 결정하라.

다음 조건을 만족해야 한다.

* 브라우저 client가 아니라 server client를 사용해 관리자 작업 수행
* 현재 로그인 사용자의 세션과 RLS를 유지
* service role key 사용 금지
* bucket 이름을 문자열로 여러 파일에 반복하지 않기
* path 규칙을 공통 상수 또는 함수로 관리
* 업로드·삭제 오류를 호출부가 구분할 수 있도록 구조화
* 실제 Supabase 오류 전체를 사용자에게 그대로 노출하지 않기
* 로그에 파일 내용, token, cookie를 기록하지 않기
* 프로젝트 이미지와 사이트 이미지의 허용 경로를 명확하게 분리

## 4. 안전한 object path 규칙

현재 object path 생성 방식을 조사하고 충돌과 경로 조작을 방지하라.

### 프로젝트 대표 이미지

다음 구조를 유지하거나 이에 준하는 안전한 구조를 사용하라.

```text
{projectId}/thumbnail/{uuid}.{extension}
```

요구사항:

* `projectId`는 DB에서 확인된 실제 프로젝트 ID 사용
* 클라이언트가 전달한 임의 path를 신뢰하지 않음
* 파일명은 UUID 또는 충분히 충돌 가능성이 낮은 랜덤 값 사용
* 원본 파일명은 object path에 직접 사용하지 않기
* 확장자는 검증된 MIME/signature 기준으로 결정
* 사용자 입력 확장자를 그대로 신뢰하지 않기
* `..`, `/`, `\`, null byte 등 path traversal 문자 차단
* 다른 projectId 경로의 object를 삭제하지 못하게 검증

### 사이트 이미지

다음 경로 구분을 유지하라.

```text
logo/{uuid}.{extension}
hero/{uuid}.{extension}
```

요구사항:

* logo action은 `logo/` 경로만 생성·삭제
* hero action은 `hero/` 경로만 생성·삭제
* 클라이언트가 bucket이나 prefix를 선택하지 못하게 함
* 기존 DB path 삭제 시에도 허용 prefix를 검증
* 허용되지 않은 path라면 삭제하지 말고 안전하게 실패 처리

## 5. 파일 검증 강화

현재 MIME type과 signature 검증을 유지하면서 다음 항목을 보완하라.

허용 형식:

* JPEG
* PNG
* WebP

차단 형식:

* SVG
* GIF
* BMP
* TIFF
* AVIF는 현재 지원 여부를 명시적으로 결정
* 실행 파일
* HTML
* XML
* MIME type만 이미지로 위장한 파일
* 확장자만 이미지인 파일

최소 검증:

1. 파일 존재 여부
2. 파일 크기가 0보다 큰지
3. 최대 파일 크기
4. MIME type
5. magic number 또는 file signature
6. 검증된 형식과 MIME type 일치
7. 이미지 decoding 가능 여부
8. 가로·세로 크기
9. 최대 pixel 수
10. 허용 확장자 결정

권장 제한값은 현재 UI 용도에 맞게 합리적으로 정하라.

예시:

```text
프로젝트 thumbnail
- 최대 5MB
- 최소 320×180
- 최대 4096×4096
- 최대 총 pixel 수 제한

사이트 logo
- 최대 2MB
- 최소 크기 과도하게 제한하지 않음
- 최대 2048×2048

Hero 이미지
- 최대 8MB
- 최소 1280×480
- 최대 6000×4000
```

위 값은 예시이므로 기존 디자인과 실제 사용 환경을 조사한 뒤 결정하라.

다음 사항도 고려하라.

* 지나치게 큰 해상도의 압축 이미지로 인한 메모리 사용
* 이미지 decode 과정의 예외
* 서버 환경에서 사용 가능한 이미지 metadata 라이브러리
* 새 dependency가 필요한 경우 유지보수성과 bundle 영향
* Next.js 서버 런타임과 호환성
* Edge runtime에서 동작하지 않는 라이브러리 사용 여부

새 라이브러리를 도입한다면 이유와 대안을 설명하라.

## 6. 프로젝트 이미지 업로드 보상 처리

프로젝트 대표 이미지 업로드 흐름을 다음 순서로 보완하라.

```text
1. requireContentManager()
2. 프로젝트 존재 여부 확인
3. 파일 검증
4. 새 object path 생성
5. Storage upload
6. projects.thumbnail_path 저장
7. DB 저장 실패 시 새 object 삭제
8. 성공 시 revalidate
```

DB 저장 실패 후 rollback 삭제도 실패한 경우:

* 원래 DB 상태는 유지
* 사용자에게 업로드 실패를 알림
* 새 object path를 서버 로그에 안전하게 기록
* 해당 object를 orphan 후보로 식별 가능하게 함
* 실패를 성공으로 처리하지 않음

rollback 삭제 실패를 숨기지 말되, 사용자에게 내부 path 전체나 Supabase 상세 오류를 노출하지 마라.

## 7. 프로젝트 이미지 교체 정합성

프로젝트 이미지 교체는 다음 순서를 기본으로 하라.

```text
1. 현재 프로젝트와 기존 thumbnail path 조회
2. 새 파일 검증
3. 새 object 업로드
4. DB path를 새 object path로 변경
5. DB 변경 실패 시 새 object rollback 삭제
6. DB 변경 성공 후 기존 object 삭제 시도
7. 기존 object 삭제 실패 시 새 이미지 상태는 유지
8. 삭제 실패 object를 orphan 후보로 기록
```

다음 방식은 피하라.

```text
기존 object 먼저 삭제
→ 새 upload 또는 DB 저장 실패
→ 프로젝트 이미지가 사라짐
```

동시 요청도 고려하라.

예:

```text
교체 요청 A와 B가 동시에 실행
→ 마지막 DB update가 승리
→ 사용되지 않는 object가 남을 수 있음
```

이를 완전히 직렬화하기 어렵다면 다음을 적용하라.

* DB update 조건에 기존 path를 포함하는 optimistic concurrency 검토
* update 결과 row 수 확인
* 경쟁 상태 발생 시 새 object rollback
* 최종 DB path가 어떤 object인지 확인
* orphan 정리 도구로 잔여 object 처리

복잡한 lock을 무리하게 도입하지 말고 현재 규모에 맞는 안전한 방식을 선택하라.

## 8. 프로젝트 이미지 삭제 정합성

이미지 삭제는 다음 순서를 검토하라.

권장 흐름:

```text
1. 현재 프로젝트와 thumbnail path 조회
2. DB thumbnail_path를 null로 변경
3. DB 변경 성공 후 Storage object 삭제
4. Storage 삭제 실패 시 DB는 null 유지
5. 삭제 실패 object는 orphan 후보
```

이 방식의 장점:

* 공개 페이지가 존재하지 않는 object를 계속 가리키지 않음
* 삭제 실패 object는 사용자에게 노출되지 않음
* 후속 orphan 정리 가능

다음 사항을 처리하라.

* 이미 path가 null인 경우 idempotent 성공
* object가 이미 없는 경우 정상 정리로 취급 가능
* Storage 권한 오류는 별도 실패로 기록
* DB update 실패 시 object 삭제하지 않음
* 다른 프로젝트 path 삭제 차단
* 삭제 action 중복 실행 안전성
* 성공 후 관리자·공개 페이지 revalidation

## 9. 프로젝트 삭제 시 이미지 정리

프로젝트 삭제와 대표 이미지 삭제의 관계를 조사하고 다음 정책을 적용하라.

권장 흐름:

```text
1. requireContentManager()
2. 프로젝트와 thumbnail path 조회
3. 프로젝트 DB 삭제
4. DB 삭제 성공 후 Storage object 삭제
5. Storage 삭제 실패 시 프로젝트 삭제는 유지
6. 실패 object는 orphan 후보
```

다음 사항을 확인하라.

* child table cascade 또는 선행 삭제
* 프로젝트 삭제 실패 시 object를 삭제하지 않음
* 프로젝트 삭제 성공 후 Storage 실패를 어떻게 보고할지
* 삭제된 프로젝트의 image path를 orphan 검사에서 식별할 수 있는지
* 프로젝트 삭제 action의 재실행 안전성
* 이미 삭제된 프로젝트 처리

Storage 삭제 실패 때문에 DB 프로젝트 삭제 전체를 되돌리는 복잡한 보상 트랜잭션은 기본적으로 피하라. 대신 orphan 정리 체계를 제공하라.

## 10. 사이트 로고·Hero 이미지 흐름 보완

```text
1. requireContentManager()

6. 해당 DB path 저장
```


* 삭제 후 기본 fallback UI 정상 표시

## 11. orphan object 점검 도구 구축

DB에서 참조되지 않는 Storage object를 찾을 수 있는 점검 도구를 추가하라.

대상:

* `project-images`
* `site-assets`

### 프로젝트 이미지 orphan 판정

다음 조건을 만족하는 object:

```text
project-images bucket에 존재
AND
projects.thumbnail_path에서 참조되지 않음
```

### 사이트 이미지 orphan 판정

다음 조건을 만족하는 object:

```text
site-assets bucket에 존재
AND
site_settings.logo_path 또는 hero_image_path에서 참조되지 않음
```

다음 형태의 script 또는 SQL 점검 도구를 검토하라.

```text
storage:orphans:check
storage:orphans:cleanup
```

요구사항:

* 기본 명령은 read-only
* orphan 후보 목록과 개수 출력
* bucket, path, 생성 시각, 크기 출력 가능
* 실제 삭제는 명시적인 옵션 필요
* dry-run 기본값
* 운영 환경에서는 확인 없이 자동 삭제 금지
* 특정 최소 경과 시간보다 최근 object는 기본 제외
* 업로드 진행 중 object 오삭제 방지
* 허용 prefix 밖의 object는 별도 경고
* DB가 참조하는 object는 절대 삭제하지 않음
* 삭제 전 최종 참조 여부 재확인

예:

```text
pnpm run storage:orphans:check
pnpm run storage:orphans:cleanup -- --dry-run
pnpm run storage:orphans:cleanup -- --apply
```

실제 script 이름은 기존 명명 규칙에 맞게 결정하라.

service role key 없이 linked CLI 또는 SQL 기반으로 수행할 수 있는 방식을 우선하라.

관리 API 권한이 꼭 필요하다면 앱의 일반 환경 변수와 분리하고, 이번 작업에서 secret을 저장하지 마라.

## 12. dangling DB path 점검

Storage에 존재하지 않는 object를 DB가 가리키는 상태도 점검하라.

대상:

* `projects.thumbnail_path`
* `site_settings.logo_path`
* `site_settings.hero_image_path`

다음 상태를 출력하라.

```text
DB path 있음
AND
해당 bucket object 없음
→ dangling reference
```

점검 도구는 기본적으로 read-only로 구성하라.

자동 수정은 기본적으로 수행하지 마라.

필요하다면 다음 옵션을 제공할 수 있다.

* dangling project thumbnail을 null로 변경
* dangling logo/hero path를 null로 변경

단, 운영 데이터 변경은 명시적인 `--apply` 옵션과 사전 출력이 있어야 한다.

## 13. Storage path 정합성 검사

DB에 저장된 path가 허용 규칙을 따르는지 검사하라.

프로젝트 이미지:

```text
{projectId}/thumbnail/{uuid}.{ext}
```

사이트 로고:

```text
logo/{uuid}.{ext}
```

사이트 Hero:

```text
hero/{uuid}.{ext}
```

다음 상태를 찾아라.

* 다른 projectId 경로 참조
* 잘못된 prefix
* public URL 전체가 DB에 저장된 경우
* bucket 이름이 path에 포함된 경우
* `..` 또는 역슬래시 포함
* 허용되지 않은 확장자
* 빈 문자열
* 공백 문자열
* 중복 참조
* 하나의 object를 여러 프로젝트가 참조

점검 결과는 migration을 자동 생성하기보다 운영자가 확인할 수 있는 보고 형태를 우선하라.

## 14. Storage 오류 분류 및 사용자 메시지

Supabase Storage 오류를 사용자에게 그대로 노출하지 말고 의미 있는 상태로 분류하라.

예시 오류 코드:

```text
INVALID_FILE
FILE_TOO_LARGE
INVALID_IMAGE_FORMAT
INVALID_IMAGE_DIMENSIONS
UPLOAD_FAILED
DATABASE_UPDATE_FAILED
ROLLBACK_FAILED
DELETE_FAILED
CONFLICT
UNAUTHORIZED
NOT_FOUND
```

사용자에게는 다음처럼 이해 가능한 메시지를 표시하라.

* 지원하지 않는 이미지 형식입니다.
* 파일 크기가 제한을 초과했습니다.
* 이미지 해상도가 허용 범위를 벗어났습니다.
* 이미지 업로드에 실패했습니다.
* 이미지 저장 중 문제가 발생했습니다.
* 기존 이미지 정리에 실패했지만 새 이미지는 저장되었습니다.
* 권한이 없습니다.
* 대상 프로젝트를 찾을 수 없습니다.

내부 로그에는 action 이름과 단계 정도를 기록하되 다음은 금지한다.

* access token
* refresh token
* cookie 전체
* service role key
* 파일 원본 내용
* 관리자 비밀번호
* Supabase key 전체
* 사용자의 로컬 전체 파일 경로

## 16. 이미지 공개 URL 처리 검토

DB에는 object path만 저장하는 현재 원칙을 유지하라.

다음 사항을 검증하라.

* mapper에서 bucket과 path를 조합해 public URL 생성
* path가 null이면 URL도 null
* 빈 문자열은 null로 정규화
* 이미 public URL인 값이 들어온 경우 안전 처리
* 잘못된 path로 public URL 생성하지 않기
* Supabase Project URL이 바뀌어도 DB 데이터를 수정할 필요 없음
* 공개 URL 생성 함수 중복 제거
* Server·Client 환경에서 동일한 결과
* `next/image` remote pattern과 일치
* 존재하지 않는 object는 브라우저에서 깨진 이미지가 될 수 있음을 고려
* 적절한 fallback 이미지 또는 UI 제공

public URL 존재 여부를 매 공개 페이지 요청마다 Storage API로 확인해 성능을 저하시키지 마라. 정합성 문제는 점검 도구로 해결하라.

## 23. 검증

작업 완료 후 프로젝트의 실제 script를 확인한 뒤 최소한 다음 검증을 수행하라.

```powershell
pnpm.cmd lint
pnpm.cmd exec tsc --noEmit
pnpm.cmd build
pnpm.cmd supabase db reset
pnpm.cmd supabase test db
pnpm.cmd run test:env
pnpm.cmd run test:supabase
```

이번 작업에서 Storage 관련 test script를 추가했다면 함께 실행하라.

예:

```powershell
pnpm.cmd run test:storage
pnpm.cmd run storage:orphans:check
pnpm.cmd run storage:dangling:check
pnpm.cmd run storage:paths:check
```

실제 script 이름은 구현 결과에 맞게 사용하라.

다음 실패 시나리오를 자동 또는 수동으로 검증하라.

```text
파일 검증 실패
→ Storage와 DB 변경 없음

Storage upload 실패
→ DB 변경 없음

Storage upload 성공 + DB 실패
→ 새 object rollback

교체 성공 + 기존 object 삭제 실패
→ 새 이미지 유지
→ orphan 후보 보고

삭제 DB 성공 + Storage 실패
→ 공개 path 제거 유지
→ orphan 후보 보고
```

원격 Supabase에 실제 테스트 이미지를 올리지 못했다면 다음을 구분해서 보고하라.

* 단위 테스트로 검증한 항목
* local Supabase로 검증한 항목
* 원격 환경에서 read-only로 검증한 항목
* 실제 브라우저 수동 검증이 필요한 항목

운영 이미지나 운영 콘텐츠를 테스트 목적으로 삭제하지 마라.

## 24. 최종 보고 형식

작업이 끝나면 다음 순서로 결과를 보고하라.

### 1. 기존 이미지 관리 구조 분석

* bucket 구성
* object path 구성
* 업로드·교체·삭제 순서
* 파일 검증
* public URL 생성
* 발견한 정합성 위험

### 2. 최종 이미지 처리 흐름

다음 기능별로 순서를 작성하라.

* 프로젝트 이미지 업로드
* 프로젝트 이미지 교체
* 프로젝트 이미지 삭제
* 프로젝트 삭제
* 로고 업로드·교체·삭제
* Hero 업로드·교체·삭제

### 3. 실패 및 보상 처리

다음 표 형식으로 정리하라.

```text
실패 단계 | DB 상태 | Storage 상태 | 보상 처리 | 사용자 결과
```

### 4. 파일 제한

다음 표 형식으로 작성하라.

```text
용도 | 허용 형식 | 최대 크기 | 최소 해상도 | 최대 해상도
```

### 5. object path 규칙

다음 표 형식으로 작성하라.

```text
용도 | bucket | prefix | path 예시
```

실제 운영 object path나 UUID는 노출하지 마라.

### 6. 변경 파일 목록

각 파일에 대해 다음 형식으로 작성하라.

```text
파일 경로
- 변경 목적
- 핵심 변경 내용
```

### 7. orphan·dangling 점검 기능

* 추가한 script
* 기본 동작
* dry-run 여부
* 삭제 안전장치
* 실제 원격 실행 여부

### 8. 권한 검증 결과

다음 표 형식으로 작성하라.

```text
역할 | project-images write | site-assets write | 결과
```

### 9. 테스트 결과

실제로 실행한 명령과 성공·실패 결과를 정확히 작성하라.

DB 테스트와 Storage 테스트 개수가 출력된다면 함께 작성하라.

### 10. 수동 검증 결과

* 프로젝트 이미지
* 로고
* Hero 이미지
* 중복 제출
* 잘못된 파일
* 권한별 접근
* rollback 시나리오

실제로 확인하지 않은 항목은 확인했다고 표현하지 마라.

### 11. 남은 위험 요소

* 완전히 제거할 수 없는 동시성 문제
* cleanup 운영 절차 의존성
* 브라우저 기반 E2E 미구현
* 이미지 최적화 또는 리사이징 미구현
* audit log 미구현
* 장기 Storage 용량 모니터링 미구현

### 12. 다음 작업

이번 프롬프트 범위를 넘어 다음 프롬프트에서 처리할 항목만 작성하라.

* 관리자 UI와 데이터 무결성 보완
* Playwright E2E
* CI/CD
* Vercel Preview·Production 배포 검증
* 운영 오류 추적 및 모니터링

오류, rollback 실패, orphan object 또는 미검증 항목이 남아 있다면 성공한 것처럼 표현하지 말고 정확한 상태와 재현 방법을 작성하라.

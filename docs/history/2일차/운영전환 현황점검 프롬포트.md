# DotG 웹사이트 출시단계 진입 전 현황 점검

현재 DotG 웹사이트는 다음 개발 단계를 완료한 상태라고 보고되어 있다.

1. 기본구조
2. 구현단계
3. 운영전환

다음 단계인 **출시단계**에 들어가기 전에 현재 워크스페이스 전체를 직접 조사하여 실제 코드와 설정이 어느 상태인지 다시 점검하라.

이번 작업의 목적은 새로운 기능을 구현하거나 코드를 수정하는 것이 아니다.

**현재 저장소 상태를 조사하고, 출시단계에서 해야 할 작업의 정확한 출발점을 확정하는 것**이 목적이다.

---

# 0. 작업 원칙

다음 규칙을 반드시 지켜라.

* 이번 작업에서는 소스 코드를 수정하지 않는다.
* migration을 새로 만들지 않는다.
* package를 설치하거나 업데이트하지 않는다.
* 실제 Production 배포를 수행하지 않는다.
* 실제 원격 DB에 destructive operation을 수행하지 않는다.
* Git commit/push를 수행하지 않는다.
* 발견한 문제를 임의로 고치지 않는다.
* "기존에 구현되어 있을 것이다"라고 추측하지 말고 실제 파일과 설정을 확인한다.
* 문서에 적힌 내용보다 현재 코드와 설정을 우선한다.
* 로컬에서 안전하게 실행 가능한 read-only 또는 검증 명령은 직접 실행한다.
* secret, access token, API key의 실제 값을 결과에 출력하지 않는다.
* `.env*`, GitHub Actions, Supabase, Vercel 관련 설정에서 secret의 존재 여부는 확인하되 값은 기록하지 않는다.
* 원격 서비스 접근 정보가 없으면 실패로 판정하지 말고 `외부 설정 필요`로 구분한다.

이번 작업으로 변경 파일이 생기면 안 된다.

작업 전후에 반드시 다음을 확인한다.

```powershell
git status --short
```

검증 명령 때문에 자동 생성 파일이 변경될 경우 해당 변경이 무엇인지 보고하고, 사용자 코드에는 손대지 마라.

# 6. RLS 및 권한 체계 점검

모든 public table의 RLS 상태를 migration과 테스트 기준으로 조사하라.

```text

member
editor
admin
```

각 역할에 대해 실제 가능한 동작을 표로 작성한다.

예:

| 기능          | anon | member | editor | admin |
| ----------- | ---- | ------ | ------ | ----- |
| 공개 프로젝트 조회  |      |        |        |       |
| 관리자 페이지 접근  |      |        |        |       |
| 프로젝트 생성     |      |        |        |       |

추측으로 작성하지 말고 실제 policy와 application authorization을 모두 확인하라.

다음 보안 항목도 확인한다.

* profile self-promotion 차단

현재 존재하는 주요 운영 문서를 목록화하고 각각의 목적을 한 줄로 설명한다.

특히 다음 계열을 확인한다.

* DB schema
* authentication
* project management
* notice management
* recruitment management
* site settings
* storage
* environment
* remote deployment
* production runbook
* release checklist
* release readiness

문서가 현재 구현과 어긋나는 부분이 있다면 수정하지 말고 별도로 기록한다.

# 22. 출시 Blocking Issue 판정

조사 결과를 바탕으로 문제를 다음 등급으로 분류하라.

## BLOCKER

출시단계에 들어가기 전에 반드시 수정해야 하는 코드/구조 문제.

예:

* build 실패
* migration 충돌
* RLS 누락
* production에서 mock fallback
* 인증 우회
* secret 노출

## HIGH

출시 전에 반드시 해결해야 하지만 출시단계 작업 안에서 처리할 수 있는 문제.

## MEDIUM

출시 전에 처리하는 것이 권장되는 문제.

## LOW

출시 후 고도화 단계에서도 처리 가능한 문제.

문제가 없다면 억지로 만들지 않는다.

# 23. 출시 준비도 판정

최종적으로 다음 중 하나로 현재 상태를 판정하라.

```text
NOT READY
PARTIALLY READY
READY FOR RELEASE STAGE
```

의미는 다음과 같다.

### NOT READY

운영전환 구현 자체에 중요한 미완성 또는 실패가 있어 출시단계 이전에 추가 개발이 필요하다.

### PARTIALLY READY

주요 구현은 끝났지만 코드 또는 자동 검증에 해결할 문제가 남아 있다.

### READY FOR RELEASE STAGE

코드/로컬/CI 관점에서는 출시단계로 넘어갈 수 있으며, 남은 작업의 핵심이 실제 Supabase/Vercel/GitHub/도메인 환경 구축과 실환경 검증이다.

주의:

`READY FOR RELEASE STAGE`는 실제 서비스 출시 완료라는 뜻이 아니다.

# 25. 마지막 확인

작업 종료 직전에 다시 실행한다.

```powershell
git status --short
```

이번 점검으로 의도하지 않은 소스 코드 변경이 발생하지 않았는지 확인한다.

최종 보고서 마지막에 반드시 다음을 포함한다.

```text
점검 과정에서 수정한 소스 코드: 없음
```

실제로 파일이 변경되었다면 거짓으로 `없음`이라고 하지 말고 어떤 파일이 왜 변경됐는지 정확히 보고한다.

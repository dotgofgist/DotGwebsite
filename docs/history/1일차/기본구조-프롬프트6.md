현재 작업 중인 저장소는 게임창작부 동아리 웹사이트 프로젝트다.

이번 작업은 7단계 중 **프롬프트 6: 관리자용 콘텐츠 관리 서브 사이트 UI 구현**에 해당한다.

이전 단계에서 다음 작업이 완료되었다고 가정한다.

* Next.js App Router 기반 공개 및 관리자 라우팅 골격
* 공개 사이트 Header와 Footer
* 모바일 내비게이션
* 공통 UI 컴포넌트
* 메인 페이지
* 동아리 소개와 연락처
* 프로젝트 타입, 임시 데이터, 목록 및 상세
* 공지사항 타입, 임시 데이터, 목록 및 상세
* 모집 정보 타입, 임시 데이터, 모집 안내
* 메인 페이지와 각 기능 데이터 연동
* 관리자 경로의 임시 페이지

기존 파일을 먼저 읽고 실제 구현 상태에 맞춰 필요한 부분만 수정하라.

프로젝트 전체를 재생성하거나 기존 공개 사이트 구조를 전면 교체하지 마라.

# 1. 작업 목표

관리자가 콘텐츠를 관리할 수 있는 서브 사이트의 UI 골격을 구현한다.

이번 단계에서 구현할 항목은 다음과 같다.

1. 관리자 로그인 화면
2. 관리자 대시보드 공통 레이아웃
3. 관리자 Header
4. 관리자 Sidebar
5. 모바일 관리자 메뉴
6. 관리자 대시보드 홈
7. 프로젝트 관리 목록
8. 프로젝트 생성 폼 UI
9. 프로젝트 수정 폼 UI
10. 공지사항 관리 목록
11. 공지사항 생성 폼 UI
12. 공지사항 수정 폼 UI
13. 모집 정보 관리 UI
14. 사이트 기본 정보 관리 UI
15. 연락처 및 SNS 설정 UI
16. 삭제 확인 UI 골격
17. 관리자 페이지 모바일 대응
18. 기존 mock data 재사용
19. 접근 가능한 관리자 내비게이션과 폼

이번 단계에서는 실제 데이터 저장, 수정, 삭제를 수행하지 않는다.

Supabase Auth, DB CRUD, Storage는 다음 단계에서 연결한다.

## 요구사항

* 시맨틱 `<aside>` 또는 `<nav>`를 사용한다.
* 메뉴는 `src/config/navigation.ts`에서 가져온다.
* 현재 경로에 따라 활성 메뉴를 표시한다.
* `/admin/projects/new`와 `/admin/projects/[id]/edit`에서도 프로젝트 관리 메뉴가 활성화되어야 한다.
* `/admin/notices/new`와 수정 페이지에서도 공지사항 관리 메뉴가 활성화되어야 한다.
* `/admin`은 정확히 `/admin`에서만 활성화한다.
* 활성 링크에는 `aria-current="page"`를 적용한다.
* 충분한 클릭 영역을 제공한다.
* focus-visible 상태를 유지한다.
* 아이콘 패키지를 설치하지 않는다.
* 텍스트, 간단한 inline SVG 또는 CSS 장식을 사용한다.

현재 경로 판별이 필요하므로 Sidebar 전체 또는 메뉴 부분은 Client Component일 수 있다.

Client Component 범위를 최소화하라.


삭제 버튼 UI를 위해 재사용할 수 있는 확인 인터페이스를 만든다.

다만 외부 Modal 라이브러리는 사용하지 않는다.

이번 단계에서는 다음 중 더 단순한 방식을 선택한다.

## 선택지 A: 인라인 확인 영역

* 삭제 버튼을 누르면 같은 행 또는 카드 내부에 확인 영역 표시
* 취소 및 확인 버튼 제공
* 실제 삭제는 수행하지 않음

## 선택지 B: 네이티브 `<dialog>`

* 브라우저 네이티브 dialog 사용
* 최소한의 Client Component 구현
* 접근성 속성 확인
* 실제 삭제는 수행하지 않음

복잡한 커스텀 Modal을 직접 구현하지 마라.

권장 props:

```ts
type ConfirmDialogProps = {
  triggerLabel: string;
  title: string;
  description: string;
  confirmLabel?: string;
  onConfirm?: () => void;
};
```

# 35. 관리자 경로 활성 표시

관리자 Sidebar와 모바일 메뉴는 다음 규칙으로 활성 경로를 표시한다.

```ts
function isAdminNavigationItemActive(
  pathname: string,
  href: string,
): boolean {
  if (href === "/admin") {
    return pathname === "/admin";
  }

  return pathname === href || pathname.startsWith(`${href}/`);
}
```

`/admin/login`에서는 관리자 Sidebar 자체가 표시되지 않는다.

# 37. 디자인 기준

* 고정 또는 안정적인 Sidebar
* 명확한 페이지 제목
* 카드 기반 대시보드
* 폼 필드 간 충분한 간격

* 모바일에서는 단일 열 우선
* 과도한 애니메이션 금지
* 과도한 그라데이션 금지
* 지나치게 작은 글자 금지

```text
--danger
--danger-foreground
--muted
--muted-foreground
```

기존 변수 구조와 충돌하지 않게 하라.

색상값을 여러 파일에 반복 하드코딩하지 마라.

# 38. 반응형 요구사항

최소 너비 360px에서 관리자 기능을 사용할 수 있어야 한다.

## 레이아웃

* Sidebar는 데스크톱에서 표시
* 모바일에서는 메뉴 버튼으로 전환
* 콘텐츠가 Sidebar 아래에 가려지지 않음
* Header 내용이 작은 화면에서 겹치지 않음
* 긴 페이지 제목이 줄바꿈 가능
* 액션 버튼이 모바일에서 아래로 내려갈 수 있음

## 표와 목록

* 모바일에서 가로 스크롤 또는 카드형 UI 제공
* 삭제 및 수정 버튼이 화면 밖으로 나가지 않음
* 긴 제목과 slug가 줄바꿈됨
* 관리 액션의 클릭 영역이 충분함

## 폼

* 모든 입력은 모바일에서 가로폭 100%
* 2열 필드는 모바일에서 1열로 전환
* 긴 설명과 label이 겹치지 않음
* 버튼 그룹은 모바일에서 세로 배치 가능
* textarea가 화면 밖으로 넘치지 않음
* 고정 픽셀 너비를 남용하지 않음

# 40. 접근성 요구사항

## 관리자 내비게이션

* Sidebar에 의미 있는 nav label
* 활성 링크에 `aria-current="page"`
* 모바일 메뉴 버튼에 `aria-expanded`
* 모바일 메뉴에 `aria-controls`
* Escape 키 닫기
* focus-visible 표시

## 폼

* 모든 입력에 연결된 label
* 필수 필드에 `required`
* 설명 문구는 `aria-describedby`로 연결 가능
* 비활성 버튼의 이유를 텍스트로 전달
* placeholder만으로 label을 대체하지 않음
* 입력 순서가 논리적이어야 함

## 표

* 실제 table 사용 시 `<thead>`, `<tbody>`, `<th scope="col">`
* 모바일 카드형 목록도 정보 관계가 명확해야 함
* 관리 버튼 이름에 대상 제목을 포함하거나 accessible label 제공

예:

```text
Project Aurora 수정
Project Aurora 삭제
```

## 삭제 확인

* 삭제 대상이 문구에 포함되어야 함
* 확인과 취소 버튼을 구분
* 위험 동작을 색상만으로 표현하지 않음
* 실제 삭제되지 않는다는 안내 제공

## 일반

* 페이지마다 하나의 `<h1>`
* heading 순서 유지
* 색상 대비 확보
* 키보드 focus 제거 금지
* 빈 링크 금지
* `href="#"` 금지

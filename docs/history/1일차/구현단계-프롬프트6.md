# 3. 모집 관리 정책

모집 정보는 여러 개 저장할 수 있다.

예:

```text
2026년 1학기 신규 부원 모집
2026년 여름 프로젝트 팀원 모집
2026년 2학기 신규 부원 모집
```

이 중 공개 사이트의 `/recruitment`와 메인 페이지 CTA에 표시할 모집 정보는 최대 1개다.

해당 모집 정보는 다음 값으로 구분한다.

```text
is_current = true
```

공개 페이지에 실제로 표시되려면 다음 조건을 모두 만족해야 한다.

```text
is_current = true
publication_status = published
```

다음 상태는 현재 모집으로 지정할 수 없다.

```text
publication_status = archived
```

`draft` 상태를 현재 모집으로 지정할 수 있는지는 다음 정책을 적용한다.

```text
draft + is_current = true
→ 관리자 내부에서 현재 모집으로 준비 가능
→ 공개 페이지에는 표시되지 않음

published + is_current = true
→ 공개 모집 페이지와 메인 CTA에 표시

archived
→ 현재 모집 지정 불가
```

# 4. 권한 정책

모집 정보 관리 권한은 다음 역할에만 허용한다.

```text
editor
admin
```

다음 역할에는 허용하지 않는다.

```text
anon
authenticated member
```

권한 검사는 다음 세 계층에서 적용한다.

```text
관리자 Dashboard Layout
→ 관리자 페이지 접근 보호

모집 query 및 Server Action
→ 서버 함수 재사용 시 권한 재검사

Supabase RLS
→ 실제 DB SELECT·INSERT·UPDATE 강제
```

관리자 Layout을 통과했다는 이유만으로 Server Action의 권한 검사를 생략하지 마라.

Service Role Key로 RLS를 우회하지 마라.

# 36. 모집 생성 처리

새 모집 생성 시:

```text

updated_at
created_by
updated_by
published_at
```

정책:

* id는 DB에서 UUID 생성
* created_by = auth.uid()
* updated_by = auth.uid()
* is_current = false
* 처음부터 published이면 published_at = now()
* draft면 published_at = NULL 또는 기존 정책에 따름

# 37. 모집 수정 처리

기존 모집 수정 시:

* id로 기존 row 확인
* 존재하지 않으면 예외
* created_by와 created_at 유지
* updated_by = auth.uid()
* updated_at trigger 적용
* 기존 is_current 값 유지
* publication status가 archived로 바뀌면 is_current를 false로 변경
* published_at 정책 적용
* 절차 전체 교체
* 본문과 절차가 같은 transaction 안에서 저장

# 38. publishedAt 정책

권장 정책:

```text
draft 또는 archived → 처음 published
→ published_at = now()

이미 published_at이 있는 모집 수정
→ 기존 published_at 유지

published → draft
→ 기존 published_at 유지

published → archived
→ 기존 published_at 유지
→ is_current = false

archived → published
→ 기존 published_at이 있으면 유지
```

다른 정책을 선택했다면 문서와 완료 보고에 작성한다.

# 39. 현재 모집 지정 RPC

같은 migration에 다음 함수를 구현한다.

```text
public.set_current_recruitment()
```

입력:

```text
p_recruitment_id uuid
```

동작:

1. `can_manage_content()` 검사
2. 대상 모집 존재 확인
3. 대상이 archived인지 확인
4. 기존 `is_current = true` row를 모두 false로 변경
5. 대상 row를 `is_current = true`로 변경
6. `updated_by = auth.uid()`
7. 대상 UUID 반환

모든 변경은 하나의 transaction 안에서 처리한다.

# 40. 현재 모집 지정 해제 RPC

필요하면 다음 함수를 구현한다.

```text
public.unset_current_recruitment()
```

입력:

```text
p_recruitment_id uuid
```

동작:

* 권한 검사
* 해당 row가 현재 모집인지 확인
* `is_current = false`
* `updated_by = auth.uid()`
* 다른 모집을 자동으로 현재 모집으로 지정하지 않음

현재 모집이 0개인 상태를 허용한다.

공개 모집 페이지는 이 경우 정상적인 빈 상태를 표시한다.

# 41. 현재 모집 동시성

두 명의 관리자가 동시에 서로 다른 모집을 현재 모집으로 지정하더라도 다음 조건을 지켜야 한다.

```text
is_current = true인 row 최대 1개
```

partial unique index가 최종 방어 역할을 해야 한다.

RPC는 다음 순서를 transaction 안에서 수행한다.

```text
기존 current 해제
→ 새 current 지정
```

unique violation이 발생하면 사용자 친화적 오류로 변환한다.

RLS나 unique index를 제거해 문제를 우회하지 마라.

생성된 타입을 수동으로 축약하거나 가짜 타입으로 작성하지 마라.

Docker를 사용할 수 없다면:

* migration 작성
* SQL 정적 검토
* 타입 미생성 상태 보고
* `any`로 우회하지 않음

* 입력 검증

# 69. DB constraint 점검

# 85. 최종 완료 기준

다음 조건을 모두 만족하면 이번 작업을 완료한 것으로 본다.

* 관리자 모집 목록이 실제 Supabase 데이터를 사용한다.
* 관리자 모집 수정 페이지가 실제 Supabase 데이터를 사용한다.
* 관리자 모집 mock query가 더 이상 관리자 UI에서 사용되지 않는다.
* 모집 정보 생성이 실제 DB에 저장된다.
* 모집 정보 수정이 실제 DB에 저장된다.
* 모집 절차가 실제 DB에 저장된다.
* 모집 정보와 절차가 원자적으로 저장된다.
* 모집 절차 수정 시 기존 절차가 정확히 교체된다.
* 모든 query와 mutation에서 관리자 권한을 재검사한다.
* anon과 member는 모집 정보를 수정할 수 없다.
* editor와 admin은 모집 정보를 관리할 수 있다.
* created_by와 updated_by가 현재 Auth 사용자로 기록된다.
* 제목, 요약, 상태, 일정, 목록, URL, 절차가 서버에서 검증된다.
* 위험한 URL protocol이 차단된다.
* 새 모집은 기본적으로 draft이며 current가 아니다.
* 처음 공개 시 published_at이 설정된다.
* current 모집은 최대 1개만 존재한다.
* 현재 모집 지정이 transaction으로 처리된다.
* 현재 모집 지정 해제가 동작한다.
* archived 모집은 current로 지정할 수 없다.
* archive 시 current가 해제된다.
* 영구 삭제는 구현하지 않는다.
* current + published 모집만 공개 페이지에 표시된다.
* current + draft 모집은 공개되지 않는다.
* current가 없으면 공개 모집 페이지가 빈 상태를 표시한다.
* 모집 변경이 메인 페이지 CTA에 반영된다.

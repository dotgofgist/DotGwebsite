# 구현단계 작업 결과 요약

## 개요

구현단계에서는 DotG 웹사이트를 기존 mock 중심 구조에서 Supabase 기반의 공개 조회, 관리자 인증, 관리자 CRUD, Storage 이미지 관리 흐름으로 전환했다. 작업은 프롬프트 1부터 8까지 순차적으로 진행했으며, 최종적으로 프로젝트, 공지사항, 모집 정보, 사이트 설정, 연락처, SNS 링크, 이미지 자산 관리까지 Supabase와 연결했다.

커밋은 각 단계에서 만들지 않았다.

## 프롬프트별 결과

### 1. Supabase DB 기반 구축

- Supabase local 개발 구성을 추가했다.
- 초기 콘텐츠 스키마 migration을 작성했다.
- 주요 테이블을 생성했다.
  - `profiles`
  - `projects`, `project_members`, `project_links`
  - `notices`
  - `recruitments`, `recruitment_steps`
  - `site_settings`
  - `contact_items`
  - `social_links`
- 주요 enum을 정의했다.
  - `content_status`
  - `project_status`
  - `project_link_type`
  - `recruitment_status`
  - `user_role`
- public schema 전체에 RLS를 적용했다.
- `anon`, `authenticated member`, `editor`, `admin` 역할별 읽기/쓰기 경계를 설계했다.
- seed 데이터를 추가했다.
- 초기 DB 테스트와 RLS 테스트를 추가했다.
- `docs/database-schema.md`와 README에 Supabase 로컬 개발 절차를 문서화했다.

### 2. 공개 페이지 Supabase 조회 전환 준비

- 공개 페이지 query를 async 구조로 전환했다.
- Supabase 환경 변수가 없으면 기존 mock/config fallback을 유지하도록 정리했다.
- Supabase 환경 변수가 있으면 조회 실패를 조용히 mock으로 숨기지 않고 명확한 오류로 처리하도록 방향을 잡았다.
- 공개 프로젝트, 공지사항, 모집, 설정 관련 query 계층을 분리했다.
- 공개 route에 loading/error boundary를 추가했다.
- 관리자 query는 이후 CRUD 단계에서 교체하기 쉽도록 `admin-queries.ts` 경로를 마련했다.

### 3. Supabase Auth 관리자 인증

- Supabase email/password 기반 관리자 로그인 흐름을 추가했다.
- 로그인/로그아웃 Server Action을 구현했다.
- 로그인 입력값 검증과 안전한 `next` redirect 검증을 추가했다.
- `/admin` 보호 proxy를 추가했다.
- 관리자 dashboard layout에서 `requireContentManager()`로 권한을 재검사하도록 연결했다.
- `editor`, `admin`만 관리자 화면 접근이 가능하도록 했다.
- `/admin/unauthorized` 페이지를 추가했다.
- 관리자 Header에 로그인한 관리자 정보와 로그아웃 흐름을 연결했다.
- `docs/authentication.md`를 추가했다.

### 4. 관리자 프로젝트 Supabase CRUD

- 로컬 Supabase 실행, `db reset`, 타입 생성까지 완료해 실제 `database.types.ts`를 생성했다.
- 관리자 프로젝트 목록/상세 query를 mock에서 Supabase 조회로 전환했다.
- 프로젝트 mapper를 추가했다.
- 프로젝트 생성/수정/삭제 Server Action을 추가했다.
- 모든 mutation에서 `requireContentManager()`를 재검사하도록 했다.
- `created_by`, `updated_by`를 현재 인증 사용자 기준으로 기록하도록 했다.
- 프로젝트 입력 검증을 추가했다.
  - slug
  - 개발 상태
  - 공개 상태
  - 태그
  - 날짜
  - 멤버
  - 외부 링크 URL protocol
- 관리자 프로젝트 목록, 생성, 수정, 삭제 UI를 실제 Supabase CRUD에 연결했다.
- `docs/project-management.md`를 추가했다.

### 5. 관리자 공지사항 Supabase CRUD

- 관리자 공지사항 목록/상세 query를 Supabase 기반으로 전환했다.
- 공지사항 생성/수정/삭제 Server Action을 추가했다.
- 제목, slug, 요약, 본문, 공개 상태, pinned 검증을 추가했다.
- 관리자 공지 목록 UI를 실제 CRUD 흐름에 연결했다.
- 관리자 dashboard의 최근 공지 데이터를 Supabase에서 조회하도록 바꿨다.
- `docs/notice-management.md`를 추가했다.

### 6. 관리자 모집 정보 Supabase CRUD 및 current 관리

- 관리자 모집 관리가 mock 단일 폼에서 Supabase 기반 목록/생성/수정/current 관리 흐름으로 전환됐다.
- `create_recruitment`, `save_recruitment`, `set_current_recruitment`, `unset_current_recruitment` RPC를 추가했다.
- 모집 정보와 모집 절차를 원자적으로 저장하도록 구성했다.
- 절차 수정 시 기존 `recruitment_steps`를 전체 교체하도록 했다.
- `created_by`, `updated_by`를 `auth.uid()` 기반으로 기록했다.
- 처음 `published` 전환 시 `published_at`을 설정했다.
- current 지정 시 기존 current를 해제하고 새 current를 지정하도록 했다.
- archived 모집은 current 지정이 불가능하도록 막았다.
- 영구 삭제 대신 archive 흐름을 사용했다.
- 공개 모집 query는 `is_current = true` 및 `publication_status = published`만 반환하도록 정리했다.
- 모집 정보 입력 검증을 추가했다.
  - 제목
  - 요약
  - 모집 상태
  - 공개 상태
  - 대상/자격/활동 목록
  - 일정
  - 지원 URL
  - 절차
  - 문의 URL
- `docs/recruitment-management.md`를 추가했다.

### 7. 사이트 설정, 연락처, SNS Supabase 관리

- 사이트 설정, 연락처, SNS 관리가 mock/disabled UI에서 Supabase 기반 관리자 조회 및 CRUD 흐름으로 전환됐다.
- `site_settings` singleton row 관리 흐름을 구현했다.
- 사이트 설정은 `id = 1` 기준으로 upsert하도록 했다.
- 연락처 생성/수정/삭제, 활성/비활성, 정렬 순서 관리를 구현했다.
- SNS 링크 생성/수정/삭제, 활성/비활성, 정렬 순서 관리를 구현했다.
- 공개 연락처 조회 조건을 `is_active = true`로 제한했다.
- 공개 SNS 조회 조건을 `is_active = true` 및 `url is not null`로 제한했다.
- 연락처 URL은 `http`, `https`, `mailto`만 허용했다.
- SNS URL은 `http`, `https`만 허용했다.
- 관리자 dashboard에 사이트 설정, 연락처, SNS 상태 요약을 연결했다.
- Header, Footer, Hero, Club summary, Contact card, SNS banner가 Supabase 설정/연락처/SNS 데이터를 사용하도록 연결했다.
- `docs/site-settings-management.md`를 추가했다.

### 8. Supabase Storage 이미지 관리 및 최종 통합 검증

- Supabase Storage migration을 추가했다.
- public bucket을 생성했다.
  - `project-images`
  - `site-assets`
- Storage RLS 정책을 추가했다.
  - 공개 이미지는 `anon`, `authenticated`가 읽을 수 있음
  - `editor`, `admin`만 업로드/수정/삭제 가능
  - 프로젝트 이미지는 `{projectId}/thumbnail/...` 경로로 제한
  - 사이트 이미지는 `logo/...`, `hero/...` 경로로 제한
- `site_settings.logo_path`, `site_settings.hero_image_path` 컬럼을 추가했다.
- 프로젝트 대표 이미지 업로드/교체/삭제 UI와 Server Action을 추가했다.
- 프로젝트 삭제 시 기존 thumbnail object 삭제를 시도하도록 했다.
- 사이트 설정 관리자 화면에 로고/Hero 이미지 업로드/교체/삭제 UI를 추가했다.
- 공개 Header 로고와 메인 Hero 이미지를 Supabase Storage public URL로 렌더링하도록 연결했다.
- DB에는 object path만 저장하고 query mapper에서 public URL을 생성하도록 했다.
- JPEG, PNG, WebP만 허용하도록 서버 검증을 추가했다.
- 브라우저 MIME 값뿐 아니라 파일 시그니처도 확인하도록 했다.
- SVG 등 허용하지 않은 형식은 차단하도록 했다.
- `next.config.ts`에 `NEXT_PUBLIC_SUPABASE_URL` 기반 Storage remote pattern을 추가했다.
- `docs/storage-management.md`를 추가했다.
- README와 schema 문서를 현재 Storage 상태에 맞게 갱신했다.

## 최종 구현 상태

- 공개 페이지는 Supabase가 설정된 환경에서 실제 DB 데이터를 조회한다.
- Supabase가 설정되지 않은 환경에서는 일부 공개 페이지가 기존 fallback 데이터를 사용한다.
- 관리자 화면은 Supabase Auth와 `profiles.role` 기반 권한 검사를 사용한다.
- `editor`, `admin`은 콘텐츠 관리가 가능하다.
- `member`, `anon`은 관리자 mutation을 수행할 수 없다.
- 프로젝트, 공지사항, 모집, 사이트 설정, 연락처, SNS 링크는 관리자 화면에서 Supabase에 저장된다.
- 프로젝트 대표 이미지, 사이트 로고, Hero 이미지는 Supabase Storage에 저장된다.
- 이미지 URL 자체를 DB에 저장하지 않고 object path만 저장한다.
- 공개 렌더링 시점에 Supabase public URL을 생성한다.
- service role key나 secret을 앱 코드에 하드코딩하지 않았다.

## 최종 검증

프롬프트 8 완료 시점 기준 검증 결과는 다음과 같다.

- `pnpm.cmd lint` 성공
- `pnpm.cmd build` 성공
- `pnpm.cmd exec tsc --noEmit` 성공
- `pnpm.cmd supabase db reset` 성공
- `pnpm.cmd supabase test db` 성공
  - `Files=5`
  - `Tests=104`
  - `Result: PASS`
- `pnpm.cmd run supabase:types` 성공
- secret/service role key 하드코딩 검색 결과 코드 내 발견 없음

## 참고 및 남은 확인 사항

- 실제 브라우저에서 관리자 계정으로 전체 CRUD와 이미지 업로드를 클릭 검증하지는 않았다.
- 로컬 관리자 계정 정보가 없어 브라우저 수동 검증 대신 DB/RLS/빌드/타입 검증으로 확인했다.
- Supabase local status 출력에는 로컬 개발용 key가 포함될 수 있으므로 문서와 결과 요약에는 값을 기록하지 않았다.
- 원격 Supabase 프로젝트 연결, 운영 환경 변수 설정, Vercel 배포 검증은 별도 단계에서 진행해야 한다.

이번 작업은 7단계 중 **프롬프트 5: 공지사항 게시판과 모집 안내 및 지원 링크 구현**에 해당한다.

이전 단계에서 다음 작업이 완료되었다고 가정한다.

* Next.js App Router 기반 공개 및 관리자 라우팅 골격
* 공개 사이트 Header와 Footer
* 모바일 내비게이션
* 공통 UI 컴포넌트
* 메인 페이지
* 동아리 소개 페이지
* 연락처와 SNS 배너
* 프로젝트 타입과 임시 데이터
* 프로젝트 목록 및 상세 페이지
* 메인 페이지 대표 프로젝트 연동
* 공지사항 및 모집 페이지의 임시 라우팅

기존 파일을 먼저 읽고 실제 구현 상태에 맞춰 필요한 부분만 수정하라.

프로젝트 전체를 재생성하거나 기존 공통 레이아웃과 기능을 전면 교체하지 마라.

# 6. 공지사항 타입

다음 파일을 생성한다.

```text
src/features/notices/types.ts
```

최소한 다음 타입을 정의한다.

```ts
export type Notice = {
  id: string;
  slug: string;
  title: string;
  summary: string;
  content: string;
  pinned: boolean;
  publishedAt: string;
  updatedAt?: string;
};
```

필요한 경우 다음 타입을 추가할 수 있다.

```ts
export type NoticePreview = Pick<
  Notice,
  "id" | "slug" | "title" | "summary" | "pinned" | "publishedAt"
>;
```

## 타입 규칙

* `any`를 사용하지 않는다.
* 날짜는 ISO 8601 문자열로 관리한다.
* 본문은 plain text로 관리한다.
* HTML 문자열을 직접 저장하지 않는다.
* Markdown 라이브러리를 도입하지 않는다.
* 카테고리, 작성자, 조회수 등 아직 필요하지 않은 필드를 추가하지 않는다.
* 관리자 전용 필드를 미리 과도하게 설계하지 않는다.

# 8. 공지사항 조회 함수

다음 파일을 생성한다.

```text
src/features/notices/queries.ts
```

로컬 mock data를 조회하는 순수 함수를 작성한다.

최소 함수:

```ts
export function getAllNotices(): Notice[];

export function getLatestNotices(limit?: number): Notice[];

export function getNoticeBySlug(slug: string): Notice | undefined;
```

필요한 경우 다음 함수도 추가할 수 있다.

```ts
export function getPinnedNotices(): Notice[];
```

## 정렬 규칙

공지사항 목록은 다음 순서로 정렬한다.

1. 고정 공지
2. 최신 발행일
3. 동일 날짜일 경우 기존 배열 순서

`getAllNotices()`는 정렬된 새 배열을 반환한다.

원본 mock data 배열을 직접 변경하지 마라.

`getLatestNotices()`는 고정 여부와 관계없이 발행일 기준 최신 공지를 반환하거나, 메인 페이지 성격에 맞게 고정 공지를 우선 포함할 수 있다.

어떤 규칙을 선택했는지 코드에서 명확하게 드러나게 하라.

`limit`이 전달되면 안전하게 제한한다.

비동기 함수로 만들지 않는다.

Supabase API를 흉내 내지 않는다.

## 본문 렌더링

공지 content는 plain text다.

줄바꿈 또는 빈 줄을 기준으로 문단을 나누어 렌더링한다.

예를 들어 다음처럼 안전하게 처리할 수 있다.

```ts
const paragraphs = notice.content
  .split(/\n\s*\n/)
  .map((paragraph) => paragraph.trim())
  .filter(Boolean);
```

각 문단은 `<p>`로 렌더링한다.

다음을 하지 마라.

* `dangerouslySetInnerHTML`
* HTML 문자열 렌더링
* Markdown 변환
* 임의의 링크 자동 변환

## heading 구조

* 공지 제목은 `<h1>`
* 추가 소제목이 필요하지 않다면 억지로 `<h2>`를 만들지 않는다.
* 메타 정보는 heading이 아닌 적절한 텍스트 요소로 작성한다.

# 30. 날짜 표시


```ts
export function formatDateRange(
  startsAt?: string,
```

## 날짜 유틸리티 규칙

* 외부 날짜 라이브러리를 설치하지 않는다.

* 유효하지 않은 날짜는 안전한 fallback을 반환하거나 렌더링을 생략한다.
* 서버와 클라이언트 hydration 차이가 발생하지 않게 한다.
* 현재 시간을 직접 표시하지 않는다.
* 날짜 문자열을 임의로 보정하지 않는다.

# 32. 디자인 기준

## 공지사항

* 게시판 또는 목록 성격이 명확해야 한다.
* 고정 공지가 자연스럽게 구분되어야 한다.
* 날짜와 제목의 위계가 명확해야 한다.
* 모바일에서도 제목과 메타 정보가 읽기 쉬워야 한다.
* 과도한 표 형태보다 유연한 목록 구조를 우선한다.

## 모집 안내

* 현재 모집 상태가 가장 먼저 보여야 한다.
* 지원 버튼의 활성 및 비활성 상태가 명확해야 한다.
* 모집 대상, 활동, 절차가 구분되어야 한다.
* 일정이 없을 때 빈 카드처럼 보이지 않게 한다.
* CTA가 지나치게 공격적으로 보이지 않게 한다.

기존 CSS 변수를 재사용한다.

```text

--foreground
--surface
--border
--primary
--primary-foreground
```

* 고정 배지가 제목을 밀어내지 않아야 한다.
* 본문 문단이 읽기 쉬운 너비를 가져야 한다.
* 긴 단어 또는 URL이 화면을 넘지 않아야 한다.

## 모집 안내

* 상태와 제목이 모바일에서 겹치지 않아야 한다.
* 지원 버튼이 화면 너비를 넘지 않아야 한다.
* 단계 목록이 모바일에서 세로로 표시되어야 한다.
* 모집 대상과 활동 목록이 읽기 쉬워야 한다.
* 긴 문장이 자연스럽게 줄바꿈되어야 한다.
* 고정 픽셀 너비를 남용하지 않는다.

# 35. 접근성 요구사항

다음을 준수한다.

## 공지사항

* 목록 페이지에 하나의 `<h1>`
* 상세 페이지에서 공지 제목을 `<h1>`로 사용
* 공지 목록은 `<ul>`과 `<li>` 사용
* 고정 여부는 텍스트로 표시
* 링크 이름으로 공지 제목을 이해할 수 있어야 함
* 날짜는 `<time dateTime="...">` 사용 가능
* focus-visible 표시 유지

## 모집

* 모집 페이지에 하나의 `<h1>`
* 모집 대상, 활동, 절차 등은 `<h2>` 사용
* 목록은 `<ul>` 또는 `<ol>` 사용
* 모집 절차는 순서가 의미 있으므로 `<ol>` 권장
* 비활성 지원 버튼의 이유가 텍스트로 전달되어야 함
* 외부 지원 링크에는 새 탭 및 보안 속성 적용
* 색상만으로 모집 상태를 구분하지 않음

## 일반

* 장식용 SVG는 `aria-hidden="true"`
* 빈 링크 금지
* `href="#"` 금지
* heading 순서를 건너뛰지 않음
* 키보드 focus 표시 제거 금지

# 36. 코드 품질 규칙

* TypeScript를 사용한다.
* `any`를 사용하지 않는다.
* 기존 export 방식을 따른다.
* `@/*` 경로 별칭을 활용한다.
* 사용하지 않는 import를 제거한다.
* 공지사항 데이터는 한 파일에서만 관리한다.
* 모집 데이터는 한 파일에서만 관리한다.
* 상태 라벨 매핑을 중복 작성하지 않는다.
* 페이지 파일은 데이터 조회와 조합만 담당한다.
* UI 컴포넌트는 mock data를 직접 import하지 않는다.
* 조회 함수는 `queries.ts`에 둔다.
* 도메인 타입은 `types.ts`에 둔다.
* 날짜 포맷이 반복되면 유틸리티로 분리한다.
* 외부 URL에 보안 속성을 적용한다.
* 불필요한 추상화를 만들지 않는다.
* 불필요한 배럴 파일을 만들지 않는다.
* 외부 패키지를 설치하지 않는다.
* 기존 공통 UI를 중복 구현하지 않는다.

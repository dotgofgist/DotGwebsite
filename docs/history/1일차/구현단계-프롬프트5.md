현재 작업 중인 저장소는 게임창작부 동아리 웹사이트 `DotG`다.

이번 작업은 새로운 개발 페이즈의 **프롬프트 5: 관리자 공지사항 Supabase 조회 및 CRUD 구현**에 해당한다.

프롬프트 1부터 프롬프트 4까지 다음 작업이 완료되었다고 가정한다.

# 14. UUID 검증

`getAdminNoticeById()`와 mutation Action은 전달된 id가 유효한 UUID 형식인지 확인할 수 있다.

# 26. 공개 상태 검증

허용 상태:

```text id="rx54nf"

```

규칙:

* 새 공지 기본값은 `draft`
* `published`인 공지만 공개 목록에 노출
* `draft`는 관리자만 조회

* 허용되지 않은 문자열을 type assertion으로 강제하지 않음

# 27. publishedAt 정책

권장 정책:

```text id="tpged6"
새 공지를 published로 생성
→ published_at = now()

기존 draft를 처음 published로 전환
→ published_at = now()

기존 published 공지 수정
→ 기존 published_at 유지

published 공지를 draft 또는 archived로 전환
→ 최초 published_at 유지

archived 또는 draft를 다시 published
→ 기존 published_at이 있으면 유지
```

이 정책은 공지의 최초 공개 시점을 유지한다.

현재 프로젝트 공개 상태 정책과 일관되게 구현한다.

다른 정책을 선택한다면 완료 보고와 문서에 명시한다.

# 29. 공지사항 mutation 방식

공지사항은 단일 `notices` 테이블만 변경하므로 프로젝트처럼 다중 테이블 transaction RPC가 필요하지 않다.

우선 다음 Supabase mutation을 직접 사용한다.

```text id="zml1ik"

```

불필요한 RPC를 추가하지 마라.

다만 기존 DB schema에서 `published_at`, 작성자·수정자 처리용 함수가 이미 있다면 재사용할 수 있다.

생성·수정 Action은 다음 순서를 따른다.


# 32. 생성 Action 구현

`createNoticeAction()`:

* id를 받지 않음
* id가 FormData에 포함되어도 신뢰하지 않음
* 입력 검증
* 공개 상태에 따른 `published_at`
* `created_by`, `updated_by`에 현재 사용자 ID
* Supabase insert
* 생성된 UUID와 slug 확인
* 경로 재검증
* 수정 페이지 또는 목록으로 이동

권장 성공 경로:

```text id="40t0t9"
/admin/notices/{createdId}/edit?created=1
```

또는:

```text id="f36uq8"
/admin/notices?created=1
```

생성 결과를 확인하기 쉬운 수정 페이지 이동을 권장한다.

# 33. 수정 Action 구현

`updateNoticeAction()`:

1. hidden id 읽기
2. UUID 검증
3. `requireContentManager()`
4. 기존 공지 조회
5. 존재하지 않으면 오류
6. 입력 검증
7. 기존 slug 및 `published_at` 확인
8. 공개 상태 정책 적용
9. `updated_by` 현재 사용자
10. Supabase update
11. `.eq("id", noticeId)` 적용
12. 변경 결과 확인
13. 경로 재검증
14. 수정 페이지로 redirect

filter 없는 update를 수행하지 마라.

이전 slug는 hidden input만 신뢰하지 말고 DB에서 조회한다.

# 41. 공개 상태 변경 처리

## draft → published

* `/notices`에 표시
* 메인 최신 공지 반영 가능
* 상세 경로 표시

## published → draft

* 공개 목록에서 제거
* 상세 경로 404
* 메인 최신 공지에서 제거

## published → archived

* 공개 목록에서 제거
* 상세 경로 404
* 관리자 목록에는 유지

## archived → published

* 공개 목록과 상세에 다시 표시
* 기존 publishedAt 정책 유지

# 61. 동시 제출 방지

pending 상태로 중복 제출을 방지한다.

동시에 동일 slug 생성 요청이 들어오더라도:

* DB unique constraint가 최종 방어
* 한 요청은 사용자 친화적 중복 오류
* 중복 row 생성 안 됨

별도 idempotency 시스템은 이번 단계에서 구현하지 않는다.

# 73. 최종 완료 기준

다음 조건을 모두 만족하면 이번 작업을 완료한 것으로 본다.

* 관리자 공지사항 목록이 실제 Supabase 데이터를 사용한다.
* 관리자 공지사항 수정 페이지가 실제 Supabase 데이터를 사용한다.
* 관리자 공지사항 mock query가 더 이상 관리자 UI에서 사용되지 않는다.
* 공지사항 생성이 실제 DB에 저장된다.
* 공지사항 수정이 실제 DB에 저장된다.
* 공지사항 삭제가 실제 DB에서 수행된다.
* 모든 query와 mutation에서 관리자 권한을 재검사한다.
* anon과 member는 공지사항을 수정할 수 없다.
* editor와 admin은 공지사항을 관리할 수 있다.
* created_by와 updated_by가 현재 Auth 사용자로 기록된다.
* slug가 서버와 DB에서 검증된다.
* 중복 slug가 사용자 친화적 오류로 표시된다.
* 제목, 요약, 본문, 고정 여부, 공개 상태가 검증된다.
* 본문은 plain text로 유지된다.
* HTML과 Markdown 에디터를 추가하지 않는다.
* 새 공지는 기본적으로 draft다.
* 처음 공개 시 published_at이 설정된다.
* 기존 공지의 최초 published_at 정책이 유지된다.
* 생성·수정·삭제 후 관련 공개·관리자 경로가 갱신된다.
* draft 공지는 공개 페이지에 표시되지 않는다.
* published 공지는 공개 페이지에 표시된다.
* archived 공지는 공개 페이지에 표시되지 않는다.
* 고정 공지가 공개 목록에서 우선 표시된다.
* 공지 변경이 메인 페이지 최신 공지에 반영된다.
* slug 변경 후 이전 경로는 404가 된다.
* 삭제 후 공개 상세는 404가 된다.
* 관리자 대시보드 공지 정보가 실제 데이터와 연결된다.
* 모집·사이트 설정 CRUD는 구현하지 않는다.
* 첨부파일과 Storage는 구현하지 않는다.
* Service Role Key를 사용하지 않는다.
* 실제 Secret이나 사용자 정보가 코드 또는 Git diff에 없다.
* 모바일과 접근성에 회귀가 없다.
* `pnpm lint`, `pnpm build`, `pnpm exec tsc --noEmit`이 통과한다.

현재 작업 중인 저장소는 게임창작부 동아리 웹사이트 `DotG`다.

이번 작업은 새로운 개발 페이즈의 **프롬프트 4: 관리자 프로젝트 Supabase 조회 및 CRUD 구현**에 해당한다.

프롬프트 1부터 프롬프트 3까지 다음 작업이 완료되었다고 가정한다.

* Supabase DB schema와 migration
* 프로젝트 관련 테이블
* `projects`
* `project_members`
* `project_links`
* 프로젝트 공개·관리자 RLS
* 실제 `database.types.ts`
* 공개 프로젝트 Supabase 조회
* 프로젝트 DB row와 도메인 타입 mapper
* 관리자 email/password 로그인
* `profiles.role` 기반 관리자 권한 확인
* `editor`와 `admin`의 관리자 접근 허용
* `/admin` Route 보호
* Server Component 기반 최종 권한 검사
* 관리자 프로젝트 목록·생성·수정 폼 UI
* 관리자 프로젝트 화면은 아직 mock data 사용
* 공개 프로젝트 목록과 상세는 실제 Supabase 데이터 사용
* 프로젝트 저장·수정·삭제는 아직 비동작

이번 작업에서는 관리자 프로젝트 기능만 실제 Supabase와 연결한다.

공지사항, 모집, 사이트 설정 CRUD는 아직 구현하지 않는다.

# 3. 권한 정책

프로젝트 관리 권한은 다음 역할에만 허용한다.

```text
editor
admin
```

다음 역할에는 허용하지 않는다.

```text
anon
authenticated member
```

권한 검사는 다음 세 계층에서 적용한다.

```text
관리자 Dashboard Layout
→ 관리자 페이지 접근 보호

프로젝트 query 및 Server Action
→ 서버 함수 재사용 시 권한 재검사

Supabase RLS
→ 실제 DB SELECT·INSERT·UPDATE·DELETE 강제
```

관리자 Layout을 통과했다는 이유만으로 Server Action의 권한 검사를 생략하지 마라.

브라우저 UI에서 버튼을 숨기는 것으로 권한을 대신하지 마라.

Service Role Key로 RLS를 우회하지 마라.

# 8. 프로젝트 관리자 조회 타입

공개 `Project` 타입을 관리자 조회에서도 재사용할 수 있는지 검토한다.

관리자 화면에는 공개 타입에 없는 다음 정보가 필요할 수 있다.

```text
publicationStatus
publishedAt
sortOrder
thumbnailPath
updatedAt
createdBy
updatedBy
```

필요하면 별도 관리자 타입을 정의한다.

```ts
export type AdminProject = Project & {
  publicationStatus: ContentStatus;
  publishedAt?: string;
  sortOrder: number;
  thumbnailPath?: string;
  updatedAt: string;
};
```

실제 필요한 필드만 추가한다.

관리자 화면에서 사용하지 않는 audit 필드를 모두 노출하지 마라.

DB Row 타입을 그대로 UI props로 전달하지 마라.

DB row와 관리자 도메인 타입 사이 mapper를 둔다.

# 9. 관리자 프로젝트 mapper

필요하면 다음 파일을 생성한다.

```text
src/features/projects/admin-mappers.ts
```

최소 mapper:

```ts
export function mapProjectRowToAdminProject(
```

변환 기준:

```text

published_at       → publishedAt
sort_order         → sortOrder
thumbnail_path     → thumbnailPath
updated_at         → updatedAt
project_members    → members
project_links      → links
```

관계 데이터 정렬:

```text

project_links.sort_order 오름차순
```

공개 mapper와 중복되는 변환은 작은 공통 함수로 분리할 수 있다.

과도한 범용 mapper framework를 만들지 마라.

# 12. 관리자 프로젝트 상세 query



관계 조회 방식:

* 또는 프로젝트·멤버·링크 병렬 조회

어느 방식을 사용하든 N+1 query를 만들지 마라.

# 13. UUID 검증

`getAdminProjectById()`와 mutation action은 전달된 id가 UUID 형식인지 먼저 확인할 수 있다.

유효하지 않은 id:

* DB query를 수행하지 않음
* 수정 페이지에서는 `notFound()` 또는 관리자용 오류 화면
* mutation에서는 안전한 action error 반환

UUID 검증을 위해 새 외부 패키지를 설치하지 마라.

복잡한 UUID 버전 검증은 필요하지 않다.

```ts
  tags: string[];
  featured: boolean;
  startedAt?: string;
  releasedAt?: string;
  sortOrder: number;
```

# 23. 프로젝트 상태 검증


허용되지 않은 문자열을 type assertion으로 강제하지 마라.

# 24. 공개 상태 검증

허용된 값:

```text
draft
published
archived
```

규칙:

* 새 프로젝트 기본값은 `draft`
* `published`일 때 `published_at` 설정 정책 필요
* `draft`로 되돌릴 때 `published_at` 유지 또는 NULL 처리 정책 결정
* `archived`는 공개 query에서 노출되지 않음

권장 정책:

```text
처음 published 전환
→ published_at = now()

이미 published_at 존재
→ 기존 값 유지

draft 또는 archived 전환
→ published_at은 기존 최초 공개 시점으로 유지
```

다른 정책을 선택했다면 완료 보고에 명확히 작성한다.

# 26. 날짜 검증

필드:


규칙:

* 두 날짜가 모두 있으면 releasedAt >= startedAt
* 시간대를 임의로 적용하지 않음
* date 컬럼에는 날짜 문자열 그대로 전달

# 29. 멤버 입력 방식

```text

기획 팀 | 게임 기획
개발 팀 | 프로그래밍
```

* 최대 항목 수 제한
* 중복 항목 검토
* 입력 순서대로 sortOrder 부여

잘못된 줄이 있으면 전체 저장을 진행하지 않고 `members` field error를 반환한다.

기존에 더 구조화된 입력 UI가 있다면 기존 구조를 유지한다.

# 32. 프로젝트 관계 저장의 원자성

프로젝트 본문, 멤버, 링크는 한 번의 저장 단위로 취급해야 한다.

다음 상황이 발생하면 안 된다.

```text
프로젝트 본문 저장 성공
+
멤버 저장 실패
+
일부 데이터만 남음
```

Supabase JavaScript client만으로 다중 테이블 transaction을 직접 구성하지 마라.

프로젝트와 관계 데이터를 원자적으로 저장하기 위해 PostgreSQL 함수/RPC를 사용하는 것을 우선한다.

# 33. 프로젝트 저장 RPC migration

기존에 동일한 함수가 없다면 새 migration을 생성한다.

```powershell
pnpm supabase migration new add_project_write_functions
```

생성된 실제 timestamp 파일을 사용한다.

migration에 다음 함수를 구현할 수 있다.

```text
public.save_project_with_relations()
```

역할:

* project id가 없으면 생성
* project id가 있으면 수정
* 프로젝트 필드 저장
* 기존 멤버 삭제 후 새 멤버 삽입
* 기존 링크 삭제 후 새 링크 삽입
* 하나의 DB transaction 안에서 처리
* 저장된 project id 반환

PostgreSQL 함수 호출 자체가 하나의 transaction으로 실행되는 특성을 이용한다.

프로젝트 수정 시:

```text
p_project_id = 기존 UUID
```

함수 인자는 실제 schema와 생성 타입에 맞춰 조정한다.

# 35. RPC 보안

저장 함수는 기본적으로 다음을 사용한다.

```text
SECURITY INVOKER
```

RLS를 우회하지 마라.

함수 내부에서도 필요하면 다음 권한을 명시적으로 확인한다.

```sql
public.can_manage_content()
```

권한이 없으면 예외를 발생시킨다.

다음 원칙을 적용한다.

* Service Role 불필요
* 함수 소유자 권한으로 RLS 우회 금지
* 명시적인 `search_path`
* 동적 SQL 금지
* 사용자 입력으로 table 또는 column 이름 생성 금지
* `auth.uid()`가 없으면 실패
* created_by와 updated_by는 `auth.uid()` 사용

---

# 36. RPC 생성 처리

프로젝트 생성 시 다음 값을 DB에서 설정한다.

```text
id
created_at
updated_at
created_by
updated_by
published_at
```

정책:

* `id`: `gen_random_uuid()`
* `created_by`: `auth.uid()`
* `updated_by`: `auth.uid()`
* `created_at`: 기본값
* `updated_at`: 기본값
* 처음 published이면 `published_at = now()`

클라이언트에서 작성자 UUID를 전달받지 마라.

---

# 37. RPC 수정 처리

프로젝트 수정 시:

* `id`로 기존 프로젝트 확인
* 존재하지 않으면 예외
* 수정 가능한 프로젝트인지 RLS 및 권한 확인
* `created_by`와 `created_at` 유지
* `updated_by = auth.uid()`
* `updated_at` trigger 또는 명시적 갱신
* 공개 전환 정책에 따라 `published_at` 처리
* 멤버와 링크는 전체 교체 가능
* 관계 삭제와 재삽입이 같은 transaction 안에서 수행됨

다른 프로젝트의 관계 데이터를 수정하지 마라.

---

# 38. JSON 관계 데이터 처리

`p_members`와 `p_links`는 JSON array로 받을 수 있다.

멤버 예시 구조:

```json
[
  {
    "name": "개발 팀",
    "role": "프로그래밍",
    "sort_order": 0
  }
]
```

링크 예시 구조:

```json
[
  {
    "link_type": "github",
    "label": "GitHub 저장소",
    "url": "https://example.com",
    "sort_order": 0
  }
]
```

SQL 함수에서 `jsonb_to_recordset` 등을 사용할 수 있다.

함수는 배열이 아닌 JSON을 안전하게 거부해야 한다.

애플리케이션 검증을 통과했다고 DB 검증을 완전히 생략하지 마라.

# 39. RPC execute 권한

# 42. Server Action 공통 순서

생성·수정 action은 다음 순서를 따른다.

```text
1. requireContentManager()
2. FormData parsing
3. 서버 입력 검증
4. 검증 실패 시 fieldErrors 반환
5. 서버 Supabase client 생성
6. RPC 또는 mutation 실행
7. DB 오류 변환
8. revalidatePath
9. redirect
```

권장 보안상 다음 순서도 가능하다.

```text
1. requireContentManager()
2. 입력 처리
```

권한 없는 사용자의 큰 입력을 먼저 처리하지 않는 것이 좋다.

# 43. 생성 Action

`createProjectAction()`:

* project id를 받지 않음
* id가 전달되어도 신뢰하지 않음
* 프로젝트 저장 RPC 호출
* 생성된 UUID 확인
* 관계 데이터 저장
* 성공 후 cache 재검증
* 생성된 프로젝트 수정 페이지로 이동

권장 성공 경로:

```text
/admin/projects/{createdId}/edit?created=1
```

또는:

```text
/admin/projects?created=1
```

생성 직후 추가 확인이 가능하도록 수정 페이지 이동을 권장한다.

---

# 44. 수정 Action

`updateProjectAction()`:

* hidden `id` 검증
* UUID 형식 검증
* 현재 프로젝트 존재 여부 확인
* 전체 폼 검증
* RPC 호출
* 이전 slug와 새 slug 비교
* 관련 경로 재검증
* 성공 후 같은 수정 페이지로 redirect

권장 성공 경로:

```text
/admin/projects/{id}/edit?saved=1
```

이전 slug는 action에서 DB 조회 결과로 얻는다.

브라우저 hidden input의 이전 slug만 신뢰하지 마라.

---

# 45. 삭제 Action

`deleteProjectAction()`:

1. `requireContentManager()`
2. id 읽기
3. UUID 검증
4. 삭제 대상 조회
5. Supabase delete 실행
6. 오류 확인
7. 관련 경로 재검증
8. 관리자 프로젝트 목록으로 redirect

조건:

```ts
.from("projects")
.delete()
.eq("id", projectId)
```

필터 없이 delete를 호출하지 마라.

프로젝트 멤버와 링크는 DB foreign key cascade로 삭제되어야 한다.

애플리케이션에서 관계 행을 하나씩 먼저 삭제하지 마라.

# 46. 삭제 정책

이번 단계에서 삭제는 영구 삭제다.

관리자에게 다음 내용을 명확하게 안내한다.

```text
프로젝트와 연결된 멤버 및 링크 정보가 함께 삭제됩니다.
이 작업은 되돌릴 수 없습니다.
```

보관이 필요한 콘텐츠는 삭제 대신 다음 상태를 사용할 수 있다.

```text
publicationStatus = archived
```

삭제 버튼과 보관 기능을 혼동하지 마라.

프로젝트 제목을 확인 문구에 포함한다.

# 47. DB 오류 변환

Supabase/Postgres 오류 원문을 그대로 사용자에게 표시하지 마라.

최소한 다음 오류를 구분한다.

## slug 중복

Postgres unique violation인 경우:

```text
이미 사용 중인 slug입니다.
```

`slug` field error로 연결한다.

## 권한 오류

```text
프로젝트를 저장할 권한이 없습니다.
```

## 존재하지 않는 프로젝트

```text
프로젝트를 찾을 수 없습니다.
```

## 관계 데이터 오류

```text
프로젝트 멤버 또는 링크 정보를 확인해 주세요.
```

## 기타 DB 오류

```text
프로젝트 저장 중 문제가 발생했습니다.
잠시 후 다시 시도해 주세요.
```

오류 코드 매핑은 작은 함수로 분리할 수 있다.

DB 오류 객체 전체를 action state로 반환하지 마라.

# 81. 최종 완료 기준

다음 조건을 모두 만족하면 이번 작업을 완료한 것으로 본다.

* 관리자 프로젝트 목록이 실제 Supabase 데이터를 사용한다.
* 관리자 프로젝트 수정 페이지가 실제 Supabase 데이터를 사용한다.
* 관리자 프로젝트 mock query가 더 이상 관리자 UI에서 사용되지 않는다.
* 프로젝트 생성이 실제 DB에 저장된다.
* 프로젝트 수정이 실제 DB에 저장된다.
* 프로젝트 삭제가 실제 DB에서 수행된다.
* 프로젝트 멤버가 실제 DB에 저장된다.
* 프로젝트 링크가 실제 DB에 저장된다.
* 프로젝트와 관계 데이터가 원자적으로 저장된다.
* 저장 RPC는 RLS를 우회하지 않는다.
* 모든 query와 mutation에서 관리자 권한을 재검사한다.
* anon과 member는 프로젝트를 수정할 수 없다.
* editor와 admin은 프로젝트를 관리할 수 있다.
* created_by와 updated_by가 서버의 Auth 사용자로 기록된다.
* slug가 서버와 DB에서 검증된다.
* 중복 slug가 사용자 친화적인 오류로 표시된다.
* 프로젝트 상태와 공개 상태가 검증된다.
* 태그, 날짜, 멤버, 링크가 검증된다.
* 위험한 URL protocol이 차단된다.
* 생성·수정·삭제 후 관련 공개·관리자 경로가 갱신된다.
* 초안은 공개 페이지에 표시되지 않는다.
* 공개 프로젝트는 공개 페이지에 표시된다.
* 보관 프로젝트는 공개 페이지에 표시되지 않는다.
* slug 변경 후 이전 경로는 404가 된다.
* 삭제 후 관련 멤버와 링크가 함께 삭제된다.
* 관리자 대시보드의 프로젝트 정보가 실제 데이터와 연결된다.
* 공지사항·모집·사이트 설정 CRUD는 구현하지 않는다.
* Storage와 이미지 업로드는 구현하지 않는다.
* Service Role Key를 사용하지 않는다.
* 실제 Secret이나 사용자 정보가 코드 또는 Git diff에 없다.
* 모바일과 접근성에 회귀가 없다.
* `pnpm lint`, `pnpm build`, `pnpm exec tsc --noEmit`이 통과한다.

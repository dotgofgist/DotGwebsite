현재 작업 중인 저장소는 게임창작부 동아리 웹사이트 프로젝트다.

이번 작업은 7단계 중 **프롬프트 4: 프로젝트 목록 및 상세 페이지 구현**에 해당한다.

이전 단계에서 다음 작업이 완료되었다고 가정한다.

* Next.js App Router 기반 라우팅 골격
* 공개 사이트 Header 및 Footer
* 모바일 내비게이션
* 공통 UI 컴포넌트
* 메인 페이지
* 동아리 소개 페이지
* 연락처 페이지
* SNS 배너
* `src/config` 기반 사이트 설정
* 프로젝트 페이지의 임시 라우팅

기존 파일을 먼저 읽고 실제 구현 상태에 맞춰 필요한 부분만 수정하라.

프로젝트 전체를 재생성하거나 기존 공통 레이아웃을 전면 교체하지 마라.

# 1. 작업 목표

게임창작부의 프로젝트를 공개 사이트에서 조회할 수 있도록 다음 기능을 구현한다.

1. 프로젝트 타입 정의
2. 프로젝트 임시 데이터
3. 프로젝트 카드
4. 프로젝트 목록 페이지
5. 프로젝트 상세 페이지
6. 프로젝트 상태 및 태그 표시
7. 프로젝트 외부 링크 표시
8. 존재하지 않는 프로젝트의 404 처리
9. 동적 메타데이터
10. 메인 페이지 대표 프로젝트와 실제 프로젝트 데이터 연결
11. 모바일 반응형 프로젝트 UI

이번 단계에서는 Supabase를 사용하지 않는다.

모든 데이터는 로컬의 `mock-data.ts`에서 관리한다.

  description: string;

  status: ProjectStatus;

  releasedAt?: string;

## 타입 규칙

* `any`를 사용하지 않는다.
* 상태값은 createdAt: string;
  };

````

## 타입 규칙

- `any` 문자열 union으로 제한한다.
- 날짜는 ISO 8601 형식의 문자열로 관리한다.
- 선택 정보는 optional property로 표시한다.
- 관리자 전용 필드는 이번 단계에서 추가하지 않는다.
- DB 스키마를 미리 과도하게 가정하지 않는다.
- 설명 콘텐츠는 현재 plain text로 관리한다.
- Markdown 또는 rich text 라이브러리를 도입하지 않는다.

# 7. 프로젝트 임시 데이터

다음 파일을 생성한다.

```text
src/features/projects/mock-data.ts
````

3개 이상의 임시 프로젝트 데이터를 작성한다.

단, 실제 동아리의 실적처럼 오해될 수 있는 허위 수상 이력, 출시 이력, 다운로드 수, 상업적 성과는 작성하지 마라.

프로젝트는 명확하게 샘플 또는 준비 중인 콘텐츠로 구성한다.

권장 프로젝트 예시:

```text
Project Aurora
픽셀 그래픽 기반의 탐험 게임 프로토타입

Signal Lost
제한된 공간에서 단서를 찾는 퍼즐 게임 콘셉트

Project Forge
여러 개발 실험을 기록하는 팀 프로젝트
```

제목은 자연스럽게 수정할 수 있다.

각 프로젝트는 다음 차이를 가져야 한다.

* 서로 다른 상태
* 서로 다른 태그
* 대표 프로젝트 여부
* 멤버 수
* 외부 링크 유무

## 데이터 작성 규칙

* 최소 1개는 `featured: true`
* 최소 1개는 `planning`
* 최소 1개는 `developing`
* 최소 1개는 `released`
* 실제 URL이 아닌 링크를 작동하는 링크처럼 만들지 않는다.
* 실제 외부 링크가 없다면 `links: []`를 사용한다.
* `href="#"`를 사용하지 않는다.
* 임의의 GitHub 저장소 URL을 생성하지 않는다.
* 임의의 Steam 또는 itch.io URL을 생성하지 않는다.
* 프로젝트 설명은 각 프로젝트마다 2~4문장 정도 작성한다.
* 태그는 2~5개 정도 작성한다.
* 날짜는 샘플 데이터임을 고려해 과도하게 구체적인 실제 성과처럼 작성하지 않는다.
* 대표 이미지가 없다면 로컬 placeholder 방식을 사용한다.

# 8. 프로젝트 이미지 처리

외부 이미지를 다운로드하지 마라.

현재 `public` 디렉터리에 적절한 이미지가 있다면 이를 재사용할 수 있다.

사용할 이미지가 없다면 다음 중 하나를 선택한다.

1. CSS 기반 placeholder
2. 프로젝트 제목의 첫 글자를 사용하는 그래픽
3. 간단한 그라데이션 배경
4. 기존 기본 에셋 재활용

실제 파일이 없는 경로를 `thumbnailUrl`에 작성하지 마라.

CSS placeholder를 사용한다면 `thumbnailUrl`을 빈 문자열로 두는 대신 타입 구조를 다음처럼 조정할 수 있다.

```ts
thumbnailUrl?: string;
```

이 경우 모든 관련 컴포넌트에서 안전하게 처리하라.

`next/image`는 실제 이미지 경로가 존재할 때만 사용한다.

이미지가 없는 경우 잘못된 이미지 요청이 발생하지 않게 하라.

# 9. 프로젝트 조회 함수

다음 파일을 생성한다.

```text
src/features/projects/queries.ts
```

로컬 mock data를 조회하는 순수 함수를 작성한다.

최소 함수:

```ts
export function getAllProjects(): Project[];

export function getFeaturedProjects(limit?: number): Project[];

export function getProjectBySlug(slug: string): Project | undefined;
```

필요한 경우 다음 함수도 추가할 수 있다.

```ts
export function getProjectsByStatus(
  status: ProjectStatus,
): Project[];
```

## 조회 함수 규칙

* 입력 배열을 직접 변경하지 않는다.
* 필요한 경우 새 배열을 반환한다.
* `featured` 프로젝트는 명확하게 필터링한다.
* `limit`이 전달되면 안전하게 제한한다.
* 음수 또는 유효하지 않은 limit을 복잡하게 처리할 필요는 없다.
* 비동기 함수로 만들지 않는다.
* Supabase API 형태를 흉내 내지 않는다.
* 나중에 실제 조회 코드로 교체하기 쉬운 책임 분리를 유지한다.

## 외부 링크 요구사항

* 실제 `href`가 존재하는 항목만 렌더링한다.
* 새 탭으로 연다.
* 다음 속성을 적용한다.

```tsx
target="_blank"
rel="noreferrer noopener"
```

* 링크 이름만으로 목적을 이해할 수 있어야 한다.
* 외부 링크임을 텍스트 또는 보조 문구로 알 수 있게 한다.
* 아이콘 패키지를 설치하지 않는다.
* 간단한 inline SVG를 사용할 수 있다.
* URL을 텍스트 그대로 길게 노출하지 않는다.
* 유효하지 않은 placeholder 링크를 만들지 않는다.

링크 배열이 비어 있으면 해당 섹션 자체를 표시하지 않거나 자연스러운 안내 문구를 표시한다.

* `startedAt`이 있으면 시작 시점을 표시한다.
* `releasedAt`이 있으면 공개 시점을 표시한다.
* 날짜는 사용자에게 읽기 쉬운 형식으로 표시한다.
* 날짜 변환을 위한 외부 라이브러리는 설치하지 않는다.
* 간단한 `Intl.DateTimeFormat` 또는 순수 함수를 사용할 수 있다.
* 유효하지 않은 날짜를 화면에 `Invalid Date`로 출력하지 않는다.

### 참여 구성원

* 이름
* 역할

구성원이 없으면 섹션을 생략하거나 준비 중 안내를 표시한다.

실제 인물의 이름을 임의로 생성하지 않는 것이 좋다.

샘플 데이터에서는 다음처럼 일반적인 이름을 사용할 수 있다.

```text
기획 팀
개발 팀
아트 팀
```

또는 명확한 샘플 인물명임을 알 수 있는 형태를 사용한다.

# 17. 프로젝트 상세 페이지

다음 파일을 수정한다.

```text

```

다음 기능을 구현한다.

Next.js 버전에 따라 `params` 타입과 사용 방식이 다를 수 있으므로, 현재 설치된 Next.js 버전과 기존 코드의 타입 규칙을 확인한 후 맞춰 작성하라.

## 존재하지 않는 프로젝트

프로젝트를 찾지 못하면 다음을 사용한다.

```ts
notFound();
```

페이지 내부에서 단순히 “없음” 텍스트만 출력하지 마라.

## 동적 metadata

프로젝트가 존재하면 다음을 기반으로 metadata를 작성한다.

```text
title: 프로젝트 제목
description: 프로젝트 summary
```

프로젝트가 존재하지 않을 때도 metadata 함수가 예외를 발생시키지 않게 한다.

## 정적 경로

현재 구조에 적합하다면 `generateStaticParams`를 구현한다.

mock data의 slug 목록을 사용한다.

불필요하게 동적 렌더링을 강제하지 마라.

# 25. 접근성 요구사항

다음을 준수한다.

## 제목 구조

* 프로젝트 목록 페이지에 하나의 `<h1>`
* 프로젝트 상세 페이지에 프로젝트 제목을 `<h1>`로 사용
* 상세 섹션 제목은 `<h2>` 사용
* 카드 제목 heading level이 페이지 구조와 자연스럽게 연결됨

## 링크

* 프로젝트 제목 또는 명확한 상세 링크 제공
* “자세히 보기”만 반복하지 않음
* 외부 링크에는 목적이 드러나는 라벨 사용
* 새 탭 링크에 보안 속성 적용
* focus-visible 표시 유지

## 이미지

* 실제 프로젝트 이미지가 있으면 의미 있는 `alt` 제공
* CSS placeholder는 접근성 트리에서 장식 요소로 처리
* 의미 없는 장식 SVG는 `aria-hidden="true"`

## 상태

* 색상만으로 상태를 표현하지 않음
* 텍스트 상태 라벨 제공

## 목록

* 프로젝트 목록은 의미 있는 목록 구조를 사용할 수 있음
* 멤버와 링크 목록도 적절한 `<ul>` 및 `<li>` 사용

이번 프롬프트의 완료 기준은 다음과 같다.

* `/projects`에 프로젝트 목록이 표시된다.
* `/projects/[slug]`에 프로젝트 상세가 표시된다.
* 존재하지 않는 프로젝트는 404 처리된다.
* 프로젝트 상태, 태그, 멤버, 링크가 타입에 따라 안전하게 표시된다.
* 메인 페이지 대표 프로젝트가 같은 mock data를 재사용한다.
* 실제 URL이 없는 링크는 렌더링되지 않는다.
* 모든 프로젝트 UI가 Server Component로 구현된다.
* 360px 이상의 모바일 화면에서 레이아웃이 깨지지 않는다.
* `pnpm lint`와 `pnpm build`가 통과한다.

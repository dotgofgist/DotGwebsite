# 4. 공식 구현 원칙

Supabase SSR에서는 브라우저와 서버용 클라이언트를 분리하고 쿠키로 세션을 유지한다.

Proxy는 만료된 Auth token을 갱신하고 요청·응답 쿠키를 동기화한다.

서버에서 권한을 판단할 때 `getSession()`에 포함된 user 객체만 신뢰하지 마라.

현재 설치된 Supabase SDK에서 지원하는 검증 API를 확인하고 다음 우선순위를 따른다.

```text
신원 검증
→ supabase.auth.getClaims()

최신 Auth 사용자 정보가 반드시 필요한 경우
→ supabase.auth.getUser()

access token이나 refresh token 자체가 필요한 특수한 경우
→ supabase.auth.getSession()
```

이번 작업에서는 raw access token이나 refresh token이 필요하지 않으므로 `getSession()`을 권한 판단에 사용하지 않는다.

Next.js Proxy는 빠른 redirect와 세션 갱신에 사용하되, 최종 권한 검사의 유일한 수단으로 사용하지 않는다.

다음 계층에서도 반드시 권한을 확인한다.

```text
관리자 Dashboard layout
향후 각 관리자 Server Action
```

# 12. 신원 검증

`getAuthenticatedIdentity()`는 서버 Supabase client를 생성한 후 검증된 Auth 정보를 사용한다.

권장 순서:

1. Supabase 환경 변수 설정 여부 확인
2. 서버 Supabase client 생성
3. `supabase.auth.getClaims()` 호출
4. claims에 유효한 사용자 식별자가 있는지 확인
5. 사용자 ID와 이메일을 안전하게 반환
6. 인증되지 않았으면 `null`

현재 SDK에서 claims 반환 구조가 다를 수 있으므로 실제 타입을 확인한다.

claims에서 이메일을 안정적으로 얻지 못한다면 다음 중 하나를 선택한다.

* ID만 우선 반환
* 필요한 경우에만 `getUser()` 추가 호출
* profile과 결합하여 표시 이름 사용

권한 확인을 위해 무조건 `getUser()` 네트워크 요청을 반복하지 마라.

`getSession()`의 user 객체만으로 인증 여부를 판단하지 마라.

# 13. Profile 역할 조회

`getCurrentContentManager()`는 검증된 사용자 ID를 기반으로 다음 테이블을 조회한다.

```text
public.profiles
```

조회 컬럼:

```text
id
display_name
role
```

조건:

```text
id = 현재 Auth 사용자 ID
```

권장 query:

```ts
.from("profiles")
.select("id, display_name, role")
.eq("id", identity.id)
.maybeSingle()
```

실제 생성 타입에 맞춰 작성한다.

처리 규칙:

```text
Auth 사용자 없음
→ null

Auth 사용자 있음 + profile 없음
→ 권한 없음 또는 명확한 설정 오류

profile.role = member
→ null

profile.role = editor
→ ContentManagerIdentity 반환

profile.role = admin
→ ContentManagerIdentity 반환
```

profile 조회 오류를 `member`로 조용히 변환하지 마라.

DB 오류와 권한 부족을 구분한다.

# 14. require 함수

`requireAuthenticatedIdentity()`는 인증되지 않은 경우 로그인 페이지로 redirect한다.

`requireContentManager()`는 다음 규칙을 적용한다.

```text
인증되지 않음
→ /admin/login

인증됨 + member
→ /admin/unauthorized

인증됨 + profile 없음
→ /admin/unauthorized 또는 명확한 설정 오류

인증됨 + editor/admin
→ 사용자 정보 반환
```

서버 함수 안에서 현재 요청 경로를 알기 어려운 경우 원래 경로 전달은 Proxy가 담당한다.

`redirect()`를 광범위한 `try/catch` 안에 넣지 마라.

Next.js의 `redirect()`는 제어 흐름을 중단하므로 일반 오류처럼 잡아서 action error로 바꾸면 안 된다.

# 34. Proxy 책임

기존 파일을 수정한다.

```text

src/proxy.ts
```

Proxy의 책임:

1. Supabase Auth token 갱신
2. 갱신된 cookie를 request에 전달
3. 갱신된 cookie를 response에 전달
4. 보호된 `/admin` 경로의 비로그인 사용자 조기 redirect

* profiles DB 역할 조회
* editor/admin 최종 권한 판단
* CRUD 권한 검사
* 복잡한 데이터 조회
* Service Role 사용
* 페이지별 세밀한 권한 결정

Next.js 16에서는 `proxy.ts` convention을 유지한다.

`middleware.ts`를 새로 만들지 마라.

# 38. Proxy 응답 cookie 보존

Auth token을 갱신한 뒤 redirect response를 새로 만들 경우, 기존 Supabase response의 갱신 cookie가 사라지지 않게 한다.

다음 중 현재 코드에 맞는 안전한 방식을 사용한다.

* 기존 response cookie를 redirect response에 복사
* Supabase client의 `setAll`에서 최종 response를 일관되게 관리
* redirect helper에 cookie 적용

갱신된 request cookie와 browser response cookie가 서로 불일치하지 않게 한다.

Proxy가 무작위 로그아웃이나 session refresh loop를 만들지 않게 한다.

현재 `@supabase/ssr`의 `getAll`/`setAll` cookie API를 유지하고 과거 `get`/`set`/`remove` 패턴으로 되돌리지 마라.

→ 실제 DB 쓰기 권한 강제

# 44. 로그인 계정 준비 방식

코드나 migration에서 실제 관리자 Auth 사용자를 만들지 않는다.

관리자 계정은 다음 방식 중 하나로 준비한다고 문서화한다.

## 로컬 개발

* Supabase Studio의 Authentication 화면에서 사용자 생성
* 해당 사용자 UUID의 `profiles.role`을 `editor` 또는 `admin`으로 변경

## Hosted Supabase

* Supabase Dashboard의 Authentication에서 사용자 생성 또는 초대
* 해당 사용자의 profile 역할을 DB에서 변경

예시 SQL은 placeholder만 사용한다.

```sql
update public.profiles
set role = 'admin'
where id = '<AUTH_USER_UUID>';
```

실제 UUID, 이메일, 비밀번호를 문서에 작성하지 마라.

공개 회원가입을 활성화하지 마라.

# 61. 최종 완료 기준

다음 조건을 모두 만족하면 이번 작업을 완료한 것으로 본다.

* 실제 Supabase email/password 로그인이 동작한다.
* 로그인은 Server Action을 통해 처리된다.
* 로그인 입력을 서버에서 검증한다.
* 로그인 실패 시 계정 존재 여부를 노출하지 않는다.
* 로그인 성공 후 profiles 역할을 확인한다.
* member는 관리자 접근이 차단된다.
* editor는 관리자 접근이 허용된다.
* admin은 관리자 접근이 허용된다.
* 안전한 next 경로로 복귀한다.
* 외부 Open Redirect가 차단된다.
* 실제 로그아웃이 동작한다.
* 로그아웃은 현재 세션 범위로 처리된다.
* 관리자 Header에 실제 사용자 정보가 표시된다.
* `/admin/unauthorized` 페이지가 존재한다.
* Proxy가 Auth token을 갱신한다.
* Proxy가 미로그인 관리자를 로그인 페이지로 redirect한다.
* Proxy가 최종 역할 판단의 유일한 계층이 아니다.
* 관리자 Dashboard Layout이 역할을 다시 검증한다.
* Service Role Key를 사용하지 않는다.
* `getSession()` user 객체를 권한 판단에 사용하지 않는다.
* 역할은 `profiles.role`에서 조회한다.
* 공개 페이지는 인증 없이 정상 동작한다.
* 공개 Supabase 조회에 회귀가 없다.
* 관리자 콘텐츠 화면은 아직 mock data를 사용한다.
* 관리자 CRUD는 구현하지 않는다.
* 환경 변수가 없어도 lint와 build가 성공한다.
* 실제 계정·비밀번호·token이 코드나 Git diff에 없다.
* 모바일과 접근성에 회귀가 없다.
* `pnpm lint`, `pnpm build`, `pnpm exec tsc --noEmit`이 통과한다.

# 3. 공식 구현 기준

Next.js App Router의 페이지와 레이아웃은 기본적으로 Server Component이므로, 공개 데이터 조회는 페이지 또는 상위 Server Component에서 수행하고 UI 컴포넌트에는 props로 전달한다.

Supabase 서버 클라이언트는 기존 `src/lib/supabase/server.ts`를 재사용한다.

프로젝트 멤버, 프로젝트 링크, 모집 절차는 Supabase의 외래키 관계 기반 nested select를 사용하거나 독립 조회를 병렬로 수행할 수 있다.

현재 설치된 다음 항목의 실제 버전과 타입을 확인한 뒤 구현한다.

```text
next
react
@supabase/supabase-js
@supabase/ssr
```

과거 버전의 API를 추측하지 마라.

# 7. 데이터 소스 정책

공개 query는 다음 정책을 따라야 한다.

## Supabase 환경 변수가 없는 경우

```text
mock data 또는 기존 config 사용
```

목적:

* 환경 변수 없이 lint와 build 유지
* 신규 개발자의 초기 실행 가능
* Supabase 미설정 Preview 환경 보호

## Supabase 환경 변수가 있는 경우

```text
Supabase만 사용
```

Supabase 조회가 실패했을 때 mock data로 조용히 fallback하지 마라.

그렇게 하면 다음 문제를 숨길 수 있다.

* 잘못된 RLS
* 잘못된 migration
* DB 연결 실패
* 잘못된 query
* seed 누락
* 잘못된 환경 변수

## 최종 정책

```text
Supabase 미설정 → mock fallback
Supabase 설정 + 조회 성공 → Supabase 결과
Supabase 설정 + 조회 실패 → 명확한 오류
```

환경 변수 설정 여부를 공개 UI에 표시하지 마라.

# 8. 공개 query와 관리자 mock query 분리

현재 관리자 페이지가 기존 query 함수를 사용한다면, 공개 query를 Supabase로 바꾸는 과정에서 관리자 페이지가 깨질 수 있다.

관리자 화면은 아직 인증과 CRUD를 연결하지 않으므로 mock data를 계속 사용해야 한다.

권장 구조:

```text
src/features/projects/
├─ queries.ts
├─ admin-queries.ts
├─ mock-data.ts
└─ mappers.ts

src/features/notices/
├─ queries.ts
├─ admin-queries.ts
├─ mock-data.ts
└─ mappers.ts

src/features/recruitment/
├─ queries.ts
├─ admin-queries.ts
├─ mock-data.ts
└─ mappers.ts
```

역할:

```text
queries.ts
- 공개 페이지용
- Supabase 설정 시 실제 공개 데이터
- 미설정 시 mock fallback

admin-queries.ts
- 현재 관리자 UI 전용
- mock data 사용
- 관리자 CRUD 단계에서 교체 예정

mappers.ts
- Supabase row를 기존 도메인 타입으로 변환
```

기존 관리자 페이지가 `queries.ts`를 사용한다면 import만 `admin-queries.ts`로 변경한다.

관리자 UI의 마크업과 기능은 수정하지 마라.

# 9. 공개 query 함수 비동기 전환

Supabase 조회를 수행하는 공개 query 함수는 비동기로 변경한다.

예:

```ts
export async function getAllProjects(): Promise<Project[]>;

export async function getFeaturedProjects(
  limit?: number,
): Promise<Project[]>;

export async function getProjectBySlug(
  slug: string,
): Promise<Project | undefined>;
```

공지사항:

```ts
export async function getAllNotices(): Promise<Notice[]>;

export async function getLatestNotices(
  limit?: number,
): Promise<Notice[]>;

export async function getNoticeBySlug(
  slug: string,
): Promise<Notice | undefined>;
```

모집:

```ts
export async function getCurrentRecruitment():
  Promise<Recruitment | undefined>;
```

기존 호출부도 모두 `await`를 사용하도록 수정한다.

Client Component에서 query 함수를 호출하지 마라.

Supabase error를 사용자 화면에 그대로 노출하지 마라.

# 11. 프로젝트 mapper

다음 파일을 생성한다.

```text
src/features/projects/mappers.ts
```

DB row와 관계 데이터를 기존 `Project` 타입으로 변환한다.

필요한 타입은 생성된 Database 타입에서 가져온다.

예시 방향:

```ts
type ProjectRow =
  Database["public"]["Tables"]["projects"]["Row"];

type ProjectMemberRow =
  Database["public"]["Tables"]["project_members"]["Row"];

type ProjectLinkRow =
  Database["public"]["Tables"]["project_links"]["Row"];
```

최소 mapper:

```ts
export function mapProjectRowToProject(
  row: ProjectRowWithRelations,
): Project;
```

## 매핑 기준

```text
id              → id
slug            → slug
title           → title
summary         → summary
description     → description
status          → status
tags            → tags
featured        → featured
started_at      → startedAt
released_at     → releasedAt
created_at      → createdAt
project_members → members
project_links   → links
```

프로젝트 링크:

```text
link_type → type
label     → label
url       → href
```

프로젝트 멤버:

```text
name → name
role → role
```

## 관계 정렬

```text
project_members.sort_order 오름차순
project_links.sort_order 오름차순
```

## thumbnail 처리

DB의 `thumbnail_path`는 향후 Storage 내부 경로다.

Storage가 아직 구현되지 않았으므로 다음 원칙을 따른다.

* `thumbnail_path`가 없으면 기존 placeholder UI 사용
* 존재하지 않는 공개 URL을 만들지 않음
* Storage public URL을 추측하지 않음
* Service Role Key를 사용하지 않음
* 현재 `Project` 타입이 `thumbnailUrl` 필수라면 optional 변경 가능성을 검토
* 타입 변경이 필요하면 모든 사용처를 안전하게 수정

가짜 이미지 URL을 만들지 마라.

# 14. 프로젝트 상세 조회

다음 함수를 Supabase 기반으로 전환한다.

```ts
getProjectBySlug(slug: string)
```

조건:

```text
slug = 전달된 slug
publication_status = published
```

다음 관계 데이터를 포함한다.

```text
project_members
project_links
```

가능하면 foreign key 관계 기반 nested select를 사용한다.

개념적 형태:

```ts
.select(`
  id,
  slug,
  title,
  summary,
  description,
  thumbnail_path,
  status,
  tags,
  featured,
  started_at,
  released_at,
  created_at,
  project_members (
    id,
    name,
    role,
    sort_order
  ),
  project_links (
    id,
    link_type,
    label,
    url,
    sort_order
  )
`)
```

실제 relation 이름과 타입은 생성된 schema를 기준으로 작성한다.

관계 추론이 불안정하거나 타입이 과도하게 복잡해지면 다음 방식도 허용한다.

1. 프로젝트 본문 조회
2. 멤버와 링크를 `Promise.all`로 병렬 조회
3. mapper에서 조합

N+1 query를 만들지 마라.

존재하지 않는 프로젝트는 `undefined`를 반환한다.

# 17. generateStaticParams 처리

# 26. site_settings 조회

singleton row를 조회한다.

조건:

```text
id = 1
```

행이 없으면 기존 `siteConfig`를 fallback으로 사용할 수 있다.

전역 metadata와 Header 브랜드를 이번 단계에서 완전히 DB 의존적으로 만들 필요는 없다.

# 29. 메인 페이지 데이터 병렬 조회

가능한 경우 `Promise.all`을 사용한다.

개념적 예시:

```ts
const [
  featuredProjects,
  latestNotices,
  recruitment,
  socialLinks,
] = await Promise.all([
  getFeaturedProjects(3),
  getLatestNotices(3),
  getCurrentRecruitment(),
  getPublicSocialLinks(),
]);
```

실제 컴포넌트 구조에 따라 페이지 또는 상위 Server Component에서 수행한다.

UI 컴포넌트에는 props로 전달한다.

불필요한 waterfall을 만들지 마라.

# 34. 공개 query의 RLS 의존성

공개 query에서는 다음을 사용하지 않는다.

* Service Role Key
* 관리자 세션
* RLS 우회
* 서버 전용 Secret Key
* 직접 SQL
* RPC 기반 권한 우회

기존 공개 Supabase 서버 클라이언트와 Publishable Key를 사용한다.

RLS가 공개된 row만 반환하도록 유지한다.

query에서도 `publication_status = published` 조건을 명시하여 코드 의도를 분명하게 한다.

* 기존 도메인 타입 전체 조회
* 목록과 상세 mapper 분리

오류 원문, SQL, RLS 정책명, 환경 변수 내용을 화면에 표시하지 마라.

새 Client Component는 error boundary에 필요한 최소 범위로 제한한다.

# 39. 빈 상태와 오류 상태 구분

# 42. 타입 안전성

다음을 준수한다.

* `any` 사용 금지
* `unknown as Project` 같은 이중 단언 금지
* `as never`로 Supabase 타입 오류 우회 금지
* DB row 타입 수동 중복 작성 금지
* 생성된 Database 타입 활용
* enum mapper에서 허용되지 않은 값 방어
* nullable 컬럼 안전 처리
* nested relation이 null 또는 배열인지 실제 타입 확인
* `single()`과 `maybeSingle()`을 목적에 맞게 사용
* query 결과가 없을 수 있는 상세 조회는 안전하게 처리

Supabase 관계 타입 추론이 불완전할 경우 최소 범위의 명시 타입을 사용할 수 있다.

그 경우 생성된 Database 타입에서 조합하고, 임의 인터페이스를 DB schema와 중복 작성하지 마라.

# 46. RLS 검증

* published 프로젝트 조회 가능
* draft 프로젝트 조회 불가
* published 공지 조회 가능
* draft 공지 조회 불가
* 현재 공개 모집 조회 가능
* 비공개 모집 조회 불가
* 활성 연락처만 조회
* 활성이고 URL이 있는 SNS만 조회
* 공개 project의 member/link만 조회

필요하다면 Supabase SQL test 또는 로컬 REST 요청으로 확인한다.

RLS 오류를 query 수정으로 우회하지 마라.

정책이 잘못됐다면 이번 단계에서 기존 migration을 직접 수정하지 말고 새 migration이 필요한지 보고한다.

프롬프트 1 migration이 아직 로컬에만 있고 적용 이력이 없다면 수정 가능 여부를 현재 프로젝트 규칙에 따라 판단하되, 이미 적용된 migration을 무단 수정하지 마라.

# 56. 최종 완료 기준

다음 조건을 모두 만족하면 이번 작업을 완료한 것으로 본다.

* 실제 Database 생성 타입을 사용한다.
* 공개 프로젝트 목록이 Supabase에서 조회된다.
* 공개 프로젝트 상세가 Supabase에서 조회된다.
* 프로젝트 멤버와 링크 관계가 조회된다.
* 대표 프로젝트가 Supabase에서 조회된다.
* 공개 공지사항 목록과 상세가 Supabase에서 조회된다.
* 최신 공지가 Supabase에서 조회된다.
* 현재 모집 정보와 절차가 Supabase에서 조회된다.
* 사이트 설정, 연락처, SNS의 공개 조회 기반이 존재한다.
* DB row와 기존 도메인 타입 사이 mapper가 존재한다.
* UI 컴포넌트가 Supabase에 직접 의존하지 않는다.
* Supabase 미설정 시 mock/config fallback이 동작한다.
* Supabase 설정 후 조회 오류가 mock으로 숨겨지지 않는다.
* 공개 데이터 없음과 조회 오류가 구분된다.
* 존재하지 않는 프로젝트와 공지는 404 처리된다.
* 관리자 화면은 mock data를 계속 사용한다.
* 관리자 인증과 CRUD는 구현하지 않는다.
* Service Role Key를 사용하지 않는다.
* 공개 RLS를 우회하지 않는다.
* 실제 환경 변수와 token을 출력하지 않는다.
* 모바일과 접근성에 회귀가 없다.
* `pnpm lint`, `pnpm build`, `pnpm exec tsc --noEmit`이 통과한다.

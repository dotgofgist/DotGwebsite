# 1일차 작업내용 요약서

## 개요

1일차 작업에서는 DotG 웹사이트의 기본 뼈대를 먼저 구축한 뒤, mock data 중심 구조를 Supabase 기반의 실제 데이터 관리 구조로 확장했다.

작업은 크게 두 단계로 진행했다.

- 기본구조: 공개 사이트, 관리자 UI, 공통 컴포넌트, mock data 기반 기능, Supabase 연결 준비
- 구현단계: Supabase DB, Auth, 관리자 CRUD, Storage 이미지 관리, 최종 검증

설치한 패키지:

- `@supabase/ssr`
- `@supabase/supabase-js`

추가한 구조:

- `src/lib/supabase/env.ts`
- `src/lib/supabase/client.ts`
- `src/lib/supabase/server.ts`

환경 변수가 없어도 import, lint, build가 실패하지 않도록 구성했다.

## 2. 구현단계 진행

### Supabase DB 기반 구축

Supabase local 개발 구성을 추가하고 초기 콘텐츠 스키마 migration을 작성했다.

주요 테이블:

- `profiles`
- `projects`
- `project_members`
- `project_links`
- `notices`
- `recruitments`
- `recruitment_steps`
- `site_settings`
- `contact_items`
- `social_links`

주요 enum:

- `content_status`
- `project_status`
- `project_link_type`
- `recruitment_status`
- `user_role`

public schema 전체에 RLS를 적용했고, `anon`, `authenticated member`, `editor`, `admin` 역할별 읽기/쓰기 경계를 설계했다.

추가로 seed data, DB 테스트, RLS 테스트를 구성하고 `docs/database-schema.md`와 README에 로컬 개발 절차를 문서화했다.

### 공개 페이지 Supabase 조회 전환

공개 페이지 query를 async 구조로 전환했다.

Supabase 환경 변수가 없는 환경에서는 기존 mock/config fallback을 유지하고, Supabase 환경 변수가 있는 환경에서는 조회 실패를 명확한 오류로 처리하도록 정리했다.

프로젝트, 공지사항, 모집, 설정 관련 query 계층을 분리하고 공개 route에 loading/error boundary를 추가했다.

### Supabase Auth 관리자 인증

Supabase email/password 기반 관리자 로그인 흐름을 구현했다.

주요 작업:

- 로그인/로그아웃 Server Action 추가
- 로그인 입력값 검증
- 안전한 `next` redirect 검증
- `/admin` 보호 proxy 추가
- `requireContentManager()` 기반 관리자 권한 재검사
- `editor`, `admin`만 관리자 화면 접근 허용
- `/admin/unauthorized` 페이지 추가
- 관리자 Header에 로그인 관리자 정보와 로그아웃 흐름 연결
- `docs/authentication.md` 추가

### 관리자 프로젝트 CRUD

관리자 프로젝트 목록과 상세 query를 mock에서 Supabase 조회로 전환했다.

- 프로젝트 mapper 추가

- slug, 상태, 태그, 날짜, 멤버, 외부 링크 URL 검증
- 관리자 프로젝트 목록, 생성, 수정, 삭제 UI 연결
- `docs/project-management.md` 추가

### 관리자 공지사항 CRUD

모집 관리를 mock 단일 폼에서 Supabase 기반 목록, 생성, 수정, current 관리 흐름으로 전환했다.

- 처음 `published` 전환 시 `published_at` 설정
- current 지정 시 기존 current 해제 후 새 current 지정
- archived 모집의 current 지정 차단
- 영구 삭제 대신 archive 흐름 사용
- 공개 모집 query는 `is_current = true` 및 `publication_status = published`만 반환
- `docs/recruitment-management.md` 추가

### 사이트 설정, 연락처, SNS 관리

사이트 설정, 연락처, SNS 관리 UI를 Supabase 기반 관리자 조회 및 CRUD 흐름으로 전환했다.

구현 내용:

- `site_settings` singleton row 관리
- 사이트 설정은 `id = 1` 기준 upsert
- 연락처 생성/수정/삭제, 활성/비활성, 정렬 순서 관리
- SNS 링크 생성/수정/삭제, 활성/비활성, 정렬 순서 관리
- 공개 연락처 조회는 `is_active = true`로 제한
- 공개 SNS 조회는 `is_active = true` 및 `url is not null`로 제한
- 연락처 URL은 `http`, `https`, `mailto`만 허용
- SNS URL은 `http`, `https`만 허용
- Header, Footer, Hero, Club summary, Contact card, SNS banner를 Supabase 데이터와 연결
- `docs/site-settings-management.md` 추가

### Supabase Storage 이미지 관리

Supabase Storage 기반 이미지 관리 기능을 추가했다.

추가한 public bucket:

- `project-images`
- `site-assets`

Storage RLS 정책:

- 공개 이미지는 `anon`, `authenticated`가 읽을 수 있음
- `editor`, `admin`만 업로드/수정/삭제 가능
- 프로젝트 이미지는 `{projectId}/thumbnail/...` 경로로 제한
- 사이트 이미지는 `logo/...`, `hero/...` 경로로 제한

구현 내용:

- `site_settings.logo_path`, `site_settings.hero_image_path` 컬럼 추가
- 프로젝트 대표 이미지 업로드/교체/삭제 UI 및 Server Action 추가
- 프로젝트 삭제 시 기존 thumbnail object 삭제 시도
- 사이트 설정 관리자 화면에 로고/Hero 이미지 업로드/교체/삭제 UI 추가
- 공개 Header 로고와 메인 Hero 이미지를 Supabase Storage public URL로 렌더링
- DB에는 public URL이 아니라 object path만 저장
- query mapper에서 Supabase public URL 생성
- JPEG, PNG, WebP만 허용
- MIME type과 파일 signature를 함께 검증
- SVG 등 허용하지 않은 형식 차단
- `next.config.ts`에 Supabase Storage remote pattern 추가
- `docs/storage-management.md` 추가
- README와 schema 문서 갱신

## 3. 최종 구현 상태

- 공개 페이지는 Supabase가 설정된 환경에서 실제 DB 데이터를 조회한다.
- Supabase가 설정되지 않은 환경에서는 일부 공개 페이지가 기존 fallback 데이터를 사용한다.
- 관리자 화면은 Supabase Auth와 `profiles.role` 기반 권한 검사를 사용한다.
- `editor`, `admin`은 콘텐츠 관리가 가능하다.
- `member`, `anon`은 관리자 mutation을 수행할 수 없다.
- 프로젝트, 공지사항, 모집, 사이트 설정, 연락처, SNS 링크는 관리자 화면에서 Supabase에 저장된다.
- 프로젝트 대표 이미지, 사이트 로고, Hero 이미지는 Supabase Storage에 저장된다.
- 이미지 URL 자체를 DB에 저장하지 않고 object path만 저장한다.
- 공개 렌더링 시점에 Supabase public URL을 생성한다.
- service role key나 secret을 앱 코드에 하드코딩하지 않았다.

## 7. 1일차 정리

1일차에는 DotG 웹사이트의 공개 화면, 관리자 화면, 데이터 접근 구조, 인증, 권한, 콘텐츠 관리, 이미지 관리까지 이어지는 핵심 기반을 구축했다.

초기에는 mock data를 활용해 화면과 구조를 빠르게 세웠고, 이후 Supabase DB, Auth, RLS, Server Action, Storage를 연결해 실제 운영 가능한 관리 흐름으로 확장했다.
